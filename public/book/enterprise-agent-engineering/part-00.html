Part 0｜先别急着做 Agent

真正优秀的 AI 工程师，往往不是最先想到“用 Agent”的那个人，而是最先问“这个问题到底需不需要 Agent”的那个人。

开始之前

如果你是一名后端工程师，那么你大概已经见过很多这样的技术浪潮。

微服务出现的时候，大家开始讨论服务拆分。

容器流行的时候，大家开始讨论 Docker。

Serverless 出现的时候，大家开始讨论函数是不是会取代服务器。

而现在，轮到了 Agent。

你可能已经在工作中看到过类似的需求：“大模型现在这么强，我们是不是也应该做个 Agent？”

或者：“隔壁部门已经有 AI 助手了，我们这个业务是不是也能接一个？”

再或者：“老板说今年要搞 Agent，大家看看我们有什么场景可以上。”

如果你已经开始接触 LLM，你甚至可能已经会调用 GPT、Claude、DeepSeek、Qwen 或其他模型。

那么看起来，你离“AI 工程师”似乎只差一步：

调用模型
    ↓
加个 Prompt
    ↓
接几个 Tool
    ↓
再套一个 Agent Framework
    ↓
完成

事实上，真正困难的地方恰恰不在这里。

困难的是：

困难的是：当一个模型进入你的软件系统以后，你到底应该让它做什么？

更重要的是：

什么事情可以交给它，什么事情不能交给它？

这门课从这里开始。

我们暂时不写 Agent。

也暂时不讨论某个框架有多漂亮。

甚至先不讨论 Prompt Engineering。

我们先做一件更基础、也更重要的事情：

重新认识我们正在解决的问题。

本书的实验怎样安排

本书的实验先服务于一个认知目标，而不是要求你一次读懂整个仓库。通常先完成主实验：使用本地 Fixture、FakeModel 或确定性测试，观察接口、状态、行动边界和失败处理是否符合契约。每一步都要回答三个问题：我在验证什么、观察到了什么、这个结果能支持什么结论？

只有明确写有 “可选真实模型实验” 的小节才会调用真实 Provider。它不是主线的前置条件；运行前要确认 Provider、模型、费用和输入数据处理条件。真实模型结果只代表本次配置与样本下的观察，不能替代离线契约测试，也不能自动证明生产效果。任何远端业务写操作都不属于默认学生主线。

章节中的作者参考实现、完整测试矩阵和生产加固细节，也不意味着每个读者都必须逐项重做。先完成本节明确的主路径，再根据目标进入深入实验。

0.1 从后端工程师到 AI Application Engineer

0.1.1 你其实已经拥有了很多 AI 工程能力

假设你现在维护一个订单系统。

它可能有这样的接口：

@app.get("/orders/{order_id}")
def get_order(order_id: int):
    return order_service.get_order(order_id)

请求进来以后，系统查数据库，然后把结果返回出去。

如果需求是：

如果需求是查询订单 10001 当前状态。

那么整个过程非常明确：

HTTP Request
    ↓
API
    ↓
Business Logic
    ↓
Database
    ↓
Response

作为后端工程师，你会自然地考虑：

  • 参数是否合法？
  • 用户有没有权限？
  • 数据库查询是否正确？
  • 超时怎么办？
  • 查询失败怎么办？
  • 是否需要缓存？
  • 日志记在哪里？
  • 怎么测试？
  • QPS 上来怎么办？

这些都是非常成熟的工程问题。

现在换一种需求：“用户不要输入订单号了。用户直接说：帮我看看张伟上周买的那台车现在为什么还没发货。”

表面上看，似乎只是多了一个聊天框。

但从系统角度看，问题马上发生了变化。

系统需要先理解：

  • “张伟”是谁？
  • “上周买的那台车”对应哪个订单？

然后它可能需要查询订单系统。

如果发现订单已经发出，又需要查询物流系统。

如果物流状态异常，还可能需要查询售后系统。

最后再把多个系统的信息组织成用户能够理解的语言。

执行过程可能变成：

用户问题
   ↓
理解用户意图
   ↓
识别订单
   ↓
查询订单系统
   ↓
观察结果
   ↓
决定是否继续查询
   ↓
查询物流系统
   ↓
综合信息
   ↓
生成回答

注意，这里面真正新出现的东西并不是“后端”。

订单 API 还是后端。

数据库还是数据库。

物流服务还是后端。

权限系统还是后端。

日志、缓存、队列、事务，这些仍然都是后端问题。

变化的是：

系统里多了一个能够处理自然语言、进行一定程度判断，并可能参与下一步决策的组件。

这个组件，就是 LLM。

0.1.2 LLM 到底是什么？

很多初学者会问：“LLM 是不是一种新的数据库？”

不是。

也有人会问：“LLM 是不是新的后端服务？”

从部署形态上看，它当然可以通过服务提供给你的应用调用，但从软件工程角色上说，这个理解仍然不够准确。

更合适的理解是：

LLM 是一种具有概率性的计算组件。

你把输入和上下文交给它，它会根据训练得到的模型能力生成一个输出。

例如：

输入：
“这个用户的投诉属于哪种类型？”

输出：
“物流延迟”

或者：

输入：
“解释为什么订单一直没有发货。”

输出：
“一段自然语言解释”

这里最重要的区别是：

对于传统函数，我们经常期待：

result = calculate_price(order)

它应该遵循明确的计算规则。

而对于：

result = model.generate(prompt)

你面对的是一种概率性输出。

这意味着：

LLM 更像一种新的计算能力，而不是传统业务规则的替代品。

于是，AI Application Engineering 的第一个核心问题出现了：

如何把这种概率性的计算能力，放进一个原本高度强调确定性、可控性和可靠性的工程系统里？

这就是我们真正要学习的东西。

0.1.3 AI Application 并不等于 Agent

这是我们在整门课程中要尽早建立的第一个概念边界。

假设我们有下面这个功能：

用户输入一段客服工单，系统自动判断它属于哪一类。

系统可能只是：

User Input
   ↓
LLM
   ↓
Structured Output
   ↓
Business Logic

这已经是一个 AI Application。

但它并不是 Agent。

再比如：

再比如：根据公司制度回答员工报销问题。

系统可能是：

Question
   ↓
Retrieve Documents
   ↓
LLM
   ↓
Answer

这也是 AI Application。

同样不一定需要 Agent。

所以：

AI Application 是更大的概念，Agent 只是其中一种系统形态。

你可以做 AI Application，而完全不做 Agent。

这一点听起来似乎非常简单，但它会影响整个课程的学习方式。

如果把“AI Application”误解成“Agent”，你很容易形成一种错误习惯：

看到任何 AI 问题，就开始设计 Agent。

我们希望你形成的恰恰相反：

看到问题，先判断它需要什么能力。

0.1.4 后端工程师真正需要增加什么能力？

这里有一个好消息。

你不需要把自己过去学过的东西扔掉。

恰恰相反，你过去积累的工程经验非常重要。

传统后端已经解决了很多 AI 系统仍然需要解决的问题：

API
Database
Authentication
Authorization
State
Concurrency
Caching
Queue
Transaction
Observability
Reliability
Testing

AI 系统只是增加了一组新的问题：

Model
Context
Retrieval
Tool
Memory
Evaluation
AI Runtime

所以可以用这样一个模型来理解：

Backend Engineering
        +
AI-specific Engineering
        ↓
AI Application Engineering

更具体一点：

传统后端负责：
数据、状态、权限、事务、执行、可靠性

AI 层负责：
理解、生成、分类、推理、动态决策

应用工程负责：
把两者安全、可靠地组合起来

这也是为什么，从后端工程师转向 AI Application Engineer，实际上是一种能力叠加，而不是推倒重来。

你已经会盖房子。

现在只是房子里多了一种过去没有的、行为并不完全确定的“新型施工材料”。

问题变成了：

问题变成了：这种材料应该放在哪里？

0.1.5 一个重要的工程边界

考虑这样一种架构：

用户
 ↓
LLM
 ↓
直接操作数据库
 ↓
返回结果

它看起来很“智能”。

用户说一句话，模型自己决定 SQL，自己执行，自己修改数据。

但如果你真正做过生产系统，应该会本能地产生怀疑：

谁负责权限？

谁保证事务？

谁保证只能修改允许修改的数据？

谁记录审计？

谁处理重复执行？

谁保证金额不会算错？

谁阻止恶意输入？

谁处理数据库异常？

这时你会发现：

LLM 可以参与决策，但不意味着 LLM 应该拥有整个系统的控制权。

更常见的工程思路是：

                    ┌─────────────┐
User ─────────────→ │ AI Runtime  │
                    └──────┬──────┘
                           │
                    产生决策 / 请求
                           │
                           ↓
                    ┌─────────────┐
                    │ Backend     │
                    │ Controls    │
                    └──────┬──────┘
                           │
                  权限 / 校验 / 执行
                           │
                           ↓
                    Business System

AI 决定“可能应该做什么”。

传统工程体系负责保证：“即使 AI 决定错了，系统也不能随便把事情做坏。”

这个边界以后会贯穿：

  • Tool Calling
  • Agent
  • Security
  • Production
  • Human-in-the-loop

先画出现在的架构。

然后再问自己：

本章留下一个问题

你现在应该已经发现：

AI Application 并不是“把 LLM API 接进后端”这么简单。

但是还有一个更麻烦的问题。

传统软件最让工程师安心的一件事是：

同样的输入，系统应该稳定地给出同样的结果。

那么 LLM 呢？

答案并不一样。

下一章，我们来看一件会彻底改变工程方法的事情：

概率性软件。

0.2 当软件开始“没那么确定”

0.2.1 传统软件最舒服的地方

想象这样一个函数：

def calculate_total_price(price: float, quantity: int) -> float:
    return price * quantity

输入：

price = 100
quantity = 3

你期待输出：

300

不是：

299

也不是：

“差不多是 300”

更不是：

“根据我的理解，这件商品总价应该在 280～320 之间。”

传统软件之所以好用，很大程度上就是因为它遵循确定的规则。

你可以写：

assert calculate_total_price(100, 3) == 300

然后把这类测试不断积累起来。

这就是软件工程非常重要的一部分：

把系统行为固定下来，并持续验证。

0.2.2 现在换成一个语言任务

假设你希望程序判断：“这个用户是在投诉物流，还是投诉商品质量？”

你把下面的文本给模型：“东西已经到了，但是包装完全坏了，里面的产品也有划痕。”

模型可能回答：

模型可能回答商品质量

也可能认为：

也可能认为：物流问题

甚至给出：

甚至给出物流导致的商品损坏

到底哪一个是错的？

这件事比 100 × 3 = 300 复杂得多。

因为这里不存在一个天然唯一的答案。

有些任务本身就带有：

  • 语言歧义
  • 上下文依赖
  • 信息缺失
  • 多种合理解释

因此，AI 系统中的“正确性”开始发生变化。

0.2.3 这并不意味着 AI 是“不可靠的软件”

这里容易产生一个误解：“既然 AI 有概率性，那它是不是就不能做工程？”

不是。

真正的变化是：

传统软件常常更接近：

Correct / Incorrect

AI 系统则经常更像：

在一个任务分布上，
它能有多大概率完成任务？

例如：

一个分类 Agent 在 100 个测试案例中：

正确 94 个
错误 6 个

我们就可以讨论：

Task Success Rate = 94%

然后继续分析：

然后继续分析：那 6 个为什么错？

这就引出了整个 AI Engineering 中非常重要的概念：

Evaluation。

0.2.4 为什么“Demo 成功”毫无意义？

假设你做了一个售后 Agent。

你输入：“我的车充不上电怎么办？”

Agent 回答得非常漂亮。

你很高兴。

于是你把截图发给领导。

领导说：“不错，什么时候上线？”

这时候真正的问题才刚刚开始。

你有没有测试过：

  • “我的车完全没反应。”
  • “充电桩一直跳枪。”
  • “换了三个充电桩都不行。”
  • “充电速度比以前慢了一半。”
  • “是车辆问题还是充电桩问题？”
  • “昨天晚上开始发生。”
  • “我不知道车辆具体型号。”

更不用说：

  • 错误的工具调用
  • 工具超时
  • 数据缺失
  • 权限不足
  • 恶意输入
  • 极端边界条件

所以：

一个成功回答的 Demo，只证明这个案例成功了。

它不能证明：

系统在真实任务分布中表现良好。

这是 AI Application Engineering 和传统 Demo-driven Development 的一个重要分界点。

0.2.5 AI 系统多了一层“失败面”

传统系统当然也会失败。

但是 AI 系统会多出一整类新的失败方式。

例如：

模型理解错了
模型选择错了
模型产生幻觉
模型用了错误的数据
模型没有看到关键信息
模型调用了错误工具
模型参数填错了
模型在多个步骤之间丢失状态

你可以把它想象成：

传统系统

Code
 ↓
Data
 ↓
Infrastructure

而 AI 系统变成：

Code
 ↓
Context
 ↓
Model
 ↓
Tool
 ↓
External Data
 ↓
State
 ↓
Infrastructure

失败面自然变大。

因此一个非常重要的工程转变出现了：

以前我们主要问“代码有没有 Bug”。

现在我们还必须问“模型在这些任务上表现得怎么样”。

0.2.6 第一次建立 Dataset 意识

我们现在先不做复杂 Evaluation。

只做一个很小的实验。

假设任务是：

把客服文本分类成 物流 / 商品 / 退款 / 其他。

建立：

期望：商品

case_003
输入：我不想要了，怎么退款？
期望：退款

然后让模型运行。

记录：

Input
Expected
Actual
Match

这张表非常简单。

但它其实已经是 Evaluation 的雏形。

以后我们会把它逐渐发展成：

Dataset
    ↓

    ↓
Evaluator
    ↓
Metrics
    ↓
Regression

你可以暂时把它理解成：

我们开始把“感觉不错”变成“有数据证明”。

0.2.7 遇到失败时，不要急着改 Prompt

这是 AI 工程中非常常见的坏习惯。

例如 Agent 选错了工具。

初学者通常会马上说：“Prompt 再写详细一点。”

有时候确实有效。

但也有可能根本不是 Prompt 的问题。

假设：

模型没有看到必要的信息

那应该修 Context。

如果：

工具的 description 写得很混乱

那应该修 Tool Design。

如果：

数据库本身就没有数据

那应该查 Data。

如果：

这个任务本身有多种合理答案

那你可能需要重新定义 Evaluation。

因此，碰到失败以后应该养成一个非常重要的习惯：

Failure
   ↓
Observe
   ↓
Classify
   ↓
Diagnose
   ↓
Fix

而不是：

Failure
   ↓
修改 Prompt
   ↓
再试一次

0.2.8 小练习：把一次成功变成十次测试

给自己找一个简单的 AI 任务。

例如：

例如：将一段工单分类。

准备至少 10 个案例。

其中故意加入：

  • 正常案例
  • 模糊案例
  • 缺失信息
  • 超长输入
  • 相互矛盾的信息

然后记录每一次结果。

你会第一次真正看到：

AI 系统不是“跑通”的，而是“测出来”的。

把这些案例里最容易失败的输入也记下来。到本 Part 的机会评估记录中，你会用它们定义初始的成功条件和停止条件；稍后在 Part 6，我们再把这样的案例组织成正式的评估集。

本章最重要的一句话

请记住：

在传统软件里，测试往往是在实现之后验证功能；在 AI 软件里，Evaluation 本身就是系统设计的一部分。

以后当你看到任何 AI 系统，都可以问：“你怎么证明它有效？”

如果对方只能回答：“你自己试试，效果挺好的。”

你就应该继续追问。

0.3 几类不同的技术选择：哪些能力需要组合？

现在我们知道 AI 系统和传统软件不完全一样。

但新的问题来了：

但新的问题来了：那么，什么时候该使用什么样的 AI 架构？

这时候很容易出现另一种误区：“越复杂的架构，能力越强，所以 Agent 应该是最终答案。”

事实恰恰相反。

0.3.1 软件架构不是游戏里的装备等级

在游戏里：

普通装备
↓
高级装备
↓
传奇装备

通常越高级越强。

但软件架构不是这样。

一个简单的：

if amount > 10000:
    require_manager_approval()

可能比一个复杂的 Agent 更适合审批系统。

因为软件的目标不是：

看起来多先进。

而是：

而是：用合适的复杂度解决问题。

所以我们先建立一个非常重要的原则：

架构复杂度应该由问题复杂度驱动

而不是反过来：

因为我学会了 Agent，所以问题必须用 Agent

0.3.2 规则清楚时，传统软件就够了

如果规则非常清楚：

金额 < 1000
    → 自动通过

1000 ≤ 金额 < 10000
    → 主管审批

金额 ≥ 10000
    → 财务审批

那就写规则。

没有必要调用 LLM。

没有必要 RAG。

没有必要 Agent。

因为问题本身是：

因为问题本身是：确定性的。

传统软件已经能很好地解决。

0.3.3 需要语言理解或生成时，加入 LLM

再看一个问题：“请把这段用户投诉总结成三句话。”

这里没有复杂流程。

也没有必要自主调用工具。

你只需要：

Input
 ↓
LLM
 ↓
Output

这就是非常典型的 LLM Application。

常见任务包括：

  • 分类
  • 提取
  • 总结
  • 改写
  • 翻译
  • 生成

0.3.4 缺少外部知识时，增加检索路径（RAG）

现在问题变成：“根据公司的报销制度，告诉我这次差旅能不能报销。”

普通 LLM 可能并不知道你公司的内部制度。

怎么办？

给它知识。

于是出现：

Question
   ↓
Retrieve Relevant Documents
   ↓
LLM
   ↓
Answer

这就是 RAG。

它解决的是：

模型缺少外部知识。

0.3.5 需要访问业务系统时，提供 Tool

再往前走一步。

用户说：“帮我查一下订单 10001。”

模型光知道文字是没用的。

它需要访问真正的订单系统。

于是出现：

LLM
 ↓
Tool
 ↓
Business System

例如：

query_order(order_id=10001)

这时候模型可以：

  1. 理解用户问题
  2. 决定需要查询订单
  3. 请求工具
  4. 获得结果

注意：

能调用 Tool，不等于已经是 Agent。

因为下一步是否继续、调用哪个工具、是否结束，仍然可以由你的 Workflow 明确规定。

0.3.6 流程可以预先定义时，使用 Workflow

假设企业规定了一个固定流程：

第一步：查询订单
第二步：查询物流
第三步：判断是否异常
第四步：生成回答

那么你完全可以写：

Query Order
   ↓
Query Logistics
   ↓
Check Status
   ↓
Generate Answer

这里可以有 LLM，也可以有 RAG，也可以有 Tool。

但是：

控制流程依然是程序员决定的。

这就是 Workflow。

0.3.7 需要动态选择下一步时，再考虑 Agent

什么时候 Workflow 开始不够用了？

假设任务变成：“调查这个订单为什么延迟。”

可能存在很多完全不同的情况：

先查订单
    ↓
如果订单没发货 → 查仓库

如果已经出库 → 查物流

如果物流停滞 → 查中转站

如果物流正常 → 查售后

如果数据冲突 → 再查另一套系统

此时你很难提前写死所有路径。

系统需要根据当前观察结果动态选择下一步。

于是开始出现：

Observe
   ↓
Decide
   ↓
Act
   ↓
Observe
   ↓
Decide
   ↓
Act

这就是我们开始称之为 Agent 的地方。

Agent 的关键不是：“它用了 LLM。”

而是：

下一步做什么，不完全由预先写死的 Workflow 决定。

0.3.8 需要有意义的分工时，再考虑 Multi-Agent

最后再考虑一种更复杂的任务：“研究某个汽车故障问题，结合历史案例、维修手册和零件库存，形成诊断建议，并生成维修执行计划。”

你可以让一个 Agent 全部完成。

也可以拆成：

Research Agent
      ↓
Analysis Agent
      ↓
Execution Agent

为什么要拆？

可能是因为：

  • 任务天然可以分工
  • 上下文差异很大
  • 权限边界不同
  • 某些任务可以并行
  • 一个 Agent 管理起来已经过于复杂

但再次强调：

Multi-Agent 不是天然比 Single Agent 好。

多个 Agent 也会带来：

  • 更多 Token
  • 更多延迟
  • 更多状态
  • 更多通信
  • 更复杂的失败传播

所以它也不是“升级版”。

0.3.9 把能力选择与控制流选择分开

刚才出现的名字并不属于同一条互斥的架构阶梯。它们回答的是不同问题：

需要回答的问题 可能采用的能力或设计 它解决什么问题
规则能否直接表达？ Traditional Software 让确定性规则由程序执行
需要理解或生成自然语言吗？ LLM Application 使用模型完成分类、提取、总结等任务
当前任务需要外部知识吗？ RAG 从受控知识源取得相关证据
当前任务需要访问业务系统吗？ Tool 让应用以受控接口查询或执行动作
执行路径能提前确定吗？ Workflow 由程序掌握主要流程和分支
下一步是否需要根据观察动态选择？ Agent 在运行时约束下把部分控制流交给模型
是否存在真实的角色边界或并行收益？ Multi-Agent 在不同能力、上下文、权限或执行节奏之间协作

这些选项可以组合。例如，一个系统可以采用 RAG + Tool + Workflow；也可以在固定 Workflow 的某个分支内放入一个 Agent。Multi-Agent 还可能调用 RAG 与 Tools。它们不是“由差到好”的等级，而是对知识、行动和控制流的不同选择。

因此，正确的判断方式不是从上往下选一个名字，而是先把问题拆成几项独立判断：

  1. 哪些规则应当由确定性代码执行？
  2. 哪些步骤需要模型进行语言理解或生成？
  3. 当前决策需要什么外部证据？
  4. 需要查询或改变哪些业务系统？
  5. 哪些流程可以预先定义，哪些步骤必须根据观察动态选择？
  6. 是否有充分理由把任务拆给多个角色？

最后再组合出最简单、能够达到目标的方案。

0.3.10 一个判断技巧

以后当别人跟你说：“这个需求需要 Agent。”

你可以连续问五个问题。

第一：

第一：规则能解决吗？

第二：

第二：如果不能，只需要语言理解吗？

第三：

第三：是不是只是缺少知识？

第四：

第四：是不是只是需要调用几个 API？

第五：

第五：下一步到底为什么需要动态决策？

最后这个问题尤其重要。

如果你发现：

如果你发现所有步骤都能提前规定。

那你很可能不需要 Agent。

在最后的机会评估记录里，请把“为什么需要动态决策”写成一句可被反驳的假设，而不是只勾选一个架构名称。例如，写明固定 Workflow 可能在哪些真实分支中失效，以及你准备通过什么案例判断这种差异是否重要。

0.4 有些问题，你真的不应该用 Agent

这一章非常容易被忽略。

但它其实决定了一个工程师到底是：“会使用 Agent。”

还是：

“懂 Agent 工程。”

0.4.1 一个很诱人的需求

假设老板说：“我们做一个 Agent，把公司的退款全部自动处理掉。”

听起来非常先进。

用户提出退款申请。

Agent：

  1. 读取订单。
  2. 判断原因。
  3. 查询政策。
  4. 决定退款金额。
  5. 执行退款。

然后大家可能会兴奋：“这不就是 Agent 的典型场景吗？”

从技术上说，当然可以做。

但问题是：

应该这样做吗？

0.4.2 为什么“能做”不等于“适合做”

一个系统是否应该交给 Agent，不只取决于模型能力。

至少还应该看：

Business Value
Complexity
Risk
Reliability
Cost
Latency
Auditability

假设退款规则其实非常明确：

购买 7 天内
+
商品未使用
+
符合售后政策
→
允许退款

那么让 Agent 来决定：“到底退不退？”

其实可能是在主动把一个确定性问题变成概率性问题。

这是一种非常典型的：

Overengineering。

0.4.3 确定性规则应该留在确定性系统里

一个更合理的架构可能是：

用户申请退款
      ↓
LLM
理解用户描述 / 提取原因
      ↓
结构化业务数据
      ↓
Deterministic Rules
      ↓
Refund Workflow
      ↓
Refund System

这里 AI 仍然发挥价值。

例如：

例如：从复杂的自然语言中提取退款原因。

但是：

真正决定退款资格的核心规则，仍然由确定性逻辑执行。

这就是 AI Boundary。

0.4.4 风险越高，自治边界越重要

考虑下面三件事情：

查询订单
修改订单
退款 10000 元

三者显然不是同一个风险等级。

我们可以粗略理解：

Read
 ↓
低风险

Write
 ↓
中风险

Irreversible / High-value Action
 ↓
高风险

这时候 Agent 的自治程度应该随风险变化。

例如：

查询订单
→ Agent 可自动完成

修改配送地址
→ 可能需要额外校验

退款
→ 根据金额/规则触发人工审批

所以一个成熟的 Agent 系统不会只问：“模型聪不聪明？”

还会问：

“模型有多大的权限？”

0.4.5 Agent 的自治程度不是越高越好

可以把系统想象成一条连续谱：

完全确定性
│
├── Rule
│
├── Workflow
│
├── LLM-assisted
│
├── Agent with constrained tools
│
├── Agent with broader autonomy
│
└── Highly autonomous Agent

越往后：

  • 自主性更强
  • 潜在能力更大

但同时也意味着：

  • 风险更高
  • 可控性更弱
  • 调试更复杂
  • Evaluation 更重要

所以真正成熟的设计通常不是：

尽可能追求最大自治。

而是：

在业务价值允许的前提下，给予 Agent 恰到好处的自治能力。

0.4.6 一个反直觉的例子

假设某公司的审批流程非常复杂。

有人可能会说：“规则这么复杂，正好交给 Agent。”

其实未必。

如果流程虽然复杂，但每一步规则仍然是明确的，那么程序化 Workflow 反而更适合。

真正需要 Agent 的地方，可能只是：

把人类提供的自然语言材料转换为结构化信息。

例如：

员工描述
   ↓
LLM
   ↓
提取：
金额
出差地点
日期
事由
   ↓
Deterministic Workflow
   ↓
审批

所以：

复杂，不代表一定需要 Agent。

我们真正关心的是：

复杂性来自哪里？

这是一个非常值得养成的工程习惯。

0.5 从一个陌生业务里找到真正值得做的事情

前面四章，我们已经建立了一套基本认知：

AI 不是 Agent
Agent 不是万能
复杂不等于先进
概率性意味着需要 Evaluation
AI 应该有边界

现在终于可以做一件真正接近工作现场的事情了。

0.5.1 你被调去了一个完全陌生的行业

假设你原本是一名金融数据后端工程师。

现在公司业务调整，你进入一家新能源汽车企业。

你对新能源汽车的业务几乎不了解。

第一天，你拿到这些东西：

Vehicle Service API
Battery Diagnostic API
Parts Inventory API
Warranty Policy Documents
Historical Service Records

产品经理告诉你：“我们想做一个 AI Agent，帮助维修人员诊断车辆问题。”

你该怎么办？

最危险的做法，是立即开始设计：

Supervisor Agent
   ↓
Research Agent
   ↓
Diagnosis Agent
   ↓
Execution Agent

因为你其实还不知道：

维修人员现在到底是怎么工作的。

0.5.2 第一步：先理解业务

真正的第一步，是问：

真正的第一步，是问：谁在使用？

可能是：

可能是：一线维修技师。

然后问：

然后问：他现在遇到什么问题？

假设你进一步了解到：

维修技师接到一辆故障车后，需要：

  1. 查看车辆基本信息。
  2. 查看故障码。
  3. 查看电池诊断信息。
  4. 查看历史维修记录。
  5. 对照维修手册。
  6. 判断可能原因。
  7. 查询所需零件。
  8. 形成维修建议。

你终于开始看到真实的业务流程了。

0.5.3 第二步：把流程拆开

现在先不要谈 Agent。

把整个过程画出来：

车辆进入维修

    ↓

读取车辆信息

    ↓

读取故障码

    ↓

读取电池诊断

    ↓

读取历史维修记录

    ↓

查询维修手册

    ↓

分析故障原因

    ↓

查询零件库存

    ↓

形成维修建议

接着继续问：

接着继续问：哪些步骤是确定性的？

例如：

读取车辆信息
读取故障码
查询库存

这些都非常适合：

API / Database / Traditional Backend。

0.5.4 哪些步骤真正需要“智能”？

再看：“结合故障码、历史案例、维修手册，分析这个问题最可能的原因。”

这里可能需要：

  • 非结构化知识理解
  • 多来源信息综合
  • 自然语言解释

这就是 AI 很可能有价值的地方。

再看：“下一步应该查哪个系统？”

如果故障类型非常多，而且无法提前写死所有路径，那么这里可能开始有 Agent 的价值。

于是你得到：

确定性数据访问
       ↓
Traditional Backend

知识查询
       ↓
RAG

故障理解 / 综合分析
       ↓
LLM

动态决定下一步调查路径
       ↓
Agent

注意：

Agent 只是整个系统中的一部分。

这才是我们想培养的 AI Application Engineer 思维。

0.5.5 一张业务机会分析表

以后面对任何陌生业务，你都可以先写这样一张表。

问题 需要问什么
Business Goal 要解决什么业务问题？
User 谁使用？
Current Process 现在怎么做？
Pain Point 最痛苦的地方在哪里？
Information 需要知道什么？
Decision 哪里需要判断？
Action 需要执行什么？
Uncertainty 哪些部分无法提前写死？
Risk 错了会怎样？
Side Effect 会不会修改真实业务数据？
Human 哪里需要人工批准？
Evaluation 怎样证明它有效？

这张表看起来不像“AI 技术”。

实际上，它很可能是你以后做 Agent 项目最重要的工具之一。

因为它迫使你：

先理解业务，再选择技术。

0.5.6 找三个不同的机会

回到新能源汽车维修的例子。

你可以发现三个完全不同的机会。

机会一：知识查询

“这个故障码是什么意思？”

最可能是：

RAG + LLM

没必要 Agent。

机会二：跨系统调查

“为什么这辆车突然充电变慢？”

需要：

车辆信息
+
电池诊断
+
历史记录
+
维修手册

而且可能根据前一步结果决定下一步查询什么。

这时：

Agent + Tools + RAG

就有可能合理。

机会三：查询零件库存

“这个维修方案需要什么零件，目前还有库存吗？”

这其实可能非常确定：

Repair Plan
   ↓
Parts API

完全没有必要为了“AI 化”而变成 Agent。

0.5.7 这才是真正的 AI Opportunity Discovery

你现在应该已经可以看出：

一个真实业务通常不是：

Use Agent

或者：

Don't Use Agent

这么简单。

更常见的情况是：

一个业务流程
       ↓
拆成很多任务
       ↓
有些用传统软件
有些用 LLM
有些用 RAG
有些用 Tool
有些用 Workflow
有些才需要 Agent

甚至同一个 Agent 系统内部，也应该存在：

明确的确定性边界。

所以最终你设计的不是：“一个 Agent。”

而是：

一个由确定性软件和概率性 AI 共同组成的系统。

Part 0 实验：把工程判断变成一份机会评估记录

到这里，你已经不止一次听到“先理解业务”“不要为了 Agent 而 Agent”这样的建议。建议本身并不难记，真正困难的是：当一个具体需求摆到面前时，你能不能把这些原则转化成一项别人也能审查的工程决策。

所以，本 Part 的实验不从代码开始。你要交付的是一份 Agent Opportunity Assessment（AI 机会评估记录）。这不是因为工程实现不重要，而是因为在还没有决定解决什么问题之前，先写代码只会让最初的假设更难被质疑。

本实验会继续使用前文的新能源汽车维修场景。如果你更熟悉客服、运维、金融数据或软件研发，也可以换成自己的业务，但请始终选定一个具体流程，而不是写“提升效率”这样无法检验的大目标。

先明确：你正在为谁解决什么问题？

假设维修技师说：“这辆车充电速度突然变慢。我需要知道先查什么，哪些证据支持这个判断，以及下一步该找谁或查哪个系统。”

不要马上把这句话翻译成“创建一个维修 Agent”。先把它翻译成业务结果：技师希望更快地定位问题，避免漏掉重要证据，并且不希望系统在证据不足时给出看似确定的结论。

请在记录里写清楚：谁会使用这个结果、谁有权作出最终维修判断、现有流程哪里耗时或容易出错，以及什么事情不属于这次实验的范围。不要为了让项目显得重要而预先承诺节省比例；目前你还没有测量这些数据。

第一步：还原现有流程，而不是画一张 Agent 图

先把你已经了解的工作过程列出来。新能源汽车维修的示例可以写成：读取车辆信息、读取故障码、查看电池诊断、查历史维修记录、检索维修手册、综合分析、查询零件库存、形成维修建议。

然后补上每一步真正影响工程设计的信息。下面这张表不是要求你画出完整企业架构，而是帮助你看清：哪些步骤已经有确定的系统负责，哪些步骤需要理解非结构化信息，哪里存在不确定判断，哪里可能影响真实业务。

流程步骤 输入与数据来源 当前如何完成 不确定性来自哪里 是否有副作用 失败时谁处理
读取故障码 车辆诊断接口 调用现有 API 通常较低 只读 维修系统/技师
查找维修依据 手册、历史案例 关键词搜索或人工查阅 术语差异、证据相关性 只读 技师复核
综合判断可能原因 诊断结果、维修记录、手册 由技师综合分析 多来源证据是否吻合 可能影响后续操作 由有资质人员确认
查询零件库存 零件库存 API 精确查询 通常较低 只读 仓储或维修系统

这张表应当随着你对业务的了解而变化。如果你不知道某个环节的真实做法，就把它标为“待确认”，不要用想象出来的流程填满空白。机会评估的价值之一，正是把未知事项暴露出来。

第二步：寻找机会，也刻意寻找不该使用 Agent 的地方

现在回到前文的概念。你已经知道 LLM、RAG、Tool、Workflow、Agent 和 Multi-Agent 并不是一组从低级到高级的装备。它们解决的是不同类型的问题。

对同一业务流程，至少找出三类性质不同的机会。维修场景可以提供一个起点：

候选机会 主要困难 可以先考虑的方案 还需要验证什么
解释某个故障码 技术语言理解与知识查找 RAG + LLM 检索证据是否正确，回答有没有超出证据
调查充电变慢的原因 多来源证据综合，下一步查询可能因结果而变 受约束的 Agent + Tools + RAG 动态调查是否比固定流程更有收益，是否能明确表达证据不足
查询维修方案需要的零件及库存 请求字段明确，系统已有精确接口 传统 API / Workflow 现有接口是否已满足需求，是否有必要加入模型

第三类机会很重要：它提醒你，正确的工程结论可能是“不使用 Agent”。你还可以再找一个高风险动作，例如改变车辆配置、确认保修承诺或触发采购，明确哪些操作不应由模型单独决定。

请把至少三个机会写入自己的记录，并说明每个机会的主要不确定性来自哪里。不要只写“这个适合 AI”，要写出为什么规则、普通 LLM 调用、RAG、固定 Workflow 或 Agent 中的某一类方案有可能更适合。

第三步：比较方案，而不是直接选中最复杂的方案

选出其中一个值得继续研究的机会，再比较下列候选方案：

方案 何时优先考虑 主要代价或风险 当前证据缺口
传统规则/API 输入输出明确，规则可枚举 对开放文本与未知情况适应性有限 规则是否覆盖主要案例
LLM Application 需要语言理解、分类、抽取或解释，但流程固定 输出存在概率性，需校验和评估 结构化输出与边界案例表现
RAG Workflow 回答必须依据可检索的知识，流程可预先规定 检索错误或证据不相关会传导到答案 Recall、版本过滤与证据支持
固定 Workflow 步骤已知，部分步骤由 AI 帮助完成 对流程外情况需要明确的异常路径 流程是否覆盖真实分支
Single Agent 下一步行动需要依据运行中观察到的结果调整 路径、成本和失败方式更难预测 动态决策是否产生可测收益
Multi-Agent 存在可证明的专业能力、上下文、权限或并行边界 协调、通信、成本和故障传播增加 拆分带来的收益是否超过额外开销

这里不要求你实现六种架构。你要做的是解释选择：为什么当前优先验证某一种方案？哪一种更简单的方案是有效的对照？为什么暂时不选择其余方案？

如果你无法说明 Agent 相对于固定 Workflow 的具体收益，就不要把“Agent 更先进”作为选择理由。先选择最简单、足以验证假设的基线，并把更复杂的方案留作需要证据支持的候选项。

第四步：在实现前写下怎样判断成功

前文已经讨论过，AI 系统不能只凭一次 Demo 判断效果。现在把这个认识用回你的业务问题。

例如，“帮助技师排查充电变慢”至少可能包含几种不同的成功标准：是否找到相关证据、是否遗漏关键风险、是否把证据与推断区分开、在信息不足时能否停下来，以及所需的模型调用和人工复核成本是否可以接受。

把你准备如何验证写清楚。案例不必现在就构成大规模的正式基准集，但至少要有正常案例、信息不足或相互矛盾的案例，以及可能导致高风险误判的案例。每一类案例都要说明什么结果可接受、什么结果不可接受。

评价问题 需要事先定义的内容
任务是否完成？ 可观察的成功条件，而不是“答案看起来不错”
依据是否可靠？ 必须出现的证据，以及哪些结论不能由现有证据支持
信息不足怎么办？ 允许澄清、拒答或转交人工的条件
系统带来什么代价？ 模型/工具调用、延迟、成本和人工介入等需要记录的指标
什么情况应该停止？ 触发人工复核、拒绝执行或暂缓上线的条件

本 Part 只要求你定义初始评估计划，并不要求此刻证明方案已经达到上线标准。到了 Part 6，你会学习如何把任务和案例组织成可复现的 Evaluation Harness，并通过统一指标比较版本或架构。

第五步：划定行动和风险边界

现在问最后一组问题：系统只是读取车辆信息和维修手册，还是会创建工单、申请零件、改变业务记录？如果它判断错了，后果是什么？谁有权批准高风险动作？

把动作分成至少两类：

  • 只读调查： 获取信息、检索知识、整理证据。这些动作也需要访问控制，但通常不会直接改变业务状态。
  • 有副作用的动作： 写入工单、修改记录、发起采购或改变配置。它们需要明确授权与目标边界，不能因为模型请求调用工具就自动执行。

如果真实目标、权限或失败处理方式尚不明确，就把它们写成上线前置条件。不要为了让方案“完整”而在本次机会评估里连接真实业务系统。本实验不调用 Provider，也不执行任何外部业务操作。

怎样判断这份实验是否完成？

完成的标准不是你是否选了 Agent，而是别人能否读完记录后看清你的推理依据：

  • 业务目标与当前流程具体到可讨论的程度；未知事实没有被当成已知事实；
  • 至少比较三类性质不同的机会，并明确一个不适合 Agent 的机会；
  • 架构选择包含一个合理的简单基线，并说明为什么增加自治或多 Agent 协作值得或不值得；
  • 评估计划写出了可观察的成功条件、失败条件与停止条件；
  • 写操作、人工决策和外部验证边界明确；
  • 结论与证据相匹配，没有把假设写成已验证收益。

做到这里，你就完成了 Part 0 的实验。它没有模型调用，也没有新增服务，但会决定后续实验究竟是在验证一个真实问题，还是只是在为技术寻找用武之地。

把评估结论带回业务现场

假设老板对你说：“今年公司的重点就是 Agent。你们团队找个场景先做起来。”

你不需要重新设计一份方案。把刚才的 Agent Opportunity Assessment 拿出来，用它回答五件事：我们究竟要改善哪个业务结果；问题中真正的不确定性在哪里；为什么当前优先选择这个最简单的基线；要用哪些案例判断它是否有效；哪些动作需要人工授权或应当被禁止。

如果你的记录还不能回答这些问题，就回到记录中补上缺失的证据，而不是把“做 Agent”当作已经完成的问题定义。你可以尝试用下面这句话向业务方解释你的决定：“我建议先用 ______ 作为基线，验证 ______ 这项业务假设。只有当案例证明固定流程无法妥善处理 ______，并且动态决策带来可衡量的收益时，我们才升级为 Agent。涉及 ______ 的写操作在本次验证中仍保持关闭。”

这不是一份额外的作业，而是把刚才的实验产物带回真实的工程沟通中。你应该能指出每个空格的依据，以及哪些地方仍然只是待验证的假设。

本 Part 小结

如果你认真读完这一部分，你现在不应该只是知道几个名词：

  • LLM
  • RAG
  • Tool
  • Workflow
  • Agent
  • Multi-Agent

真正应该发生的是一种思维变化。

以前面对需求，你可能习惯这样想：

需求
 ↓
设计 API
 ↓
设计数据库
 ↓
写代码
 ↓
测试

现在，你应该开始多问几件事情：

这个问题是什么？

问题的不确定性来自哪里？

哪些地方需要 AI？

哪些地方不需要 AI？

需要知识还是需要行动？

流程能不能提前定义？

下一步是否真的需要动态决策？

Agent 的自治边界应该在哪里？

如何证明这个系统有效？

这几句话，看起来不像“Agent 技术”。

但它们实际上构成了：

AI Application Engineering 的第一性原理。
