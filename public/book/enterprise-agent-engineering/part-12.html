Part 12｜Agent Application Architecture：把工程能力迁移到陌生领域

前面各部分建立的不是一套必须照搬的架构，而是一组可以迁移的工程判断：先定义问题与评估，再选择控制权边界，明确 Context、Tool、State、证据和权限，最后用轨迹与回归验证系统行为。

本 Part 不再引入新的 Agent Pattern，而是把这些判断放进一个陌生业务。给你的材料不会直接告诉你要用哪种架构；你需要自己找出业务流程、数据来源、决策点和风险，并证明选出的方案足以解决问题。

到这里，最容易出现的错觉是：“我是不是已经学会 Agent 了？”

真正的答案，要到现在才能验证。

因为现实中的 AI 工程师，很少会拿到一道题目：“请使用 RAG + Agent + Tool Calling 实现一个客户问答系统。”

这种题目适合课程，不适合工作。

工作中的任务更像：“我们现在做的是半导体制造，最近良率下降，工艺工程师希望做一个智能异常调查助手。你先看看有没有必要做，应该怎么做。现有系统里有 MES、设备数据、工艺知识库、历史批次数据，也有几个内部 API。先给方案，再做一个能跑的版本。”

注意这里没有告诉你：

应该用 RAG。

没有告诉你：

应该用 Agent。

更没有告诉你：

应该拆成三个 Agent。

甚至没有保证：

这个问题真的值得用 AI。

你必须自己从一个陌生行业里，把真正的问题找出来。

这才是 AI Application Engineer 与“会调用大模型 API 的开发者”之间最重要的一道分水岭。

12.1 当你进入一个完全陌生的行业

我们现在假设，你原来是一名做金融数据平台的后端工程师。

你熟悉：

  • Python
  • FastAPI
  • PostgreSQL
  • Redis
  • 消息队列
  • 数据采集
  • API
  • 日志
  • 监控
  • 测试

但是你从来没有进入过半导体制造行业。

第一天，业务方给你发来一份需求：

“建设智能良率异常调查助手。”

你打开需求文档。

里面出现大量你并不熟悉的词：

  • Lot
  • Wafer
  • Recipe
  • Equipment
  • Chamber
  • Yield
  • Defect
  • Process Step
  • SPC
  • Alarm
  • Root Cause
  • Preventive Action

这时候最危险的事情，不是你“不懂半导体”。

真正危险的是：

你因为不懂业务，而过早开始设计 Agent。

你可能会马上想到：“这个系统知识很多，所以做 RAG。”

然后继续：“调查过程比较复杂，所以做 Agent。”

再然后：“不同角色可以拆成多 Agent。”

最终架构图可能非常漂亮：

                Supervisor Agent
                 /      |      \
          Search Agent  SQL Agent  Report Agent
               |           |          |
              RAG         DB       LLM

问题是：

你甚至还不知道这个业务问题是什么。

这和拿着锤子找钉子没有区别。

所以进入陌生领域以后，第一个动作不是：

选择模型

也不是：

选择 Agent Framework

而是：

理解业务

更准确地说，是建立一个最小但足够工作的领域模型。

你必须先知道：

你必须先知道：谁，在什么情况下，因为什么问题，需要做什么决策？

这句话看起来简单，实际上包含了 AI 应用架构设计所需要的大部分信息。

12.2 第一件事：别急着懂整个行业

进入一个陌生行业时，一个常见错误是试图“先把行业学懂”。

这通常会陷入无限学习。

比如半导体制造，你完全可以花大量时间去学习晶圆制造工艺、光刻、刻蚀、沉积、清洗、检测……

然后一个月以后，你还是不知道应该做什么系统。

AI 工程师真正需要的不是：

成为这个行业的专家。

而是：

足够理解一个具体业务流程，使自己能够正确设计软件系统。

这两者差别很大。

假设业务给了你下面这段描述：

某生产线每天生产大量晶圆批次。每个 Lot 会经过多个 Process Step，每个 Step 在特定 Equipment 上执行。系统会记录设备报警、工艺参数、检测结果和最终 Yield。
当 Yield 异常下降时，工艺工程师需要查看该 Lot 的生产路径，再与历史正常 Lot 比较，寻找异常设备、异常参数或异常缺陷模式，然后查阅工艺规范和历史调查记录，最后形成一份 RCA（Root Cause Analysis）报告。

你现在还不需要知道半导体具体是怎么制造出来的。

但是你已经可以开始建立系统模型。

例如：

Lot
 │
 ├── Process Steps
 │       │
 │       ├── Equipment
 │       ├── Recipe
 │       └── Parameters
 │
 ├── Inspection Results
 │
 ├── Alarm Records
 │
 └── Yield

然后你再问：“什么叫异常？”

业务方回答：“通常是 Yield 比产品基线低超过某个阈值，或者某类 defect 在短时间内显著增加。”

突然之间，一个模糊的行业问题开始变成了软件问题。

你开始看到：

异常检测
   ↓
数据查询
   ↓
历史比较
   ↓
知识查找
   ↓
原因分析
   ↓
调查报告

这才是 AI 工程开始真正介入的地方。

12.3 先画业务流程，而不是架构图

现在我们继续假设业务方给了你一个具体场景。

场景：某 Lot 良率异常

工程师输入：

Lot ID: LOT-20261008-017

系统发现：

Yield = 82.4%
Product Baseline = 94.1%

业务人员希望知道：

业务人员希望知道：为什么这个 Lot 的 Yield 掉下来了？

如果你是一个普通的软件工程师，第一反应通常是：“查数据库。”

没错。

但是问题不会止于 SQL。

因为真正的调查过程可能是这样的：

发现异常
   ↓
查询 Lot 基本信息
   ↓
查看经过了哪些 Process Step
   ↓
查看各 Step 使用了哪些 Equipment
   ↓
查看报警
   ↓
查看关键工艺参数
   ↓
寻找异常参数
   ↓
与历史正常 Lot 比较
   ↓
查找相关工艺 SOP
   ↓
查找历史 RCA
   ↓
形成可能原因
   ↓
给出证据
   ↓
形成调查报告

现在，请停一下。

你会发现这里实际上混合了很多完全不同性质的事情。

例如：

“这个 Lot 的 Yield 是多少？”

这是典型数据库查询。

不需要 LLM。

“最近 30 天同产品的平均 Yield 是多少？”

还是数据库查询。

不需要 Agent。

“这个 Lot 是否超过既定异常阈值？”

这是确定性规则。

更不应该交给 Agent 判断。

“这个 Lot 使用过哪些设备？”

还是数据查询。

“根据这批数据，哪些因素最值得调查？”

这里开始有 AI 的空间了。

“这个报警与 Yield 下降有没有可能存在关系？”

可能需要模型辅助分析。

“SOP 里对这个异常模式有什么描述？”

这是 RAG。

“结合历史 RCA，这次异常最值得检查哪几个方向？”

可能需要 RAG + LLM，甚至 Agent。

“请生成调查报告，并把证据附上。”

LLM 很适合。

于是，原本一句：“做一个智能异常调查 Agent。”

现在已经被拆成了不同性质的任务。

这就是问题拆解先于架构选择。

12.4 你要学会画的，不是系统架构，而是“决策地图”

到现在，你应该已经习惯这样看问题：

业务动作
   ↓
需要什么信息？
   ↓
信息在哪里？
   ↓
如何获取？
   ↓
是否需要判断？
   ↓
判断是否确定性？
   ↓
如果不是，模型能否辅助？
   ↓
模型是否需要工具？
   ↓
是否需要自主决定下一步？

把这个思路放到我们的案例里，就会得到一张非常重要的地图。

任务 信息来源 性质 适合的方式
判断 Yield 是否低于阈值 DB 确定性 普通代码
查询 Lot 信息 MES API 确定性 Tool / Service
查询设备报警 Equipment API 确定性 Tool
获取历史正常 Lot DB/API 检索 Tool
查 SOP Knowledge Base 非结构化知识 RAG
查历史 RCA Knowledge Base 非结构化知识 RAG
根据多个证据提出可能原因 多源信息 概率性推理 LLM
决定下一步调查方向 动态 Agentic Agent
生成调查报告 非结构化生成 LLM LLM / Workflow
自动修改设备参数 高风险 确定性+审批 禁止直接交给 Agent

注意最后一行。

这是本章刻意保留的一个陷阱。

业务方可能会非常兴奋：“既然 Agent 已经找到原因了，那是不是可以让它直接修改设备参数？”

你的回答应该是：

不应该。

至少在当前系统里不应该。

原因不是“AI 还不够智能”。

而是：

这是一个高风险、强约束、可产生真实物理后果的操作。

这意味着即使整个调查分析过程使用了 Agent，也不代表最后的执行动作应该由 Agent 自主完成。

可能合理的结构是：

Agent
  ↓
提出建议
  ↓
解释理由
  ↓
给出证据
  ↓
人工审批
  ↓
确定性控制系统
  ↓
执行

这再次验证了 Part 0 的核心观点：

AI 能参与多少，不由模型能力决定，而由业务风险决定。

12.5 架构选择：现在才轮到 Agent 出场

到了这一步，你才应该开始比较架构。

假设我们要求系统完成：“调查一个异常 Lot，并给出带证据的原因分析报告。”

你至少可以设计五种方案。

方案 A：纯传统软件

流程完全写死：

查询 Lot
→ 查询 Yield
→ 查询设备
→ 查询报警
→ 查询参数
→ 查询历史
→ 输出报告

优点非常明显：

  • 稳定
  • 可控
  • 易测试
  • 成本低
  • 容易审计

缺点也明显：

如果调查逻辑非常固定，它很好。

但一旦调查方向会随着发现动态变化，它就会开始变得越来越复杂。

例如：

例如：如果发现设备报警 A，则查询参数 B； 如果参数 B 异常，则继续查历史 Lot C； 如果历史 Lot 也异常，则查 SOP D……

最终可能出现一个巨大的规则树。

方案 B：固定 Workflow + LLM

可以把流程固定下来：

1. 查 Lot
2. 查生产路径
3. 查报警
4. 查参数
5. RAG 查知识
6. LLM 综合分析
7. 生成报告

这个方案其实已经非常强。

而且它可能是最终生产系统的首选。

因为工程师可以很清楚地知道：

每一个调查任务都会经历哪些步骤。

这意味着：

可观测
可预测
可回放
可测试

如果业务流程本身比较固定，那么这个方案可能比 Agent 更好。

方案 C：Single Agent

Agent 拿到任务：

调查 LOT-20261008-017

然后自己决定：

query_lot
↓
query_process_history
↓
query_equipment_alarm
↓
search_sop
↓
query_similar_lots
↓
search_historical_rca
↓
generate_report

它可以根据观察结果调整下一步。

比如：“发现设备 E-17 在该 Lot 上有 3 次报警，我应该进一步检查这个设备最近 20 个相同产品 Lot 的表现。”

这时候 Agent 就比固定 Workflow 灵活。

方案 D：Multi-Agent

还可以拆成：

Investigation Supervisor
       │
       ├── Data Analyst
       ├── Equipment Analyst
       ├── Knowledge Researcher
       └── Report Writer

听起来很漂亮。

但是现在你应该已经学会保持怀疑。

为什么一定要拆？

如果所有 Agent：

  • 使用相同的数据
  • 使用相同的权限
  • 使用相同的模型
  • 使用相同的上下文
  • 没有明显并行机会

那么 Multi-Agent 很可能只是增加：

调用次数
通信
状态
失败点
调试难度
成本

却没有增加真正的能力。

所以：

Multi-Agent 不能因为“角色看起来合理”就成立。

必须存在真实的工程边界。

12.6 现在做一个真正的架构 Shootout

你现在的任务不是直接实现一个 Agent。

而是做一次架构实验。

对同一个任务，分别实现：

Traditional
Workflow + LLM
RAG Workflow
Single Agent
Multi-Agent

然后使用前面 Part 6 建立的 Evaluation Harness 统一评估。

例如准备 50 个历史调查案例。

每个案例包含：

{
  "lot_id": "LOT-...",
  "expected_findings": [],
  "required_evidence": [],
  "acceptable_conclusions": [],
  "forbidden_actions": []
}

然后测：

Task Success
Final Answer Quality
Evidence Accuracy
Tool Accuracy
Retrieval Quality
Latency
Token Usage
Cost
Failure Rate
Human Intervention

这时候你可能得到非常有意思的结果。

例如：

                     Success   Cost   Latency
Traditional            91%      低      低
Workflow + LLM         93%      中      中
RAG Workflow           95%      中      中
Single Agent           96%      高      高
Multi-Agent            96%      很高    很高

然后你会发现一个现实问题：

Multi-Agent 并没有比 Single Agent 更准确。

如果这是真的，那么你为什么要采用 Multi-Agent？

答案不能是：“因为 Multi-Agent 更先进。”

应该是：“因为它解决了某个 Single Agent 无法很好解决的问题。”

例如后续你发现：

  • 设备分析和文档检索完全可以并行；
  • 两类任务需要不同权限；
  • 两类任务需要不同上下文；
  • 两种分析需要完全不同的专业 Tool；
  • Supervisor 只负责协调。

这时 Multi-Agent 才开始有工程意义。

12.7 真正的跨领域迁移，不是“换一个 Prompt”

到了这里，很多人仍然会低估这个能力。

他们可能觉得：“我只是把之前做客户服务 Agent 的代码，换成制造业 Prompt。”

这不是领域迁移。

真正的迁移发生在更高一层。

你需要把过去学到的能力抽象成：

领域
 ↓
业务流程
 ↓
参与者
 ↓
数据
 ↓
决策
 ↓
工具
 ↓
知识
 ↓
风险
 ↓
AI机会
 ↓
系统架构
 ↓
评估
 ↓
生产化

例如你原来做金融数据。

过去可能是：

金融产品
↓
数据接口
↓
净值
↓
异常检测
↓
人工核验
↓
报告

进入制造业以后变成：

生产批次
↓
MES
↓
设备 / 工艺 / 检测数据
↓
异常检测
↓
工程师调查
↓
RCA报告

表面上完全不同。

但从 AI 工程角度，它们其实拥有非常相似的结构：

结构化数据
+
非结构化知识
+
多个内部工具
+
复杂调查过程
+
最终需要人类判断

这就是工程能力真正可以迁移的地方。

12.8 开始真正动手：先定义系统边界

现在，我们终于可以开始实现。

假设你拿到一个已经存在的后端仓库：

factory-ai-assistant/
├── app/
│   ├── api/
│   ├── models/
│   ├── services/
│   ├── repositories/

12.10 用“证据链”而不是“漂亮答案”设计系统

在制造异常调查场景里，一句：“可能是设备 E-17 导致良率下降。”

几乎没有价值。

工程师真正需要的是：

工程师真正需要的是：为什么？

所以系统输出不能只有最终结论。

应该类似：

Investigation Result

Conclusion
-----------
Equipment E-17 is the primary candidate.

Evidence
--------
1. LOT-20261008-017 used E-17 during Process Step 42.
2. E-17 generated Alarm A-204 three times during the lot run.
3. Yield loss is concentrated in the inspection category X.
4. Among the previous 20 comparable lots,
   similar behavior occurred in 3 lots using E-17.
5. Historical RCA #RCA-182 describes a similar pattern.

Confidence
----------
Medium

Recommended Next Checks
-----------------------
1. Verify chamber pressure calibration.
2. Compare Recipe version used by E-17.
3. Review maintenance records.

Source References
-----------------
...

这里有一个非常重要的变化。

我们不再让 Agent 输出：

Answer

而要求它输出：

+
Evidence
+
Uncertainty
+
Next Action
+

这就是从聊天机器人思维走向工程系统思维。

12.11 你还必须允许 Agent 说：“证据不足”

这是一个很重要的毕业能力。

很多 AI 系统失败，并不是因为模型不会回答。

而是因为系统不允许它不回答。

例如：

查询结果：
没有发现异常设备
没有匹配历史 RCA
知识库没有相关 SOP

模型仍然可能生成：“综合分析表明，设备问题可能是主要原因……”

这时候真正需要的，不是再加一个 Prompt：“请不要幻觉。”

而是从系统设计上允许：

{
  "status": "insufficient_evidence",
  "conclusion": null,
  "evidence": [],
  "next_steps": []
}

换句话说：

“不知道”也是一种合法的系统状态。

这也是为什么 Evaluation、Policy、Structured Output、State、Runtime 最终必须结合起来。

诱导模型越权

12.13 生产化之前，再问一次：到底需要 Agent 吗？

这是整个课程故意设计成的最后一道回头检查。

经过几轮实现以后，你可能已经拥有一个很漂亮的 Agent。

它可以：

自己查数据
自己搜知识
自己做分析
自己规划调查路线
自己生成报告

然后你重新审视业务流程。

发现实际生产环境里：

发现实际生产环境里 90% 的调查都遵循固定路径。

甚至工程师真正使用的流程是：

查看 Lot
→ 查看报警
→ 查看历史对比
→ 查 SOP
→ 输出报告

只有最后 10% 的复杂案例需要动态调查。

那么最好的架构可能不是：

所有任务 → Agent

而是：

                Investigation System
                       │
          ┌────────────┴────────────┐
          │                         │
       Standard                 Complex
       Cases                    Cases
          │                         │
      Workflow                   Agent
          │                         │
          └────────────┬────────────┘
                       ▼
                    Report

这可能比“全 Agent 化”更优秀。

这就是你在 Part 0 学到的原则，到了 Part 12 又重新回来：

不要因为你已经学会 Agent，就强迫所有问题使用 Agent。

成熟的 AI 工程师，应该越来越少使用 Agent，而不是越来越多。

因为你越来越知道：

Agent 的自主性是一种昂贵能力。

只有在它真的创造价值时，才值得付出这个成本。

12.14 最后一轮 Production Review

12.16 现在轮到你：从零完成一个陌生领域

到这里，Part 12 不应该再给你一份“标准答案”。

真正的毕业项目，应该把一部分信息故意留白。

你可以使用下面的模拟任务作为最终 Capstone。

Capstone：冷链运输异常调查系统——配套实验的正式任务

前文使用智能制造异常 Lot 调查来讲解陌生领域的拆解方法；那是贯穿正文的示例。配套仓库为了检验你能否迁移工程判断，刻意改用了另一个领域：冷链运输异常调查。这不是正文与代码的疏漏，而是 Capstone 的迁移要求。请不要把智能制造示例中的字段、业务规则或预设架构直接当成仓库任务的事实。

从 labs/lab12_capstone/TASK.md 开始，先阅读 labs/lab12_capstone/domain_pack/ 的全部材料。学生实现应从 labs/lab12_capstone/starter_repo/ 起步；作者参考基线只用于建立比较，不是让你复制答案。仓库中的离线参考路径可以用于理解基线：

python -m reference.lab12_workflow_first.src.run --mode fake
python -m pytest labs/lab12_capstone/tests reference/lab12_workflow_first/tests

然后完成下面五个阶段。

阶段一：理解业务

提交 business-process.md、problem-decomposition.md 和 risk-register.md。画出参与者、当前流程、信息来源、决策点和未解决问题；将确定性规则、知识检索、模型辅助推理和必须由人决定的事项分开。不要假设数据完整或彼此一致。

阶段二：作出架构决策

提交 ADR-001.md，至少比较规则系统、Workflow + RAG + LLM、只读 Single Agent 和 Multi-Agent。解释每种架构解决什么问题、代价是什么、可能怎样失败，以及增加自治或协作是否值得。这里不设定标准答案，要求你的选择与证据相匹配。

阶段三：实现可审查的只读系统

以 starter_repo/ 为起点，系统需要结合 shipment、温度读数、配送、告警、SOP 和历史事件证据；输出结构化结果与轨迹；对重要判断引用提供的证据 ID；明确不确定性和下一步检查；遇到无效输出或证据不足时安全降级。运行结果必须是建议性的只读分析，不得释放、隔离、修改或销毁货物。模型输出不能覆盖独立的确定性安全状态。

阶段四：评估而不是展示 Demo

使用 domain_pack/evaluation_dataset.json 原样作为离线主线基线。可以增加独立版本的挑战集，但不得静默删改或重写原有案例。离线主线至少评价运营状态正确性、问题类型、所需证据覆盖、引用依据是否真实存在，以及无依据的确定性表达。用同一数据集比较至少两个架构或有意义的版本，并把工程契约测试与模型质量结论分开报告。

阶段五：完成生产审查

提交 production-review.md，讨论 timeout、retry、幂等性（如适用）、访问控制、审计、Prompt Injection、预算、证据来源、人工复核和回归评估。尤其要说明为什么在这个场景里，一个只读的建议系统可能比完全自治的 Agent 更合适。

最终提交：

deliverables/
├── business-process.md
├── problem-decomposition.md
├── ADR-001.md
├── risk-register.md
├── evaluation-report.md
└── production-review.md

本章的验收不是“Demo 能返回一个答案”。它要求确定性安全状态不受模型文本覆盖；所有材料性引用都来自给定证据集合；无效结构化输出能够退化为不确定结果并提示下一步；轨迹记录证据构造、安全判定、最终结果和终止原因；八个基线案例保持不变。通过这些离线合同测试仍不代表真实 Provider 质量、业务流程适配或生产安全已经获得证明。

可选真实模型实验：在参考基线中观察当前 Provider

本章学生主线仍从 starter_repo/ 实现与离线合同测试开始。只有在明确需要测量当前模型表现，且已经确认 Provider、模型价格、数据处理和输出留存条件时，才运行作者的只读 Workflow-first 参考实现。它是比较基线，不是要求学生复制的标准架构。

python -m reference.lab12_workflow_first.src.run --mode real

真实模型输出需要逐案审查；它不证明真实业务适配、生产隔离或安全发布已经完成。

12.20 全书最后的一句话

如果你在学习这本书之前，面对一个新需求时通常会问：“这里应该用哪个 Agent Framework？”

你应该先问：

普通后端服务。

有时候是：

Workflow。

有时候是：

LLM。

有时候是：

RAG。

有时候是：

Single Agent。

有时候是：

Multi-Agent。

还有很多时候：

根本不需要 AI。

真正成熟的 AI 工程师，不是那个最喜欢 Agent 的人。

而是那个能够在复杂现实里准确判断：

哪里应该让 AI 做决定，哪里必须让程序做决定；哪里应该增加自主性，哪里应该刻意限制自主性。

“使用 AI”

到：

“工程化 AI”

的那条线。

而这，才是本书真正意义上的终点。
