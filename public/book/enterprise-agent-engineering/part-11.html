Part 11｜Agent Evolution：让 Agent 不只是上线，而是持续变好

一个传统软件系统发布以后，通常是“代码变了”。
一个 Agent 发布以后，可能是模型变了、Prompt 变了、Context 变了、知识变了、Tool 变了、用户变了，甚至任务本身也变了。

无论系统采用 Single Agent、Multi-Agent 还是 Coding Agent，交付后都不会停止变化。模型或 Provider 可能升级，Prompt、工具、知识源、数据分布和用户行为也会变化。单次上线前测试不能自动覆盖这些变化；本 Part 关注如何把变化转化成明确假设，并通过有归因的对照和回归来判断是否值得发布。

这个系统上线以后怎么办？

假设你今天发布了：

Agent v1

运行一个月以后，你发现：

用户越来越多
业务规则发生变化
知识库更新
工具接口升级
模型能力变化

同时：

生产失败案例

也不断积累。

如果你只是不断：“改 Prompt。”

这个 Agent 很可能最终变成一堆没人敢动的配置。

所以这一部分，我们要解决的是：

如何让 Agent 形成持续改进的工程闭环。

11.1 为什么 Agent 上线以后反而更需要工程？

传统项目经常有一种感觉：

开发
 ↓
测试
 ↓
上线
 ↓
完成

当然真实软件也会持续迭代。

但 Agent 有一个非常特殊的地方：

它面对的是变化中的概率性环境。

例如你今天的 Agent：

Task Success = 95%

三个月以后：

Task Success = 90%

代码可能完全没变。

为什么？

可能是：

用户问题变了
知识库变了
Tool API 变了
业务规则变了
模型 Provider 变了
模型版本变了

所以：

Agent 的行为不是只由代码版本决定。

这意味着：

Agent 需要一种比传统代码版本管理更完整的演进机制。

甚至：模型本身完全不变。

11.48 Part 11 最重要的几个认识

第一

Agent 的行为由多个版本化组件共同决定。

第二

生产失败应该进入下一轮 Evaluation。

第三

Failure Taxonomy 比零散修 Bug 更有价值。

第四

改 Agent 应该从 Hypothesis 出发，而不是从“感觉”出发。

第五

Prompt、Tool、Skill、Memory、Knowledge 都可以演进。

第六

Agent Evolution 不等于重新训练模型。

第七

每一个改动都应该经过 Evaluation 和 Regression。

第八

Agent 的最终目标不是“越来越复杂”，而是：

越来越适合真实任务。
