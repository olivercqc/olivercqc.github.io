Part 3｜Tools & Agent Harness：让模型开始与真实世界交互

一个模型如果只能说话，它更像一个顾问。
一个模型如果能够调用工具、观察结果，并决定下一步做什么，它才开始真正成为一个 Agent。

Part 1 让模型调用具备了软件依赖应有的边界，Part 2 则解释了每次决策的输入应如何构造。即便输入合适，模型也不能直接改变业务世界：它最多提出下一步行动，真正执行仍要经过应用程序的检查。

本 Part 要把“建议”与“执行”之间的边界做成一个可观察、可测试的闭环。

3.1 从“回答问题”到“做事情”

先看两个请求。

第一个：“解释一下为什么我的订单还没有发货。”

模型可以直接回答。

它不需要访问任何真实系统，只需要根据给它的上下文生成文字。

所以：

User
 ↓
Context
 ↓
LLM
 ↓
Answer

这是一个典型的 LLM Application。

现在换一个请求：“帮我查一下订单 10001 现在到哪里了。”

模型自己知道订单号，但它并不知道订单系统当前的数据。

它必须访问：

Order Service

这时候事情发生了变化。

模型需要表达：“我想调用查询订单这个能力。”

例如：

{
  "name": "query_order",
  "arguments": {
    "order_id": 10001
  }
}

应用程序收到这个请求以后：

LLM
 ↓
Tool Call
 ↓
Backend Tool
 ↓
Order Service
 ↓
Tool Result

然后把结果再交给模型。

最终模型才能告诉用户：“订单 10001 已于昨天出库，目前正在运输中。”

这一刻，一个重要变化出现了。

模型不再只是：

生成内容。

它开始：

参与系统执行。

3.2 Tool 到底是什么？

如果你是一名后端工程师，可以用一个非常熟悉的概念理解 Tool：

Tool 本质上就是一个供 AI 使用的接口。

你以前设计 API：

GET /orders/{order_id}

现在只是给 Agent 一个可以使用的能力：

query_order(order_id: int)

从这个角度看，Tool 和 API 有很多相似之处：

API
├── Name
├── Input
├── Output
├── Permission
├── Error
└── Side Effect

Tool 同样需要这些东西。

但是 Tool 又多了一层非常关键的东西：

模型需要“理解”这个工具是什么。

传统 API 的消费者通常是：

  • 前端
  • 后端
  • 其他机器程序

它们不需要通过自然语言理解 API。

Agent 不一样。

模型必须知道：

  • 什么时候应该使用这个 Tool？
  • 这个 Tool 能解决什么问题？
  • 参数应该怎么填写？

因此 Tool 的描述质量会直接影响 Agent 的行为。

3.3 第一个 Tool

假设我们有：

def query_order(order_id: int) -> dict:
    ...

从人的角度看，这已经很清楚了。

但模型看到的接口，通常还需要更明确的 Schema。

例如：

{
  "name": "query_order",
  "description": "根据订单 ID 查询订单当前状态、商品信息和物流状态。",
  "input_schema": {
    "type": "object",
    "properties": {
      "order_id": {
        "type": "integer",
        "description": "要查询的订单 ID"
      }
    },
    "required": ["order_id"]
  }
}

这里实际上存在三种信息：

Tool Name

叫什么？

Tool Description

能做什么？

Input Schema

应该怎么调用？

这三个信息共同决定了模型能否正确使用工具。

3.4 为什么 Tool Description 很重要？

假设你的系统有两个工具：

query_order()
query_customer()

用户说：“帮我看看张三那个订单。”

模型必须知道：

模型必须知道：先查订单还是先查客户？

如果 Tool Description 写得非常模糊：

query_order:
查询数据。

query_customer:
查询数据。

模型很容易选错。

如果描述清楚：

query_order:
根据已知订单 ID 查询订单状态、商品和物流信息。
不要用于搜索未知订单。

query_customer:
根据客户姓名、手机号等身份信息查询客户记录。
不用于查询订单状态。

模型就拥有了更明确的能力边界。

因此：

Tool Description 不是注释。

它是：

模型进行工具选择时的重要输入。

3.5 Tool Granularity：工具到底应该多大？

这是 Agent Engineering 中一个非常值得认真思考的问题。

假设你要给 Agent 一个“订单管理”工具。

你可以设计成：

manage_order(...)

让它传：

{
  "action": "query / update / cancel / refund",
  "order_id": "...",
  "..."
}

看起来非常灵活。

但问题也很明显。

模型必须同时决定：

  • 操作类型
  • 参数
  • 风险
  • 副作用

于是工具变得非常复杂。

另一种设计：

query_order()
update_shipping_address()
cancel_order()
request_refund()

每个工具只负责一个清晰能力。

这样模型面对的是：

我需要查询
→ query_order

我需要改地址
→ update_shipping_address

我需要取消订单
→ cancel_order

模型更容易理解。

但工具太细也有问题：

但工具太细也有问题工具数量过多。

所以 Tool Design 没有一个绝对标准。

你需要在：

Tool Granularity

和：

Tool Count

之间做平衡。

可以先记住一个非常实用的原则：

一个 Tool 最好表达一个相对清晰、容易描述、容易授权和容易验证的能力。

3.6 Tool 是“能力”，不是“魔法”

再看一个非常危险的设计：

execute_sql(sql: str)

你可能觉得这很方便。

模型只要会 SQL，就能访问数据库。

但从工程角度看，这相当于：

但从工程角度看，这相当于给了模型非常大的权限。

模型可能生成：

DROP TABLE orders;

当然，优秀模型不一定会这么做。

但工程系统不能建立在：“模型应该不会这么做。”

之上。

一个更合理的思想是：

不要给 Agent 最大权限，而应该给它完成任务所需要的最小权限。

例如：

query_order(order_id)
query_inventory(part_id)
create_service_ticket(data)

而不是：

execute_anything(...)

这其实就是我们在传统安全工程里非常熟悉的：

Least Privilege。

只是现在权限的使用者从“程序代码”扩展到了“模型驱动的程序”。

3.7 Read Tool 和 Write Tool

到这里，可以做一个非常有用的区分。

Read Tool

例如：

query_order()
query_inventory()
search_policy()
get_vehicle_status()

它们主要：

它们主要获取信息。

通常风险较低。

Write Tool

例如：

update_order()
create_ticket()
cancel_order()
issue_refund()

它们会：

它们会：改变真实世界。

因此风险更高。

Irreversible Tool

例如：

refund_money()
delete_customer_data()
shutdown_production_line()

一旦执行，可能很难恢复。

风险进一步上升。

所以在 Agent 设计中，可以形成：

Read
 ↓
Low Risk

Write
 ↓
Higher Risk

Irreversible
 ↓
High Risk

这会直接连接到我们以后学习的：

  • Authorization
  • Human Approval
  • Safety
  • Production

3.9 Agent Loop：真正的核心来了

把刚才的过程抽象一下。

    response = model(context)

    if response.tool_call:
        result = execute_tool(response.tool_call)
        context.append(result)
    else:
        break

这段代码很短。

但它实际上已经表达出了 Agent 的核心机制。

我们逐步读。

第一步：调用模型

response = model(context)

模型看到：

  • 当前任务
  • 当前状态
  • 历史信息
  • Tool 定义
  • 已有结果

然后产生一个结果。

第二步：判断结果

如果模型说：我要调用 query_order。

那么进入：

if response.tool_call:

第三步：执行 Tool

result = execute_tool(response.tool_call)

注意：

这里不是模型执行 Tool。

而是：

你的程序执行 Tool。

这是一个极其重要的边界。

模型只提出：“我想调用这个能力。”

真正执行：

由你的 Runtime / Backend 负责。

第四步：把结果重新放入 Context

context.append(result)

模型下一次调用就能看到：

模型下一次调用就能看到刚刚发生了什么。

第五步：继续

再次：

response = model(context)

模型可能决定：

模型可能决定继续查询物流。

也可能：

也可能已经足够了，可以回答用户。

于是整个过程就形成：

Decision
   ↓
Action
   ↓
Observation
   ↓
Decision
   ↓
Action
   ↓
Observation
   ↓
Final

这就是 Agent Loop。

3.10 Agent Loop 最重要的不是“循环”

很多人第一次看到 Agent Loop，会觉得：“不就是 while True 吗？”

从代码结构来说，确实如此。

但真正重要的是：

传统 Workflow：

 ↓

 ↓

Agent：

当然，这里的“决定”仍然受到：

  • Schema

等机制限制。

所以真正的 Agent 并不是：

而是：

3.12 Tool Dispatcher：不要让 Agent 直接执行 Python 函数

最初你可能写：

if tool_name == "query_order":
    return query_order(...)

工具少的时候当然可以。

但工具一多，这段代码很快失控。

所以可以建立：

Tool Registry
      ↓
Tool Dispatcher
      ↓
Tool Executor

例如：

tools = {
    "query_order": query_order,
    "query_inventory": query_inventory,
    "create_ticket": create_ticket,
}

然后：

def dispatch(tool_call):
    tool = tools.get(tool_call.name)

    if tool is None:
        raise UnknownToolError(tool_call.name)

    validate_arguments(tool_call)
    return tool(**tool_call.arguments)

这样以后可以在 Dispatcher 层统一加入：

Validation
Authorization
Logging
Timeout
Retry
Tracing
Audit

于是 Tool 执行不再是：

Model
 ↓
Function

而是：

Model
 ↓
Tool Call
 ↓
Dispatcher
 ├── Validate
 ├── Authorize
 ├── Execute
 ├── Observe
 └── Record
 ↓
Tool Result

这已经开始非常像真正的 Runtime 了。

3.13 Tool Schema Validation

假设模型产生：

{
  "tool": "query_order",
  "arguments": {
    "order_id": "abc"
  }
}

但你的函数要求：

order_id: int

此时不能直接调用。

应该：

Tool Call
 ↓
Schema Validation
 ↓
Invalid

然后决定：

  • 返回错误给模型
  • 请求修复
  • 重试
  • 终止任务

这与 Part 1 学过的 Structured Output 很类似。

事实上：

Tool Call 本身就是另一种 Structured Output。

模型不是自由生成一句：“我想查一下订单。”

而是在告诉系统：

Tool = query_order
Arguments = {"order_id": 10001}

这样程序才能可靠地执行。

3.14 Tool Error 是 Context 的一部分

假设：

query_order(10001)

结果：

OrderNotFound

你有两种方式。

第一种：

第一种：直接给用户报错。

第二种：

把这个错误作为 Agent 的观察结果。

例如：

Tool:
query_order(10001)

Result:
ORDER_NOT_FOUND

然后模型可能决定：“那我应该先搜索这个客户的订单。”

于是调用：

search_customer_orders(...)

这件事情非常重要。

因为：

Tool Error 不一定意味着整个 Agent Task 失败。

有些错误是：

有些错误是：下一步决策需要知道的信息。

这也是 Agent 与传统 API 调用模式开始产生区别的地方。

3.15 但是，不要把所有错误都交给模型

这又涉及一个重要工程边界。

假设：

数据库连接彻底断了。

你没有必要让模型思考：“是不是应该再调用数据库？”

因为：

因为：基础设施已经挂了。

再比如：

用户没有执行退款的权限。

也不是一个：“让模型想办法解决”的问题。

权限失败应该直接阻止操作。

所以可以把错误分成：

Recoverable / Informational
        ↓
可以进入 Agent Context

Hard Failure
        ↓
Runtime 处理

Security / Authorization Failure
        ↓
必须阻止

这就是为什么：

Agent Runtime 不能只是一个 while loop。

3.16 Agent State：Agent 到底记住了什么？

现在我们开始进入另一个问题。

假设 Agent 已经完成：

Step 1
查询订单

Step 2
查询物流

Step 3
查询维修记录

它现在处于：“已经发现订单本身没有问题，物流存在异常。”

这个状态必须保存。

因此 Agent 需要一个 State。

例如：

class AgentState(BaseModel):
    task_id: str
    status: str
    current_goal: str
    tool_results: list[dict]
    pending_actions: list[str]
    completed_actions: list[str]

这样：

Agent
 ↓
State
 ↓
Decision
 ↓
Tool
 ↓
State Update
 ↓
Next Decision

这和你以前设计 Workflow、State Machine 时的思路已经非常接近。

3.17 Context 与 State：在 Runtime 中分别承担什么责任？

Part 2 已经说明，Context 是面向当前决策构造的输入视图，State 则是系统管理的任务状态。进入 Runtime 后，这个区别变成了实现约束：模型看到的状态只是一次调用的快照，不能因为模型返回了不同文本，就自动把权威状态改掉。

例如，Runtime 当前记录 diagnosis_status = waiting_for_logistics，本次 Context 可以把它连同最近工具结果一起提供给模型。模型建议“调查结束”后，Runtime 仍需检查证据、权限和终止条件，再通过受控状态转换把任务更新为完成或待人工复核。

因此，Context Builder 可以读取 State，但状态更新必须走明确的应用逻辑；不能将模型生成的自然语言当作唯一状态来源。

3.18 Agent Harness：运行时究竟管理什么？

我们前面一直在说 Agent Harness。现在需要把它与 Evaluation Harness 区分开来。

Agent Harness / Runtime 负责把一次模型决策变成受约束的执行循环。常见职责包括：

  • Model Client：调用模型并处理响应格式；
  • Context Builder：按当前任务组装输入；
  • Tool Registry / Dispatcher：验证和调用获准的工具；
  • State Transition：通过应用逻辑更新权威状态；
  • Policy：检查权限、参数、目标和副作用边界；
  • Loop / Stop / Budget：限制循环、设置终止条件与预算；
  • Trace / Observability：记录此次运行发生了什么。

具体模块可以合并，也可以由框架提供；这里列的是职责，不是要求每个项目都创建同名文件。Memory、独立输出校验器和更强的安全控制可以作为外围服务或按需接入，并非每一个最小 Runtime 都必须全部内建。

User Task
   ↓
Agent Runtime / Harness
   ├── Model Client
   ├── Context Builder
   ├── Tool Dispatcher
   ├── State + Policy
   ├── Loop / Stop / Budget
   └── Trace
   ↓
Business Systems

Evaluation Harness 是另一条独立的验证路径。 它管理固定 Dataset、重复运行、Evaluator、指标汇总和报告，用于判断某个 Agent 版本是否达到要求，而不是每次在线调用都必须参与 Runtime 决策。

Dataset → Runner → Agent Runtime → Trace / Results
                                     ↓
                         Evaluators → Metrics / Report

因此，不要把 Agent 定义成“Model + Context + Tools + State + Memory + Policy + Runtime + Evaluator”。这会把运行时职责与离线/外部评估职责混为一谈。更有用的问题是：Runtime 能否安全、可观测地执行一次任务？Evaluation Harness 能否用可重复的证据判断其表现？

以后查看任意 Agent Framework 时，可以分别问：它为 Runtime 提供了哪些能力？又如何支持离线评估、回归与报告？

3.34 你现在应该能回答几个问题

为什么 Agent 需要 Tool？

因为模型本身不能直接访问你的业务系统和真实世界。

Tool 是什么？

可以把它理解成：

暴露给模型使用的、经过工程约束的业务能力接口。

Tool 是由模型执行的吗？

不是。

模型提出 Tool Call。

真正的执行由你的 Runtime 完成。

Tool Call 为什么需要 Schema？

因为：

自然语言不能直接作为可靠的程序调用接口。

Agent Loop 的核心是什么？

Decision
→ Action
→ Observation
→ Decision

不是 while True 本身。

Agent 为什么需要 State？

因为长期任务需要知道：

当前已经完成了什么，现在处于什么阶段。

Agent Harness 是什么？

可以把它理解成：

围绕模型、Context、Tools、State 和 Policy 构建起来的运行时系统。

本 Part → Part 4：从行动能力到知识来源

现在已有一个能够提出工具调用、接收结果并继续运行的最小闭环。它可以访问业务系统，但这不意味着它已经能从大量文档中找到可靠依据，也不意味着它拥有跨任务的长期记忆。

下一部分拆开两个容易混淆的问题：RAG 如何从外部资料中检索当前需要的证据；Memory 又在什么条件下保存值得未来继续使用的信息。两者都要接受质量和生命周期管理。
