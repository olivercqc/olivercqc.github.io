Part 5｜Workflow → Agent：什么时候真的需要 Agent？

Agent 并不是 Workflow 的“高级版本”。
真正的问题是：你的任务到底需要不确定的执行路径，还是一个明确的执行流程？

到 Part 4 为止，我们已经认识了模型输入、工具执行、知识检索与记忆等能力。这里的目标不是再把这些能力复述一遍，而是回答一个架构问题：在任务与评估条件固定时，哪些能力值得组合，控制权又应该留给谁？

我们先看同一个审批任务，再逐步比较不同方案。比较时始终使用同一组任务与评价条件：哪些步骤可由规则确定，哪些地方需要模型处理语言，是否需要外部知识或工具，以及执行路径是否真的需要根据观察动态调整。

同一个系统可以组合 RAG、Tool 和 Workflow；Agent 也可以只出现在流程中的某个节点。核心判断不是“能否组合”，而是每增加一分自由度，是否换来了可测量的任务收益。能够动态决策，不等于应该动态决策。

5.1 先看一个最普通的审批流程

假设公司有一个报销系统。

流程规定：

员工提交报销
    ↓
检查金额
    ↓
金额 ≤ 1000？
   ↙      ↘
 Yes      No
 ↓         ↓
主管审批   财务审批
   \      /
    ↓    ↓
   审批完成
      ↓
    通知员工

这个流程看起来其实挺复杂。

有：

  • 判断
  • 分支
  • 审批
  • 通知
  • 状态

但你会发现：

每一步都是可以提前写出来的。

那么最自然的实现是什么？

不是 Agent。

而是：

Workflow

5.2 Workflow 到底是什么？

如果不说那么多术语，可以把 Workflow 理解成：

程序员提前规定好的执行过程。

例如：

def process_reimbursement(request):
    validate_request(request)

    if request.amount <= 1000:
        approve_by_manager(request)
    else:
        approve_by_finance(request)

    notify_user(request)

谁决定下一步？

程序。

什么时候决定？

执行之前就已经写在代码里了。

所以 Workflow 的核心是：

控制流由系统预先定义。

5.3 Workflow 并不意味着不能用 LLM

这一点非常重要。

有些人一看到：

Workflow

就觉得：“这不是 AI。”

完全不是。

例如：

例如：用户提交一封自然语言报销说明。

这封说明可能写得非常随意：“上周去上海参加客户会议，打车花了 182 元，客户那边临时改了时间，所以多住了一晚……”

你可以先让 LLM 做：

自然语言
   ↓
LLM
   ↓
结构化字段

得到：

{
  "city": "上海",
  "purpose": "客户会议",
  "transportation": "taxi",
  "transportation_amount": 182,
  "extra_hotel_night": true
}

然后交给传统 Workflow：

Structured Data
   ↓
Deterministic Rules
   ↓
Approval Workflow

所以：

Workflow 和 LLM 完全可以共存。

这就是：

LLM Workflow。

5.4 LLM Workflow：让模型参与步骤，但不决定整个流程

假设我们做一个售后系统。

流程固定：

用户投诉

分类
 ↓
提取订单号
 ↓
查询订单
 ↓
查询售后政策

其中：

分类
提取
生成

可以交给 LLM。

但：

什么时候查订单
什么时候查政策
什么时候人工审批

仍然由程序决定。

于是：

User
 ↓
LLM: Classification
 ↓
LLM: Extraction
 ↓
Tool: Order API
 ↓
RAG: Policy
 ↓
LLM: Recommendation

整个过程仍然是：

整个过程仍然是：Workflow。

5.5 这时候你可能会问：那 Agent 和 Workflow 的区别到底在哪？

可以先用一个非常实用的问题来区分：

“下一步该做什么”，是谁决定的？

如果是：

程序决定

更像 Workflow。

如果是：

模型根据当前状态动态决定

更接近 Agent。

举个例子。

Workflow

Step 1 → Step 2 → Step 3 → Step 4

程序知道：

程序知道下一步就是 Step 3。

Agent

Current State
      ↓
LLM
      ↓
Should I query order?
Should I query logistics?
Should I query policy?
Should I stop?

模型根据当前 Context 动态选择。

5.6 但不要把 Agent 理解成“随机 Workflow”

Agent 不是：

Workflow 没设计好，所以让模型自己乱跑。

成熟 Agent 的关键仍然是：

明确目标
+
有限工具
+
有限权限
+
受约束的 Runtime
+
明确停止条件

也就是说：

Agent 不是取消控制，而是把一部分控制权从程序转移给模型。

而一旦控制权转移给模型，系统就需要承担额外成本。

5.7 自由度是有代价的

这是理解 Agent 的一个非常好的角度。

可以把系统的“决策自由度”理解成逐渐提高：

Fixed Function
     ↓
Fixed Workflow
     ↓
LLM-assisted Workflow
     ↓
Agent
     ↓
Multi-Agent

自由度越来越高。

同时，通常也伴随着：

Complexity ↑
Failure Surface ↑
Cost ↑
Latency ↑
Evaluation Difficulty ↑

所以：

增加自主性，本质上是在购买更多灵活性。

问题是：

问题是：你是否真的需要这些灵活性？

5.8 一个特别重要的设计问题

假设业务流程有 20 个步骤。

其中 19 个步骤都是固定的。

只有第 7 步存在一定的不确定性。

你需要不需要把整个流程都变成 Agent？

当然不需要。

更合理的方式可能是：

Workflow
   ↓
Step 1
   ↓
Step 2
   ↓
LLM Decision
   ↓
Step 8
   ↓
Step 9
   ↓
...

这就是：

把 Agent / LLM 放在真正需要动态能力的位置。

而不是：

整个系统“Agent 化”。

这会成为非常重要的架构思想：

AI 应该被放在需要 AI 的边界上

5.9 第一次认识 ReAct

现在我们来到 Agent 中一个非常经典的执行模式：

现在我们来到 Agent 中一个非常经典的执行模式 ReAct。

你可以先不要关心这个名字到底代表什么。

先看行为。

用户说：“帮我查订单 10001 为什么还没到。”

Agent：

我需要知道订单状态。
      ↓
调用 query_order()
      ↓
得到：订单已经发货。
      ↓
我还需要知道物流状态。
      ↓
调用 query_logistics()
      ↓
得到：物流 72 小时没有更新。
      ↓
可以给出结论。

你会发现：

Observe
 ↓
Decide
 ↓
Act
 ↓
Observe
 ↓
Decide

这就是 ReAct 思路的核心：

让模型在行动和观察之间循环。

5.10 ReAct 为什么有价值？

如果任务路径很简单：

query_order
 ↓
query_logistics
 ↓
answer

那么你完全没必要做复杂 ReAct。

但如果问题变成：“调查为什么这个订单异常。”

那么可能有很多可能路径：

订单问题？
 ↓
查询库存

物流问题？
 ↓
查询物流

仓库问题？
 ↓
查询出库记录

售后问题？
 ↓
查询售后记录

这时候，固定 Workflow 的路径会快速膨胀。

例如：

A → B → C
A → B → D
A → E → C
A → E → F
...

程序需要提前写越来越多分支。

Agent 的价值就在这里逐渐体现出来：

让模型根据观察结果选择路径。

5.11 但是 ReAct 也有代价

假设 Workflow：

3 steps

而 Agent：

5 tool calls
+
5 model calls

那么 Agent 可能：

  • 更慢
  • 更贵
  • 更容易出错
  • 更难调试

所以你不能因为：

所以你不能因为：Agent 可以自己决定路径。

就得出：

就得出：Agent 一定更适合。

真正的问题仍然是：

路径的不确定性有没有高到值得付出这些代价？

5.12 Planning：什么时候应该先做计划？

ReAct 是：

观察
 ↓
行动
 ↓
观察
 ↓
行动

但一些任务可能天然更适合先规划。

例如：“调查过去一年某类客户投诉，找出主要原因，并提出三个改进建议。”

这已经不是：

查一下订单。

它可能需要：

定义任务
 ↓
收集数据
 ↓
分类
 ↓
统计
 ↓
找异常
 ↓
分析原因
 ↓
形成结论
 ↓
生成建议

如果让 Agent 一步一步临时决定：

下一步做什么？

可能会非常混乱。

于是可以先让它形成计划：

Plan
  ├── Collect
  ├── Classify
  ├── Analyze
  ├── Validate
  └── Report

然后再执行。

这就是 Planning。

5.13 Planning 不是万能药

有的人学会 Planning 以后，会开始：“所有 Agent 都先做 Plan。”

其实也不对。

如果任务只是：“查询订单 10001。”

先生成一个 10 步计划，反而增加了：

  • Token
  • Latency
  • Complexity

所以：

Planning 解决的是任务规划复杂度，不是 Agent 标配。

5.14 Static Plan 和 Dynamic Plan

可以进一步区分。

Static Plan

计划由程序决定。

例如：

A → B → C → D

Dynamic Plan

模型根据当前信息产生计划。

例如：

问题
 ↓
LLM
 ↓
Plan
 ↓
执行
 ↓
发现情况变化
 ↓
Replan

后者灵活性更高。

代价也更高。

5.15 Reflection：让 Agent 检查自己的结果

现在再考虑：“模型已经完成答案了，但我们不太放心。”

一种常见思路是：

Generate
 ↓
Critique
 ↓
Repair
 ↓
Final

例如：

例如：第一轮模型生成维修建议。

然后另一个模型检查：

  • 是否引用了错误维修手册？
  • 是否遗漏了关键故障码？
  • 是否给出了没有依据的结论？

如果发现问题：

Critique
 ↓
Repair

这就是 Reflection / Self-correction 一类模式。

5.16 Reflection 到底有没有用？

这是一个必须保持工程师思维的问题。

如果：

一次生成质量已经很高

再做：

生成
 ↓
反思
 ↓
重新生成

可能只是：

花两倍的钱，得到差不多的结果。

所以任何 Reflection 机制都应该回答：

它到底减少了哪一种失败？

例如：

防止格式错误？
防止遗漏？
防止事实错误？
防止工具误用？

如果回答不出来，那么：

Reflection 很可能只是一个“听起来高级”的组件。

5.19 Architecture A：传统规则

程序直接规定：

5.27 什么时候真的值得使用 Agent？

现在，我们可以给出一个比较成熟的判断。

一个任务越满足下面这些特征，就越值得考虑 Agent：

第一

路径本身难以提前定义。

第二

下一步需要基于当前观察结果动态决定。

第三

可用工具很多，而且调用顺序不是固定的。

第四

任务可能需要探索和反复调查。

5.33 Part 5 最重要的认知变化

到这里，你应该已经不再把 Agent 看作：“一个更高级的 LLM API。”

而应该把它看成：

一种把部分控制流交给模型的系统架构。

这样一来，很多事情都变得清楚了。

Workflow

程序决定：

程序决定下一步做什么。

Agent

模型在约束范围内决定下一步做什么。

Multi-Agent

多个决策实体协作：

谁做什么、何时做、结果如何交接。

本 Part 小结：架构是在购买控制权自由度

选择架构时，先判断流程有多稳定，再判断哪些步骤需要模型参与、执行路径是否真的需要动态调整，以及规划或反思是否带来可测量收益。Traditional、Workflow、LLM Workflow、RAG Workflow、Single Agent 与 Multi-Agent 不是逐级升级的技术等级；它们把不同程度的控制权留给程序或模型。

一个成熟的架构决策至少写清三件事：当前任务为什么需要这一级自由度；它相对更简单基线改善了什么；新增的成本、延迟、失败面和治理负担能否被接受。

架构 Shootout 给出的是在特定任务、数据、评估方法和运行条件下的比较。它不能靠一次演示决定架构优劣，也不能把一个示例里的优势直接推广到所有业务。
