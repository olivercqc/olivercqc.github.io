Part 4｜RAG & Memory：让 Agent 获得知识，并记住真正值得记住的东西

一个聪明的 Agent，如果不知道公司的业务知识，它能做什么？
一个知道很多知识的 Agent，如果每次都把所有历史重新读一遍，又能坚持多久？

Part 3 让模型通过受控 Tool 访问结构化业务系统；但制度、操作手册、维修文档和过往案例往往存在于文档或知识库中，并不一定能通过一个业务 API 直接取得。你不能把所有资料硬编码进 Tool，也不应把整套知识库塞进每次请求。

另一个问题也会随之出现：如果系统希望未来任务复用过去的某些信息，是否应该保存所有对话？

这两个问题分别引出本 Part 的两条主线：RAG 解决当前任务怎样取得外部证据；Memory 解决哪些信息值得经过治理后留给未来任务。

4.1 一个 Agent 为什么会“什么都不知道”？

先来看一个非常简单的问题。

用户问：

“P0XXX 这个故障码代表什么？”

模型可能非常有通用知识。

但假设：

P0XXX 是你们公司内部定义的一种特殊故障码。

模型没有见过你们公司的内部资料。

那么它不可能因为“模型很强”就自动知道。

这时候，很多初学者会犯第一个错误：

“那就把维修手册全部放进 System Prompt。”

于是：

System Prompt
+
整个维修手册
+
全部产品文档
+
全部历史案例

系统很快开始膨胀。

下一步又会发生：

文档太长。

于是继续：

“那我换个更大上下文的模型。”

然后：

“还是有点慢。”

再然后：

“成本也太高了。”

我们又回到了 Part 2 已经讨论过的问题：

模型看到的信息越多，并不意味着当前决策越好。

真正合理的问题应该是：

我现在需要什么知识？

4.2 RAG 到底解决什么问题？

假设公司有一本：

《新能源汽车高压系统维修手册》

里面有 800 页。

用户问：

“车辆显示 P0XXX，同时充电速度明显下降，通常先检查什么？”

我们真正想做的事情是：

用户问题
   ↓
找到相关知识
   ↓
把相关知识放入 Context
   ↓
让模型回答

这就是：

Retrieval-Augmented Generation

也就是：

RAG。

“Retrieval”解决的是：

找什么。

“Generation”解决的是：

找到以后怎么理解、组织和回答。

因此一个非常朴素的 RAG 可以表示成：

Question
   ↓
Retrieve
   ↓
Relevant Documents
   ↓
Context
   ↓
LLM
   ↓
Answer

你可以把它理解成：

先查资料，再让模型基于资料回答。

4.3 RAG 其实很像搜索

如果你过去做过搜索系统，那么 RAG 很容易理解。

用户输入：

“P0XXX 充电慢”

系统要做的是：

Query
 ↓
Search
 ↓
Top Relevant Results
 ↓
Return

RAG 只是在最后多了一步：

Search Results
 ↓
LLM
 ↓
Natural Language Answer

所以不要把 RAG 神秘化。

它不是：

“给 Agent 增加了一个神奇的长期知识脑。”

更准确的理解是：

RAG 是一种让模型在需要的时候访问外部知识的机制。

4.4 可是，文档是一整本书，模型应该搜索什么？

这时候我们会遇到 RAG 的第一个真正工程问题。

假设：

维修手册
=
800 页

你不能把 800 页直接作为一个检索结果交给模型。

你必须把文档拆成更小的部分。

这就是：

Chunking。

4.5 Chunking：把文档切成可以检索的知识单元

最简单的方法：

每 1000 个字符切一段。

例如：

Document
 ↓
Chunk 1
Chunk 2
Chunk 3
Chunk 4
...

这样搜索时：

用户问题
 ↓
寻找最相关 Chunk
 ↓
返回若干 Chunk

这个思路非常简单。

但是：

怎么切，实际上会影响检索效果。

例如一个操作说明：

步骤 1：检查高压连接器

步骤 2：读取故障码

步骤 3：确认绝缘电阻

步骤 4：执行复位

如果你随便在中间切一刀：

Chunk 1:
步骤 1
步骤 2

Chunk 2:
步骤 3
步骤 4

有时候还好。

但如果刚好把：

条件

和：

对应动作

拆开了，Chunk 本身就失去了完整语义。

因此：

Chunk 不是简单的字符串切片。

它应该尽可能形成：

一个具有相对完整意义的知识单元。

4.6 一个后端工程师很容易理解的类比

假设你有一个数据库。

你不会把整张数据库表看作一次查询的最小单位。

你会根据业务查询：

Table
 ↓
Rows
 ↓
Relevant Rows

RAG 有一点类似：

Document
 ↓
Chunks
 ↓
Relevant Chunks

所以 Chunk 可以先简单理解成：

面向检索而组织的数据单元。

4.7 Embedding：如果用户说法完全不同怎么办？

现在假设文档里写的是：

“车辆高压系统出现异常，建议首先检查动力电池绝缘状态。”

而用户问：

“我的车充电特别慢，会不会是电池绝缘有问题？”

两个句子没有共享很多完全相同的关键词。

如果只做简单关键词匹配：

Keyword Search

可能效果一般。

这时候，我们希望系统能够理解：

这些文字虽然表达方式不同，但语义可能相关。

于是出现了：

Embedding

Embedding 可以先粗略理解成：

把文本转换成一个用于表示语义特征的向量。

例如：

文本
 ↓
Embedding Model
 ↓
Vector

那么：

问题 Vector

可以和：

文档 Chunk Vector

进行相似度比较。

于是：

Query
 ↓
Embedding
 ↓
Similarity Search
 ↓
Relevant Chunks

这就是我们经常说的：

向量检索。

4.8 不要把 Embedding 神秘化

你现在不需要学习高深的向量数学。

你只需要建立一个工程直觉：

Embedding 是为了让系统能够用“语义相似”而不只是“字面相同”来寻找信息。

例如：

“充电速度突然下降”

和：

“车辆充电功率异常降低”

虽然文字不同，但业务语义可能非常接近。

Embedding 就是在帮助系统发现这种关系。

4.9 但是向量搜索也不是万能的

现在假设用户问：

“工单号 2026100812345 的最终处理结果是什么？”

这是一个非常明确的标识符查询。

你其实未必需要：

“语义相似搜索。”

更直接的方式可能是：

Exact Match

或者：

Database Query

这再次印证了 Part 0 的原则：

不要因为技术存在，就强行使用技术。

RAG 也是一样。

并不是所有信息查询都需要向量数据库。

4.10 Dense、Sparse、Hybrid：三种基本检索思路

到这里，我们可以建立一个简单分类。

Sparse Retrieval

更擅长：

关键词、精确术语、编号。

例如：

P0XXX
工单号
零件号
SKU

Dense Retrieval

更擅长：

语义相似。

例如：

“充电很慢”

可能匹配：

“充电功率异常降低”。

Hybrid Retrieval

结合两者。

Keyword
   +
Semantic
   ↓
Candidate Results

这个思路很重要，因为真实业务往往既有：

人类自然语言。

也有：

专业编号、产品型号、错误码、订单号。

所以实际系统中：

混合检索往往比单一方法更符合业务需求。

4.11 Metadata：同一个关键词，不一定是同一份知识

假设知识库里有：

2024 车型维修手册
2025 车型维修手册
2026 车型维修手册

用户明确说：

“我的车是 2024 款。”

如果你只进行语义搜索，三个文档可能都很相似。

这时候可以增加 Metadata：

{
  "model_year": 2024,
  "document_type": "repair_manual",
  "language": "zh",
  "version": "v3"
}

然后检索时增加过滤：

query
+
metadata filter

于是搜索空间从：

所有文档

缩小成：

2024
+
repair_manual

这就是非常典型的：

先过滤，再检索。

4.12 Reranking：找到一堆“像”的，不代表找到了最好的

假设一次检索返回：

Result 1
Result 2
Result 3
Result 4
Result 5
Result 6
...

它们都和问题“有点关系”。

但是：

最相关的到底是哪几个？

这时候可以增加：

Reranking

简单理解：

Query
 ↓
Initial Retrieval
 ↓
Candidate Set
 ↓
Rerank
 ↓
Best Results

因此，一个常见的 RAG Pipeline 会逐渐变成：

Question
 ↓
Query Processing
 ↓
Candidate Retrieval
 ↓
Metadata Filtering
 ↓
Reranking
 ↓
Context
 ↓
LLM

这已经不是简单的：

“把向量数据库接起来。”

而是一个真正的检索系统。

4.13 RAG 的真正难点其实不是“生成”

很多刚接触 RAG 的人会认为：

“把文档放进向量库就结束了。”

实际上，真正容易出问题的是：

找错知识。

假设模型回答得非常流畅。

但它引用的是错误版本的维修手册。

那么语言生成能力再好，也只是：

很自信地说错话。

因此 RAG 系统至少存在两个独立环节：

Retrieval Quality
        ↓
Generation Quality

前面找到错的，后面再聪明也很难补救。

所以：

RAG 的 Evaluation 不能只测最终回答。

这一点会在 Part 6 再系统展开。

4.14 从 RAG 到 Agentic RAG

现在看一个简单的 RAG。

用户问：

“这个故障是什么原因？”

程序：

Question
 ↓
Retrieve
 ↓
Top 5 Chunks
 ↓
LLM
 ↓
Answer

这个流程很清楚。

但是有些任务并没有这么简单。

例如：

“调查这辆车为什么充电功率持续下降，并给出最可能的原因。”

系统第一次检索后可能发现：

资料不够。

于是可能需要：

先查故障码
 ↓
再查电池诊断
 ↓
根据结果重新构造 Query
 ↓
再检索维修手册
 ↓
比较历史案例

这时候：

“要不要查？”

“查什么？”

“查完以后还需要什么？”

开始可以由 Agent 动态决定。

于是就出现：

Agentic RAG

可以简单理解成：

Agent
 ↓
Decide whether to retrieve
 ↓
Query
 ↓
Retrieve
 ↓
Observe
 ↓
Decide whether more information is needed
 ↓
Retrieve again
 ↓
...

所以：

普通 RAG 通常是固定检索流程；Agentic RAG 开始让 Agent 参与检索策略。

4.15 什么时候不要使用 Agentic RAG？

如果问题只是：

“公司报销标准是什么？”

那么：

Question
 ↓
Retrieve
 ↓
Answer

可能已经足够。

没必要：

Agent
 ↓
规划
 ↓
多轮搜索
 ↓
反思
 ↓
再搜索
 ↓
...

否则你只是：

把一个简单搜索问题变成一个昂贵的 Agent 问题。

再次回到 Part 0：

复杂度必须由问题驱动。

4.16 现在来说 Memory

Part 2 已经区分了 History、State、Memory 与 RAG。本节向实现层再走一步：当一次交互产生了新信息，系统应该把它留在事件记录里、从外部知识源重新检索，还是提升为可能影响未来任务的记忆？

例如，“这次查询没找到维修手册”通常只是一次任务事件；“该用户长期偏好先看原始诊断数据”则可能成为记忆候选。候选并不等于已获准写入，后面会具体讨论写入治理和生命周期。

4.17 Memory 不等于“把聊天记录存起来”

数据库能保存信息，却不会替你决定哪些信息值得在未来使用。把全部对话写进数据库，只解决了“有没有保存”，没有解决“哪些应该被取回、何时仍有效、是否可以用于当前任务”。

因此，记忆是一个需要治理的应用能力，不是数据库表的另一个名字。具体写入条件、冲突处理与过期规则会在本 Part 的 Memory 设计实验中展开。

4.18 四类 Memory

我们先建立一个工程上非常实用的分类。

Working Memory

一些实现会把当前任务中的临时工作材料称为 Working Memory。为避免与 Part 3 定义的权威 State 混淆，本书采用更窄的用法：Working Memory 指临时归纳、尚未确认的假设、候选检查步骤等工作材料，不是业务系统的权威记录。

例如：

待验证的故障原因假设
对三份检索结果的临时比较
下一步可尝试的候选查询

它通常生命周期较短。订单状态、任务是否完成、写操作是否已执行等权威信息仍由应用 State 或业务系统负责，不能只留在 Working Memory 里。

Episodic Memory

过去发生过的具体事件。

例如：

上次这个设备出现 P0XXX，
最后通过更换连接器解决。

它保留的是：

发生过什么。

Semantic Memory

从大量事件中提炼出的稳定事实。

例如：

该型号设备对某类错误码
通常需要首先检查绝缘状态。

这是更抽象、更长期的知识。

User Memory

与用户长期相关的信息。

例如：

用户是电池测试工程师。
用户偏好简洁回答。
用户主要负责某类设备。

这些信息未来可以持续影响交互。

4.19 Memory 和 State 为什么还不是一回事？

两者的差异不是存在哪里，而是它们承担什么责任。status = waiting_for_diagnostic_result 是当前任务的状态，它必须跟随任务推进而更新；“用户偏好优先展示原始诊断数据”是候选长期记忆，它可以影响多个任务，但必须允许被纠正、过期或删除。

因此，不能把 Memory 当作权威任务状态，也不能用一条长期记忆覆盖当前系统记录的事实。发生冲突时，必须有明确的来源优先级和更新时间规则。

4.20 Memory 也会污染 Context

这里直接复用 Part 2 的 Context Budget 原则：Memory 是候选来源，不是默认全部注入的内容。保存阶段判断“未来是否值得保留”，读取阶段还要判断“此刻是否相关、是否仍然有效”。这两个决策必须分开。

Memory Store → Eligibility / Freshness → Relevance → Context Budget → Model

长效存储做得再好，如果检索阶段把过期、冲突或无关的记忆一股脑加入 Context，仍然会降低当前决策质量。

4.21 Memory 的一个危险问题：记错了怎么办？

想象一下：

用户说：

“我平时做 Python 开发。”

Agent 把它记成：

user_role = python_developer

半年以后，用户已经换成：

Go。

但 Memory 还是旧的。

于是 Agent 每次都假设：

“你作为 Python 工程师应该……”

这时候 Memory 就从：

帮助系统。

变成：

错误信息源。

因此 Memory 需要考虑：

  • 更新时间
  • 来源
  • 置信度
  • 覆盖规则
  • 失效
  • 删除
  • 冲突

这和传统系统中的：

Data Freshness

非常类似。

4.22 Memory Conflict

例如系统里有两个事实：

4.24 实验：建立一个真正的 Business Knowledge Agent

现在我们开始做这一 Part 的核心项目。不要重新做一个完全不同的 Demo；先把 RAG 当成一个能独立测量的知识检索组件，再理解它如何被 Part 3 的 Agent 调用。前文的新能源汽车维修业务继续作为概念例子，但配套 Lab 04 使用的是仓库内合成维修文档和固定案例，不连接真实车辆系统。

先阅读 labs/lab04_rag/TASK.md，然后跑本地检索基线与测试：

实验主线先比较 Sparse、Dense/Hash、Hybrid、Metadata Filtering 与 Reranking，再观察具体案例的命中证据。随后可以把检索结果交给真实回答模型；是否使用真实 embedding 是另一项实验选择，不能混为同一条证据链。

4.28 第四步：先设计 Memory 的生命周期，而不是把它假装成已经实现的功能

用户说：

“以后类似故障请优先给我原始诊断数据。”

这句话可以作为一个 Memory 设计例子：

{
  "type": "user_preference",
  "key": "diagnostic_output_order",
  "value": "raw_data_first"
}

但要把这个结构写进 JSON，不代表系统已经拥有跨会话记忆。配套仓库中的 Lab 03/04 当前没有实现持久化用户 Memory；Part 3 的单次运行状态、聊天消息和 RAG 文档库都不能冒充它。请将这一阶段作为设计工作表：明确记忆归属哪个用户或会话、依据什么来源写入、何时更新/遗忘、冲突时谁是事实来源、是否设置 TTL、如何控制访问，以及如何评估错误记忆造成的损害。

若以后实现 Memory，必须单独增加存储、权限、生命周期和回归测试；本轮不要为了让示例“看起来完整”就声称仓库已经能保存并恢复用户偏好。

4.29 第五步：把 Agentic Retrieval 当作一个需要单独验证的决策问题

更复杂的系统可能根据当前查询决定是否增加关键词、改变检索策略或继续寻找证据。Lab 04 的任务确实包含一个受控的 Agentic Retrieval Decision，但它是围绕本地检索策略的教学实现，不等同于一个能够自由调用多个业务 API、持久化用户 Memory 并无限循环的完整维修 Agent。

4.30 Break：故意让 Retrieval 出问题

实验不是结束在：

4.32 一个很重要的工程诊断习惯

以后一个 RAG Agent 答错时，不要只问：

“模型为什么答错？”

而应该拆成：

1. Knowledge Base 有正确资料吗？

2. Chunk 切对了吗？

3. Retrieval 找到了吗？

4. Ranking 排对了吗？

5. Context 放进去了吗？

6. Memory 有没有干扰？

7. Model 是否正确理解？

这就是：

Failure Attribution。

它会在 Part 6 Evaluation Engineering 中成为一个完整主题。

4.33 一个容易踩的坑：把 RAG 当作“知识训练”

很多初学者会说：

“我们把公司的文档训练进模型。”

但对于很多业务场景，真正需要的并不是重新训练模型。

而是：

让模型在回答当前问题时访问外部知识。

这个思路非常重要。

因为业务知识会不断变化：

2025 Policy
↓
2026 Policy
↓
2027 Policy

如果每次业务规则变化都重新训练模型，会非常笨重。

RAG 的一个重要价值，就是：

把变化频繁的业务知识从模型本体中解耦出来。

这也是为什么：

文档更新、版本管理、Metadata、Retrieval Evaluation

都会变得非常重要。

可选真实模型实验：检索证据是否支持回答

本地检索基线和检索组件测试属于主线；以下回答评估会调用真实回答模型，不能因为选择 local_hash 就当作完全离线。仅在完成主线、已确认 Provider 兼容性、费用和输入数据处理安排后运行。

python -m labs.lab04_rag.src.answer_evaluation --retriever local_hash --method hybrid_rerank --top-k 3 --output artifacts/lab04-local-retriever-answer-evaluation.json

运行前需要配置 AI_BASE_URL、AI_API_KEY 和 AI_MODEL。如果这些配置缺失，程序会把逐案例生成错误记录下来；CLI 退出码为 0 只表示报告成功写出，不表示回答评估成功。

如果还要把真实 embedding 检索与真实回答模型一起测量，则使用独立的 remote_embeddings 路径，并额外配置 AI_EMBEDDING_MODEL 及相应价格参数。两条路径不要混在一个结论里：local_hash 是“本地确定性检索 + 真实回答生成”；remote_embeddings 是“真实 embedding 检索 + 真实回答生成”。

实验要检查的不只是引用 ID 是否存在，还要人工确认来源内容是否真的支持答案。当前六例回答集和小型合成文档库适合验证流程与暴露典型失败，不足以证明生产质量。完整的跨系统动态调查可以在 Part 3 的 Agent Loop 中继续设计；持久化 Memory 仍是独立的设计与实现任务。

4.34 RAG 不是所有知识问题的答案

再来看一个问题。

用户问：

“订单 10001 现在到哪里？”

这不是典型知识库问题。

因为答案来自：

实时业务状态。

最合理的方式可能是：

query_order()

而不是：

RAG

再比如：

“某公司 2023 年公布的某项政策是什么？”

可能更适合静态知识检索。

所以：

→ Tool / API

静态知识
→ RAG

长期用户偏好
→ Memory

当然，真实系统里三者也可以组合。

这个问题同时需要：

      ↓

      ↓

+

你现在可以看到：

4.36 RAG 的另一个现实问题：知识会变化

假设维修手册：

Version 1

后来更新成：

Version 2

如果知识库里两个版本都存在，但系统没有明确规则：

“优先最新版本。”

那么 Agent 可能检索到旧文档。

因此，真实 RAG 系统需要考虑：

  • Version
  • Effective Date
  • Source
  • Authority
  • Expiration
  • Metadata

这其实已经非常接近：

企业知识管理。

所以不要把 RAG 简化成：

“向量数据库 + Prompt。”

一个真正有价值的企业 RAG，本质上是：

知识管理 + 检索 + Context Construction + LLM。

4.37 Memory 也需要生命周期

Memory 不是：

写入一次，永久有效。

例如：

Temporary Task Memory

可能只存在几个小时。

而：

User Preference

可能长期存在。

因此 Memory 可以存在：

短期
中期
长期

不同生命周期。

这又回到了后端工程师很熟悉的：

TTL / Expiration。

你会发现：

Agent Memory 越认真做，越像一个真正的数据系统。

4.38 Part 4 的一个核心认识

回到 Part 2 建立的约定，再看它们在知识型 Agent 中如何协作：

History
= 已发生的交互或事件记录

State
= 应用维护的权威当前状态

Memory
= 经筛选、可更新、可过期或删除的跨任务信息

Knowledge Source
= 手册、SOP、数据库等权威或候选资料

RAG
= 从知识源中检索并提供候选证据的处理路径

Context
= 当前决策真正提供给模型的输入视图

一次调用可以把当前请求、State 的必要快照、相关 History/Memory、RAG 检索的证据和 Tool Results 组装成 Context，但不能因此把它们视为同类数据。尤其要注意：RAG 是检索路径，不是知识本身；State 负责权威当前状态，不能被 Memory 或模型生成的文字替代。

这一区分可以帮助你判断：答案错了究竟应该检查知识来源、检索结果、状态一致性、记忆资格，还是 Context 的组装过程。

4.40 练习：什么东西绝对不应该进入 Memory？

这是一个很重要的反向思考。

例如：

“用户今天说早餐吃了包子。”

它是否应该成为永久 Memory？

再比如：

“用户明确要求以后所有回答都先给结论。”

是否值得？

再比如：

“用户今天临时让我查一次订单。”

是否值得？

要求你分别判断：

Remember
Temporary
Ignore

通过这个练习理解：

Memory 的价值不在于“记住更多”，而在于“记住真正有用的东西”。

4.41 练习：RAG 还是 Tool？

下面三个问题分别怎么解决？

问题 A

“公司的退款政策是什么？”

问题 B

“订单 10001 现在是什么状态？”

问题 C

“根据公司的退款政策判断订单 10001 是否符合退款条件。”

可能分别是：

A → RAG

B → Tool

C → RAG + Tool + LLM / Workflow

而如果判断过程需要动态查询多个系统：

C → RAG + Tool + Agent

注意这里不是唯一答案。

关键是：

能否解释为什么。

4.42 本 Part 小结：知识来源与决策时输入要分开治理

RAG 关注当前问题需要哪些外部证据，以及文档如何切分、检索、排序和校验；Memory 关注哪些交互信息值得跨任务保留，以及何时更新、限制、过期或删除。两者都可能为 Context 提供信息，但都不应绕开来源、相关性和权限判断。

遇到答案错误时，先沿证据链定位是文档、Chunk、Retrieval、Reranking、Context 还是模型理解出了问题；不要把所有失败都归因于“模型不够聪明”。

本 Part → Part 5：从拥有能力到选择架构

工具让系统能够行动，RAG 让系统能够查找资料，Memory 可以为后续任务保留有用信息。但能力越多不代表越应该把控制权交给模型。

下一部分固定同一个业务任务，比较规则系统、LLM Workflow、RAG Workflow、Single Agent 和 Multi-Agent。判断标准不是哪种架构更先进，而是额外的自由度有没有换来足够的任务收益。
