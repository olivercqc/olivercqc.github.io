Part 9｜Coding Agent：让 Agent 真正参与软件开发

“帮我写一个函数”并不难。
真正困难的是：让一个 Agent 进入一个陌生代码仓库，理解问题、找到正确位置、修改代码、运行测试、处理失败，并最终交付一个可信的变更。

到了 Part 8，我们已经开始研究复杂 Agent。

现在，把我们已经学过的能力放到一个你非常熟悉的环境里：

软件工程。

如果你本身就是后端工程师，那么这一次会特别有感觉。

因为以前你可能这样使用 LLM：

“帮我写一个 FastAPI 接口。”

或者：

“这个 SQL 为什么报错？”

或者：

“帮我实现一个 Redis Cache。”

这时候模型更像：

一个代码顾问。

它告诉你：

“你可以这样写。”

你拿过代码以后，自己：

  • 找文件
  • 找函数
  • 修改
  • 运行测试
  • 看报错
  • 再问模型
  • 再修改

真正执行软件工程的，仍然是你。

而 Coding Agent 想做的事情更进一步：

Issue
 ↓
Understand Repository
 ↓
Find Relevant Code
 ↓
Plan Change
 ↓
Edit Code
 ↓
Run Tests
 ↓
Observe Failure
 ↓
Repair
 ↓
Run Tests Again
 ↓
Final Patch

这已经不再只是：

Code Generation。

而开始变成：

Software Engineering Automation。

9.1 为什么“生成代码”不等于“会写软件”？

先看一个简单任务。

用户说：

“帮我写一个 Python 函数，实现用户邮箱格式校验。”

模型很容易完成：

import re

def is_valid_email(email: str) -> bool:
    return bool(
        re.match(
            r"^[^@\s]+@[^@\s]+\.[^@\s]+$",
            email,
        )
    )

问题看起来结束了。

但现实中的软件开发任务通常不是这样。

真实 Issue 往往是：

“用户注册时存在重复邮箱问题。部分请求在高并发下会创建两条记录，请修复，并确保现有 API 行为不变。”

这时候你必须知道：

  • 用户表在哪里？
  • 注册接口在哪里？
  • ORM Model 在哪里？
  • Database Constraint 有没有？
  • Transaction 怎么处理？
  • 是否存在 Race Condition？
  • 现有测试在哪里？
  • 哪些 API 依赖这个逻辑？
  • 有没有兼容性要求？

模型只知道 Python 语法显然不够。

所以：

Coding Agent 的第一难题不是生成代码，而是理解代码。

9.2 Repository 是 Coding Agent 的“世界”

普通 Agent 面对的是：

Business System

Coding Agent 面对的是：

Repository

一个真实 Repository 可能包含：

app/
tests/
scripts/
docs/
config/
migrations/
pyproject.toml
Dockerfile
README.md

里面又有：

几十个模块
几百个文件
数万行代码

如果用户只给模型：

Issue:
“修复注册接口重复创建用户的问题。”

模型还远远不知道：

去哪里修改。

所以 Coding Agent 的第一个核心能力是：

Repository Context

9.3 Repository Context：模型需要知道代码在哪里

假设仓库：

project/
├── app/
│   ├── api/
│   │   └── users.py
│   ├── services/
│   │   └── user_service.py
│   ├── models/
│   │   └── user.py
│   └── repositories/
│       └── user_repository.py
│
├── tests/
│   ├── test_users.py
│   └── test_user_service.py
│
└── migrations/

一个初学者可能直接把全部代码塞给模型。

但我们在 Part 2 已经知道：

Context 不是越多越好。

Coding Agent 面临的第一个问题因此变成：

哪些代码是当前 Issue 相关的？

9.4 Repository Search：先找到候选代码

例如 Issue：

“注册时重复创建用户。”

Agent 可以先搜索：

register
signup
create_user
email
User

可能得到：

app/api/users.py
app/services/user_service.py
app/models/user.py
tests/test_users.py

这时候 Agent 的 Context 才开始有意义。

于是：

Issue
 ↓
Repository Search
 ↓
Candidate Files
 ↓
Relevant Context
 ↓
Model

注意：

Search 本身也是 Tool。

所以 Coding Agent 其实天然使用了我们 Part 3 学过的 Tool Architecture。

9.5 File Read：不要一次读取整个仓库

找到：

user_service.py

以后，还需要读取。

但不要：

Read Everything

而应该：

Search
 ↓
Relevant File
 ↓
Relevant Function
 ↓
Relevant Lines

这就是一个典型的：

Context Narrowing。

从：

整个 Repository

逐步收缩到：

当前 Task 真正需要的代码。

9.6 Code Context 和普通 Context 有一点不同

普通 Agent 可能主要面对：

Natural Language
Documents
Business Data

Coding Agent 面对：

Source Code
Tests
Configuration
Schemas
Dependencies
Git History
Error Logs

这些信息之间存在非常强的结构关系。

例如：

API
 ↓
Service
 ↓
Repository
 ↓
Database

或者：

Function
 ↓
Caller
 ↓
Test

所以 Coding Agent 的 Context Engineering 其实是：

Repository-aware Context Engineering。

9.7 Code Search 为什么是核心 Tool？

假设仓库有 300 个 Python 文件。

用户说：

“修复订单取消逻辑。”

模型如果没有搜索能力，只能：

猜。

有搜索能力以后：

grep / rg / symbol search

可以快速定位：

cancel_order
cancel
order_status
OrderService

所以 Coding Agent 的基本 Tool 集合往往包括：

Search
Read File
Write File
Patch
Terminal
Test
Git

你会发现：

Coding Agent 本身就是一个 Tool-using Agent。

区别只是：

它操作的是代码仓库和开发环境。

9.8 Tool：从“查询订单”变成“修改代码”

Part 3 中我们写过：

query_order()

Coding Agent 中可能变成：

read_file()
search_code()
apply_patch()
run_tests()
git_diff()

例如：

apply_patch(
    file="app/services/user_service.py",
    patch="..."
)

然后：

run_tests(
    command="pytest tests/test_users.py"
)

这意味着：

Agent 的 Tool 不再只是“获取信息”。

它开始能够：

改变自己的工作环境。

9.9 为什么代码编辑不能只靠“重新生成文件”？

最简单的 Coding Agent 可能会：

读整个文件 → 生成整个文件 → 覆盖。

小项目也许能工作。

真实仓库却很危险。

因为一次小修改可能：

意外覆盖其他开发者正在做的代码。

或者：

删除文件中的特殊配置。

或者：

改动大量无关行。

所以更好的方式通常是：

最小变更。

也就是：

Read
 ↓
Identify Exact Change
 ↓
Patch
 ↓
Review Diff

这和 Git 的工作方式非常接近。

9.10 Diff：Coding Agent 最应该让你看到的东西

假设 Agent 修改了：

user_service.py

你不应该只看到：

“代码修改完成。”

应该看到类似：

- user = create_user(email)
+ user = get_or_create_user(email)

更重要的是：

为什么改这一行？

这会成为 Coding Agent 的重要可审查接口。

因此：

Coding Agent 不应该把代码修改当成不可见的内部行为。

它应该尽可能产生：

Patch
Diff
Test Results
Reason for Change

9.11 Test：Coding Agent 的“现实世界反馈”

现在我们来到了 Coding Agent 最关键的 Tool：

Test Execution

假设 Agent 修改了代码。

它说：

“完成了。”

但是你还不知道：

真完成了吗？

于是：

Modified Code
 ↓
Run Tests
 ↓
Observe Result

如果：

pytest
→ PASS

那么 Agent 得到了一个很强的外部证据。

如果：

pytest
→ FAIL

它得到了另一种信息：

现实世界告诉它：刚才的修改不正确。

这就是 Coding Agent 和普通代码生成最大的区别之一。

9.12 Tests 是 Agent 的 External Verification

在 Part 8 中，我们讲过 Reflection。

当时我们说：

单纯让模型“再检查一遍”并不一定可靠。

Coding Agent 提供了一个非常好的例子。

假设 Agent 说：

“这个 Bug 已经修好了。”

我们不需要完全相信它。

我们可以：

run_tests()

让测试系统告诉我们：

对不对。

因此：

LLM
 ↓
Code Change
 ↓
Test
 ↓
Real Feedback
 ↓
LLM

这是非常强的 Agent Loop。

9.13 Error：失败本身就是 Context

假设测试输出：

FAILED tests/test_users.py

AssertionError:
expected 1 user, got 2

这个错误不应该被简单丢掉。

它应该进入 Agent Context：

Code Change
+
Test Failure
 ↓
Model

模型看到：

我的修改没有解决问题。

于是它可能重新检查：

  • Transaction
  • Unique Constraint
  • Race Condition

然后进行下一次修改。

这形成：

Understand
 ↓
Modify
 ↓
Test
 ↓
Failure
 ↓
Diagnose
 ↓
Repair
 ↓
Test

现在，Agent 已经开始真正参与：

Debugging。

9.14 Coding Agent 的核心循环

我们现在可以正式写出它：

             ┌──────────────────┐
             │      Issue       │
             └────────┬─────────┘
                      ↓
                Understand
                      ↓
               Search / Read
                      ↓
                    Plan
                      ↓
                  Modify
                      ↓
                  Run Test
                      ↓
                ┌─────┴─────┐
                ↓           ↓
              PASS         FAIL
                ↓           ↓
             Review      Diagnose
                │           ↓
                │         Repair
                │           ↓
                │       Run Test
                │           │
                └───────────┘
                      ↓
                   Final Patch

这就是 Coding Agent 的基本闭环。

9.15 这其实已经很像一个软件工程师

你仔细看一下：

理解 Issue
 ↓
阅读代码
 ↓
制定方案
 ↓
修改代码
 ↓
运行测试
 ↓
分析失败
 ↓
修复
 ↓
再次测试

这就是人类工程师日常工作的一个非常典型的循环。

所以 Coding Agent 真正的价值并不是：

“AI 能写代码。”

而是：

AI 可以进入软件工程的反馈闭环。

9.16 但别急着让 Agent 修改真实生产仓库

这里 Part 7 的内容必须重新出现。

Coding Agent 拥有非常大的权限：

Read Files
Write Files
Run Commands
Run Tests
Git
Potentially Network
Potentially Secrets

所以安全边界非常重要。

9.17 Sandbox：给 Coding Agent 一个安全的工作台

理想情况：

Real Repository
       ↓
Controlled Workspace
       ↓
Coding Agent
       ↓
Sandbox

Sandbox 可以限制：

Filesystem
Network
CPU
Memory
Processes
Secrets

这样即使 Agent 执行了错误命令，也不会轻易伤害真正的系统。

9.18 为什么“禁止危险命令”远远不够？

一种非常简单的安全方式是：

禁止 rm -rf。

但现实世界的问题远远不止这一条命令。

例如：

curl ...
wget ...
python arbitrary_script.py

甚至某个看似正常的测试：

pytest

也可能执行项目里的代码。

所以安全不能只是：

命令黑名单。

而应该是：

执行环境隔离。

这就是 Sandbox 的真正价值。

9.19 Secrets：Coding Agent 不应该看到所有环境变量

很多项目里都有：

DATABASE_URL
API_KEY
AWS_SECRET
PRIVATE_KEY

如果 Agent 可以：

env

那么这些秘密可能进入 Context。

这是非常危险的。

所以 Coding Agent 的执行环境应该遵循：

只提供完成任务所需要的最小 Secrets。

例如：

Unit Test Environment
→ Test Database Credentials

Production Credentials
→ Never Expose

这其实就是我们在 Part 7 学过的：

Least Privilege。

9.20 Git：为什么 Version Control 对 Coding Agent 特别重要？

如果 Agent 会修改大量代码：

你一定希望知道它改了什么。

Git 天然提供：

Diff
Commit
Branch
Revert
History

所以一种合理的 Coding Agent 工作方式是：

Issue
 ↓
Create Workspace / Branch
 ↓
Agent Changes
 ↓
Run Tests
 ↓
Review Diff
 ↓
Human Approval
 ↓
Merge

这比：

Agent 直接修改主分支。

安全得多。

9.21 Git 其实是 Agent 的“外部状态管理器”

还可以更进一步理解。

Agent 的工作不是只有：

Model Context

它还会产生：

Code Changes
Test Results
Diff
Artifacts

这些都可以通过 Git 和文件系统保存。

所以：

代码仓库本身就是 Agent 的工作记忆的一部分。

9.22 Issue Understanding：Agent 为什么不能直接开写？

现实中的 Issue 通常不是：

“把函数 A 改成 B。”

而是：

“线上反馈某些用户在特定条件下无法提交订单，请检查并修复。”

这意味着 Agent 第一步不是写代码。

而应该：

Issue
 ↓
Clarify Expected Behavior
 ↓
Find Relevant System
 ↓
Identify Current Behavior
 ↓
Reproduce
 ↓
Locate Root Cause

这其实与传统 Debugging 非常接近。

9.23 Reproduce：先让问题真正出现

这是 Coding Agent 非常值得强调的能力。

假设 Issue：

“用户取消订单后库存没有回滚。”

一个糟糕的 Agent：

猜一个原因，直接修改库存代码。

一个更好的 Agent：

Read Issue
 ↓
Find Cancellation Flow
 ↓
Find Inventory Update
 ↓
Read Tests
 ↓
Reproduce Failure

如果能够先写：

test_cancel_order_should_restore_inventory()

并确认：

FAIL

那么后面的代码修改就拥有了：

真实问题证据。

9.24 Coding Agent + Test-driven Development

这时候可以把 TDD 思想与 Agent 结合起来：

Issue
 ↓
Understand
 ↓
Write / Update Test
 ↓
Confirm Failure
 ↓
Implement Fix
 ↓
Run Test
 ↓
Regression

这个闭环非常强。

因为 Agent 不只是：

预测什么代码应该写。

而是在：

通过测试不断获得反馈。

9.25 但是 Test 本身也可能是错的

需要注意：

Coding Agent 不能把测试结果绝对化。

因为测试可能：

  • 写错
  • 覆盖不足
  • 过时
  • 只验证局部行为

例如：

pytest
→ PASS

并不一定意味着：

Issue 已经解决。

它只意味着：

这些测试通过了。

因此 Coding Agent 仍然需要：

  • Review
  • Regression
  • Specification Understanding

这又与 Part 6 Evaluation 联系起来。

9.26 Coding Agent 的 Evaluation

现在我们回到最核心的 Agent Evaluation。

一个 Coding Agent 是否成功？

不能只说：

“测试通过了。”

应该至少考虑：

Issue Resolution

原始 Issue 是否真正解决？

Regression

旧功能是否被破坏？

Test Success

相关测试是否通过？

Diff Quality

是否产生大量无关改动？

Efficiency

用了多少：

  • Tool Calls
  • Tokens
  • Runtime

Human Intervention

中途需要多少人工帮助？

9.27 一个有趣的指标：Patch Size

假设两个 Agent 都解决了 Issue。

Agent A

修改：

2 files
15 lines

Agent B

修改：

17 files
1200 lines

两者测试都通过。

你会倾向哪个？

通常：

A。

因为它产生的变更范围更小。

这可以降低：

  • Review 成本
  • Regression 风险
  • Merge Conflict

所以：

Coding Agent 的“最小必要变更”本身就是一种工程质量。

9.28 Another Metric：Human Intervention

假设：

Agent A
完成 90% Issue
需要人工介入 3 次

Agent B
完成 88%
不需要人工介入

哪个好？

还是没有唯一答案。

取决于：

人工介入的成本。

例如：

自动修复测试代码。

可能不允许自动修改。

而：

内部低风险文档代码。

可能允许高度自治。

所以：

Coding Agent 也需要定义自己的自治边界。

9.29 Skill：为什么 Agent 不应该每次重新学习怎么工作？

假设我们经常做：

Python 项目 Bug 修复。

流程总是：

Search
 ↓
Read
 ↓
Run Tests
 ↓
Inspect Failure
 ↓
Patch
 ↓
Test

每一次都让模型从头决定这些步骤，可能很浪费。

于是可以形成：

Skill。

例如：

python_bug_fix

包含：

1. Inspect project structure
2. Locate relevant code
3. Read nearby tests
4. Reproduce issue
5. Make minimal patch
6. Run targeted tests
7. Run regression tests

于是：

Agent
+
Reusable Skills

可以提高稳定性。

9.30 Skill 和 Tool 的区别

Tool：

Agent 可以做什么。

例如：

read_file()
run_tests()
apply_patch()

Skill：

Agent 应该按照什么成熟流程使用这些能力。

例如：

debug_python_issue

它规定：

先查
→
再复现
→
再修改
→
再测试

所以：

Tool
= Capability

Skill
= Procedure

这是 Coding Agent 非常重要的一个概念。

9.31 Repository-level Skill

一个真正的企业代码库还可能拥有自己的规则：

代码风格
测试命令
Migration 流程
提交规范
安全规则
目录结构
API 兼容要求

这些规则可以形成：

Repository-level Instructions / Skills。

于是 Agent 进入仓库以后，不是：

“按自己的习惯改。”

而是：

遵守这个 Repository 的工程规范。

9.32 Context Compaction 在 Coding Agent 中为什么尤其重要？

假设 Agent 连续工作：

Read 20 files
Run 10 tests
Make 4 patches
Review 6 errors

Context 很快就会膨胀。

如果把所有：

  • 文件内容
  • Test Output
  • Diff
  • 历史决策

全部保留，模型会越来越难处理。

这时候必须做：

Compaction

保留真正重要的状态：

Current Issue
Modified Files
Current Hypothesis
Tests Passed
Tests Failed
Pending Work
Important Decisions

这就是 Part 2 Context Engineering 在 Coding Agent 中的直接应用。

9.33 Long-running Coding Agent

现在可以把所有能力组合起来。

假设 Issue 很复杂。

Agent 可能工作几个小时：

Understand Issue
 ↓
Search Repository
 ↓
Read Code
 ↓
Reproduce
 ↓
Modify
 ↓
Test
 ↓
Failure
 ↓
Repair
 ↓
More Tests
 ↓
Review

中途任务暂停。

第二天继续。

因此需要：

Task State
+
Checkpoint
+
Repository State
+
Artifacts

这就是：

Long-running Coding Agent。

9.34 Mini Coding Agent：我们的核心实验

现在正式开始这一 Part 的核心实验。学习 Coding Agent 的第一步不是把它放进你的真实业务仓库，而是在一个有明确契约、可以安全复现的受控仓库里观察它如何理解问题、定位代码、提交补丁并处理测试失败。配套 Lab 09 已经提供 fixture_repo/，不要用包含密钥、生产数据或个人文件的仓库替换它。

先阅读 labs/lab09_coding_agent/TASK.md 与 README.md。该任务要求修复重复提交订单时的幂等问题：相同 order_id 与相同 payload 应返回原订单；相同 ID 搭配不同 payload 应返回 HTTP 409。你要让 Agent 沿着 API route、Pydantic schema、service、repository、SQLAlchemy model 和测试找到根因，而不是照着 Issue 直接重写一大片代码。

先把现有测试当作证据，而不是把“所有测试一开始就通过”当成目标。先运行夹具测试，记录当前失败：

python -m pytest labs/lab09_coding_agent/fixture_repo/tests

当前夹具故意保留一个需要修复的失败：同一个 order_id 搭配不同金额时，底层唯一约束异常没有被正确转换成 HTTP 409。这是本实验的起点，不是测试设施随机失效。随后运行 Coding Agent Harness 及其自身契约测试：

python -m labs.lab09_coding_agent.src.run --mode fake
python -m pytest labs/lab09_coding_agent/tests

Fake 主线使用脚本化工具序列，把夹具复制到临时目录，在临时副本中展示定位、精确 Patch 和重新测试；它不会修改你工作区中的原始夹具。请审阅它的 Patch，再将经过审查的最小修复应用到自己的工作副本，并重新运行夹具测试，确认预期红测转绿。不要为了通过测试而删掉契约或移除数据库唯一约束。

只给 Agent：

请修复这个问题，并确保现有下单接口行为不变。”

同时提供：

9.36 Agent 第一阶段：Understand

它需要：

Read Issue
 ↓
Inspect Repository
 ↓
Find Order API
 ↓
Find Order Service
 ↓
Find Database Model
 ↓
Find Existing Tests

不能直接改代码。

9.37 Agent 第二阶段：Reproduce

尝试运行：

pytest tests/test_order.py

或者编写新的失败测试。

目标：

证明问题存在。

9.38 Agent 第三阶段：Plan

Agent 给出一个简短计划：

1. Add regression test for duplicate submission.
2. Inspect transaction / uniqueness behavior.
3. Implement minimal server-side protection.
4. Run targeted tests.
5. Run full regression suite.

注意：

Plan 不是让 Agent 写一篇长篇报告。

它是：

帮助自己管理任务。

9.39 Agent 第四阶段：Modify

Agent 使用：

read_file()
apply_patch()

只修改必要位置。

9.40 Agent 第五阶段：Test

pytest tests/test_order.py

如果：

PASS

继续。

如果：

FAIL

把错误放进 Context。

9.41 Agent 第六阶段：Repair

例如：

IntegrityError

Agent 重新分析。

发现：

只是应用层判断不够，数据库约束仍然缺失。

再修改。

重新测试。

这时候 Agent 已经不是：

“一次生成代码。”

而是在：

使用软件工程反馈循环。

9.42 Agent 第七阶段：Regression

目标测试通过之后：

pytest

运行完整测试集。

因为你不能只证明：

新功能正常。

还需要证明：

旧功能没有坏。

9.43 Agent 最终应该交付什么？

不是一句：

“Done。”

而应该产生：

Root Cause

Patch / Diff
Tests Added
Tests Passed
Regression Result
Remaining Risks

这样人类工程师才能 Review。

可选真实模型实验：观察 Coding Agent 的补丁质量

9.44 故障实验：我们主动让 Coding Agent 失败

核心实验必须包含 Failure。

Failure A：找错文件

让 Repository 存在多个相似实现。

观察 Agent 是否能够通过搜索继续定位。

Failure B：错误修改

让 Agent 第一次 Patch 故意无法通过测试。

观察：

它能否根据错误继续修复？

Failure C：测试命令错误

让 README 中存在多个测试入口。

观察：

Agent 是否能找到正确命令？

Failure D：依赖缺失

让某个测试需要额外环境。

观察：

Agent 是盲目重试，还是识别环境问题？

Failure E：权限问题

限制 Agent 修改某个目录。

观察：

Agent 如何处理 Permission Denied？

Failure F：测试全部通过，但 Issue 仍未真正解决

这是最重要的一个。

构造测试覆盖不足。

让：

pytest
→ PASS

但业务 Issue 仍存在。

然后观察：

Agent 有没有能力通过 Issue 理解发现问题？

这会让你真正理解：

Tests are evidence, not absolute truth.

9.47 Coding Agent 为什么会改变软件开发方式？

如果 Coding Agent 只能：

生成代码。

它只是一个：

更强大的代码补全工具。

但如果它能够：

Understand
+
Search
+
Edit
+
Test
+
Debug
+
Review

那么它开始影响的就不仅是：

写代码。

还包括：

  • Debugging
  • Refactoring
  • Testing
  • Documentation
  • Migration
  • Dependency Upgrade
  • Repository Maintenance

换句话说：

Agent 开始从“代码生成器”进入“软件工程协作者”的位置。

9.48 但不要把 Coding Agent 当成“可以替代程序员”

这是一个很重要的边界。

Coding Agent 很擅长：

局部修改
模式化任务
测试驱动修复
代码搜索
重复劳动

但真实的软件工程仍然需要：

Business Understanding
Architecture
Trade-offs
Risk
Ownership
Product Judgment

比如：

“这个功能到底应该存在吗？”

不是一个 Coding Agent 单纯靠代码仓库就能完全回答的问题。

又比如：

“为了性能应该选择最终一致性还是强一致性？”

这属于：

Architecture Decision。

因此：

Coding Agent 增强软件工程，不等于消灭软件工程。

转向：

这其实是 Coding Agent 最值得关注的地方。

9.50 一个新的 Engineering Unit：Task

传统软件开发经常以：

文件 / 函数 / 类

为最小工作单位。

Coding Agent 更自然的工作单位可能变成：

一个完整问题。

Search
Edit
Test
Repair

因此：

Coding Agent 的最小工作单位开始从“代码片段”向“工程任务”移动。

9.51 Task Quality 决定 Agent Quality

但任务描述如果非常模糊：

“优化一下订单系统。”

Agent 很难正确行动。

如果写成：

Agent 就拥有：

所以：

好的 Issue 本身就是 Agent Interface。

这个思想在未来的企业 Coding Agent 中会非常重要。

9.53 本 Part 最重要的几个认识

第一

Coding Agent 最重要的能力不是生成代码，而是理解 Repository。

第二

Tool 是 Agent 的手。

对于 Coding Agent 来说：

Search
Read

Test

第三

而可以得到：

真实执行结果。

第四

Sandbox 是 Coding Agent 的安全基础设施。

因为 Agent 已经拥有：

第五

Agent 应该产生：

Agent 越来越多地负责：
