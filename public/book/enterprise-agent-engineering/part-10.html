Part 10｜Multi-Agent Engineering：当一个 Agent 不再够用

多一个 Agent，并不意味着多一份能力。
很多时候，多一个 Agent 只是多了一份通信、多一份状态、多一份成本，也多了一种失败方式。

Part 9 展示了一个 Agent 如何在可审查的工程闭环中完成复杂任务。但任务复杂，并不自动说明应当拆成多个 Agent。拆分会增加消息协议、上下文同步、部分失败与协调成本；只有当不同角色确实需要不同能力、信息或权限时，这种成本才可能值得。

那么问题来了。

如果一个任务更复杂，我们是不是可以：

Agent
+
Agent
+
Agent

然后让它们一起工作？

答案当然是可以。

这就是 Multi-Agent。

但真正困难的问题不是：

“怎么创建多个 Agent？”

而是：

“为什么这个任务需要多个 Agent？”

再进一步：

“拆开以后，系统真的会变好吗？”

如果你回答不出这两个问题，那么 Multi-Agent 很可能只是：

把一个复杂系统拆成了更多复杂系统。

10.1 先从一个人能不能做开始

假设你有一个任务：“分析一份客户投诉，然后给出处理建议。”

一个 Agent 完全可以完成：

读取投诉
 ↓
查询客户信息
 ↓
检索政策
 ↓
分析
 ↓
给出建议

这时候，如果你突然设计：

Research Agent
Analysis Agent
Execution Agent

你首先应该问：

为什么？

如果一个 Agent 已经能稳定完成，那么拆成三个 Agent 很可能只会带来：

  • 更多模型调用
  • 更多 Context
  • 更多通信
  • 更高延迟
  • 更高成本
  • 更复杂的调试

这就是 Multi-Agent 最容易踩的第一个坑。

10.2 Multi-Agent 的真正价值不是“多个”

Multi-Agent 真正有价值的地方，通常来自：

分工。

而分工存在价值，是因为某些任务本身就具有：

  • 不同目标
  • 不同上下文
  • 不同工具
  • 不同权限
  • 不同执行节奏
  • 不同专业职责

例如：

Research Agent
负责寻找证据

Analysis Agent
负责分析证据

Execution Agent
负责执行动作

它们做的并不是同一件事。

所以一个非常重要的判断原则是：

只有当任务之间存在有意义的边界时，Multi-Agent 才有存在价值。

10.3 什么叫“有意义的边界”？

可以从几个角度看。

目标不同

例如：

Agent A
目标：找到所有相关资料

Agent B
目标：判断资料是否可信

上下文不同

例如：

Research Agent
需要大量网页和文档

Execution Agent
只需要结构化任务结果

如果强行让一个 Agent 保存全部信息：

如果强行让一个 Agent 保存全部信息，Context 会非常庞大。

拆开以后：

Research Context

和：

Execution Context

可以独立管理。

权限不同

例如：

Research Agent
只能 Read

Execution Agent
拥有 Write

这时候拆分本身就成为：

Security Boundary。

执行节奏不同

例如：

Research
运行 20 分钟

Validation
只需要几秒

Execution
需要人工审批

它们本身就不是同一种工作。

10.4 Single Agent 和 Multi-Agent 的第一条分界线

所以可以先形成一个非常简单的问题：

如果只使用一个 Agent，你会遇到什么真正的工程问题？

不要回答：“这样不够高级。”

也不要回答：“Multi-Agent 看起来更专业。”

必须是具体问题，例如：

  • Context 太大。
  • 权限无法隔离。
  • 任务可以高度并行。
  • 不同任务需要不同工具和策略。
  • 一个角色不应该同时负责调查和执行。
  • 任务之间天然具有明确边界。

如果说不出具体问题：

暂时不要拆。

10.5 Multi-Agent 与传统分布式系统其实非常像

作为后端工程师，你看到 Multi-Agent 以后，很容易发现一种熟悉感。

例如：

Service A
 ↓
Message
 ↓
Service B

和：

Agent A
 ↓
Message
 ↓
Agent B

结构上很像。

传统分布式系统会面对：

  • RPC
  • Message Queue
  • State
  • Retry
  • Timeout
  • Idempotency
  • Concurrency
  • Partial Failure
  • Distributed Tracing

Multi-Agent 同样会面对。

所以：

Multi-Agent Engineering，本质上越来越接近 Distributed Systems Engineering。

区别只是：

以前服务之间传递的是结构化程序数据；现在某些决策和协作逻辑也可能由模型参与。

10.6 第一种常见架构：Supervisor

最容易理解的是：

                 Supervisor
                     │
          ┌──────────┼──────────┐
          ↓          ↓          ↓
      Research     Analysis   Execution

Supervisor 负责：

Supervisor 负责：决定哪个 Agent 做什么。

例如用户提出：“分析这个异常订单并给出处理方案。”

Supervisor 可能决定：

先交给 Research Agent

Research Agent 完成以后：

再交给 Analysis Agent

Analysis 完成：

交给 Execution Agent

这和传统系统的：

这和传统系统的 Orchestrator。

非常类似。

10.7 Supervisor 的优点

这种架构很直观。

每个 Agent 都比较简单：

Research Agent
↓
专门研究

Analysis Agent
↓
专门分析

Execution Agent
↓
专门执行

而 Supervisor 管理整个过程。

优点包括：

  • 职责清晰
  • 权限容易划分
  • 工具集合可以缩小
  • Context 可以隔离
  • Agent 可以独立优化

10.8 Supervisor 的代价

但是问题马上来了：

Supervisor 自己也是一个 Agent。

它也需要：

  • 模型调用
  • Context
  • State
  • Tool
  • Evaluation

于是系统变成：

User
 ↓
Supervisor
 ↓
Agent A
 ↓
Supervisor
 ↓
Agent B
 ↓
Supervisor
 ↓
Agent C

模型调用次数可能快速增加。

所以：

Supervisor 的价值必须能够覆盖它本身的协调成本。

10.9 第二种架构：Planner / Worker

另一种常见方法是：

Planner
   ↓
Task 1
Task 2
Task 3
Task 4

然后：

Worker A
Worker B
Worker C
Worker D

分别执行。

例如：“研究四个竞争产品，然后做横向比较。”

Planner 可以分解：

Research Product B
Research Product C
Research Product D

然后四个 Worker 并行执行。

最后：

Aggregation Agent

负责综合。

10.10 为什么这个架构可能有价值？

关键是：

任务之间相对独立。

例如：

Research A
Research B
Research C
Research D

互相之间几乎不依赖。

那么如果串行执行：

A
 ↓
B
 ↓
C
 ↓
D

可能很慢。

如果并行：

      ┌→ A
      ├→ B
Task ─┼→ C
      └→ D

速度可能显著提高。

这时候：

Multi-Agent 的价值来自并行性。

而不是：“因为三个 Agent 比一个厉害。”

10.11 第三种架构：Peer-to-peer

还有一种方式：

Agent A
 ↔
Agent B
 ↔
Agent C

它们没有一个绝对的 Supervisor。

Agent 可以直接互相发送消息。

例如：

Research Agent
    ↓
Analysis Agent
    ↓
Research Agent

分析 Agent 发现：“资料不够。”

它又要求 Research Agent：“再找一些证据。”

这种方式更灵活。

但同时：

更难控制。

10.12 为什么 Peer-to-peer 很容易失控？

如果有：

A ↔ B
B ↔ C
C ↔ A

消息可能不断循环。

更复杂的是：

A → B
A → C
B → C
C → A

你很快需要考虑：

  • 消息协议
  • 消息去重
  • 超时
  • 循环检测
  • 状态一致性
  • 消息顺序

这已经非常接近：

分布式系统。

10.13 Message Passing：Agent 之间到底传什么？

这是 Multi-Agent 非常重要的问题。

最简单的做法是：

最简单的做法是：A 给 B 发一大段自然语言。

例如：“我觉得这个订单可能是物流问题，你去查一下。”

简单，但很难控制。

更成熟的方法是结构化消息：

{
  "task_id": "task-1001",
  "from": "research_agent",
  "to": "analysis_agent",
  "message_type": "evidence_bundle",
  "payload": {
    "order_id": 10001,
    "evidence": [
      {
        "source": "logistics",
        "fact": "no_update_72h"
      }
    ]
  }
}

这样：

Agent 之间开始拥有明确的通信协议。

这和 API / Event Schema 非常相似。

10.14 Agent Message 不是聊天消息

这是一个特别值得注意的概念。

用户和模型之间的：

用户和模型之间的对话消息。

与 Agent 之间的：

系统消息。

其实不是同一个东西。

用户可能说：“我的订单为什么没到？”

而 Agent A 给 Agent B 的消息更像：

Task ID
Evidence
Current State
Requested Action
Constraints

所以 Multi-Agent 中需要逐渐建立：

Agent-to-Agent Protocol。

10.15 Shared State：多个 Agent 看同一个状态

最简单的协作方式：

           Shared State
          /      |      \
         ↓       ↓       ↓
        A        B       C

例如：

{
  "task_id": "1001",
  "order_id": "10001",
  "investigation_status": "in_progress",
  "evidence": [],
  "decision": null
}

多个 Agent 都可以读取。

10.16 Shared State 的优点

优点：

  • 简单
  • 状态集中
  • 容易回放
  • 容易恢复

但也有问题：

谁可以修改？

如果：

Agent A

和：

Agent B

同时修改同一个字段，会发生什么？

这已经出现：

Concurrency Problem。

10.17 Shared State 的危险：谁拥有状态？

假设：

diagnosis = "battery_failure"

Analysis Agent 写入：

battery_failure

Research Agent 稍后写入：

charger_failure

最终：

最终：谁是正确的？

如果没有明确的：

如果没有明确的，Ownership。

系统就会很混乱。

因此 Shared State 需要：

Field Ownership
Update Rules
Conflict Resolution
Version
Timestamp
Source

这与传统分布式状态管理非常类似。

不是所有 Agent 都共享 Context。

而是：

Agent A
Context A
   ↓

   ↓

A 只传给 B：

例如：

        ↓

        ↓

这样可以减少：

也保护：

10.19 Shared Context 和 Independent Context 谁更好？

还是没有统一答案。

Shared Context

优点：

  • 信息完整
  • 实现简单

缺点：

  • Context 膨胀
  • 职责边界模糊
  • Agent 容易互相污染

Independent Context

优点：

  • 隔离
  • Context 更小
  • 权限清晰

缺点：

  • 需要消息设计
  • 信息可能丢失
  • 通信成本增加

所以：

Context Architecture 也是 Multi-Agent Architecture 的核心。

10.20 Concurrency：为什么 Multi-Agent 一定会遇到并发？

假设：

Research Agent 需要同时调查四个供应商。

四个任务完全独立。

那么最合理的方式可能是：

           Planner
              ↓
      ┌───────┼───────┐
      ↓       ↓       ↓
     A        B       C
      └───────┼───────┘
              ↓
          Aggregator

这就是并行。

但并行以后会出现：

  • 一个 Agent 快
  • 一个 Agent 慢
  • 一个 Agent 失败
  • 一个 Agent 返回脏数据

Aggregator 怎么办？

10.21 Partial Failure：不是所有 Agent 都会成功

假设：

A → SUCCESS
B → SUCCESS
C → TIMEOUT
D → SUCCESS

最终要不要继续？

可以选择：

Strict

C 失败，整体失败。

适合：

所有证据都必须齐全的任务。

Best-effort

C 失败，但 A/B/D 足够，继续。

适合：

适合：允许部分结果缺失的研究任务。

Retry

C 失败，重新执行。

适合：

适合：临时错误。

Alternative

C 失败，换另一个数据源。

适合：

适合：有替代能力。

这其实就是传统分布式系统的 Failure Semantics。

10.22 Failure Propagation：A 的错误会不会影响 B？

假设：

Research A
 ↓
Analysis B
 ↓
Execution C

如果 A 错了：

Wrong Evidence

那么 B 可能分析错。

然后 C 执行错。

最终：

一个早期错误沿着 Agent 链传播。

因此 Multi-Agent 不只是：“每个 Agent 自己做好自己的事情。”

而是需要考虑：

错误会怎样跨 Agent 传播？

10.23 Provenance：结果来自谁？

假设 Analysis Agent 得到：

结论：
这个设备最可能是电池问题。

那么必须知道：

这个结论来自哪些证据？

哪些证据由谁找到？

什么时候找到？

是否经过验证？

所以 Multi-Agent 中会逐渐需要：

Provenance。

也就是：

数据和结论的来源链。

10.24 为什么 Provenance 很重要？

尤其是企业环境。

如果 Agent 最终给出：“建议停机检修。”

工程师会问：

工程师会问：为什么？

如果系统能够回答：

Evidence 1:
Diagnostic API

Evidence 2:
Repair Manual v5

Evidence 3:
Historical Case #192

并且：

Research Agent
 → collected evidence

Analysis Agent
 → synthesized conclusion

那么整个系统更容易：

  • 审计
  • 调试
  • Review
  • 追责

10.25 Permission Boundary：Multi-Agent 一个非常实际的价值

考虑一个企业系统。

Research Agent

需要：

Search Web
Query Database

而：

Execution Agent

才拥有：

Create Ticket
Send Notification

那么拆成两个 Agent 以后：

那么拆成两个 Agent 以后权限边界天然更加清晰。

可以形成：

Research Agent
   ↓
Read Only

Analysis Agent
   ↓
Read Only

Execution Agent
   ↓
Write

这其实是 Multi-Agent 的一个非常现实、而且容易被忽略的价值：

Agent Isolation can be a Security Mechanism.

10.26 但是不要为了“安全”把每件事都拆成 Agent

例如：

Read Agent
Write Agent
Validate Agent
Notify Agent

如果每个都只做一两个非常简单的动作，

系统最后会变成：

Agent → Agent → Agent → Agent

而实际上一个：

Workflow + Permission

可能就够了。

所以：

隔离有价值，但隔离本身也有成本。

10.27 Multi-Agent 的成本会怎样增长？

假设一个 Agent 任务平均：

3 model calls

现在拆成三个 Agent：

Agent A = 3
Agent B = 3
Agent C = 3

已经是：

9 model calls

再加 Supervisor：

+ 2~3

再加验证：

+ 1~2

最后：

一个用户请求可能产生十几次模型调用。

所以：

Multi-Agent 往往是一个成本乘数器。

这也是为什么 Multi-Agent 必须经过 Evaluation。

10.28 一个重要公式

可以用一个非常粗略的工程思维模型：

Total Cost
≈
Σ Agent Model Cost
+
Coordination Cost
+
Retrieval Cost
+
Tool Cost

而：

Total Latency
≈
Critical Path
+
Coordination Overhead

如果任务可以并行：

如果任务可以并行，Latency 可能下降。

如果任务高度串行：

Multi-Agent 可能让 Latency 上升。

因此：

Multi-Agent 是否更快，取决于任务图，而不是 Agent 数量。

10.29 DAG：把 Multi-Agent 看成任务图

这时候，可以借用一个后端工程中很熟悉的思想：

这时候，可以借用一个后端工程中很熟悉的思想 DAG。

例如：

           Start
             ↓
       ┌─────┼─────┐
       ↓     ↓     ↓

10.50 Part 10 小结

这一 Part 我们表面上学习了：

  • Supervisor
  • Planner / Worker
  • Peer-to-peer
  • Shared State
  • Message Passing
  • Concurrency

但真正应该留下来的，不是这些名词。

而是下面这套思考方式。

第一

一个 Agent 能解决的问题，不要因为“可以多 Agent”就强行拆开。

第二

Multi-Agent 的价值来自真正的分工。

分工可以来自：

不同目标
不同 Context
不同 Tool
不同权限
不同执行节奏
并行性

第三

Agent-to-Agent 通信应该像 API / Event Protocol 一样被设计。

需要：

Schema
Ownership
Validation
Version
Trace

第四

Shared State 与 Independent Context 都有价值。

选择依据是：

信息共享需求和隔离需求之间的平衡。

第五

Multi-Agent 本质上开始接近分布式系统。

因此需要认真考虑：

Timeout
Retry
Idempotency
Concurrency
Partial Failure
Failure Propagation
Tracing
State Consistency

第六

Multi-Agent 必须有 Single Agent Baseline。

否则你无法证明：

否则你无法证明拆分产生了价值。

第七

Agent 的数量不是系统质量指标。

一个好的 Multi-Agent 系统不是：“我有 20 个 Agent。”

而是：

“我能解释为什么这 3 个 Agent 是必要的，而且为什么其他部分不需要拆。”
