Part 1｜把 LLM 当成一个真正的软件组件

Agent 不是从 Agent Framework 开始的。
Agent 的起点，是你第一次认真地把一个 LLM 当成系统中的软件依赖。

1.1 先把已经选中的 LLM 机会工程化

Part 0 已经讨论过何时需要 AI、何时不需要 Agent。这里先假设机会评估得出了一个有限结论：某类客服工单适合用 LLM 分类并提取字段，但整个流程仍由普通后端程序控制。

客服工单 → LLM 分类与提取 → 结构校验 → 业务系统

这个任务不需要先引入 Agent Loop。它需要的是一个可靠的模型调用边界：输入怎么组织、输出如何校验、超时和限流怎么处理、调用情况怎样记录，以及失败时业务系统应该收到什么结果。

这正是本 Part 的目标：把不完全确定的远程计算依赖，封装成行为可观察、失败可处理、结果可验证的软件组件。后面讨论 Context 与 Agent 时，我们会复用这层基础，而不是从头再造一次 API 客户端。

1.2 LLM API 看起来像函数，实际上不是函数

先看一个最简单的程序。

result = add(1, 2)

你大概知道：

输入
1, 2

输出
3

然后再看：

result = model.generate("帮我总结这段文本")

代码形式非常像。

但工程性质完全不同。

我们先不要管模型内部到底怎么计算，只看应用层。

你的程序其实是在发送：

Request
   ↓
Remote Model Service
   ↓
Response

也就是说，LLM 更接近：

一个远程计算服务。

而且这是一个特殊的远程计算服务：

  • 有网络延迟
  • 可能失败
  • 有调用成本
  • 输出可能变化
  • 输入受到上下文限制
  • 不同模型能力不同
  • 同一个任务可能存在多个合理答案

于是，一个很重要的思维模型就出现了：

传统函数

input
  ↓
function
  ↓
output

而 LLM：

request
  ↓
network
  ↓
model service
  ↓
probabilistic computation
  ↓
response

你作为后端工程师，应该立刻想到：

那么它是不是应该像其他远程服务一样，被封装起来？

答案是：

应该。

而且这恰恰是 AI Application Engineering 开始真正“像工程”的地方。

1.3 第一个问题：模型到底接收什么？

当你第一次调用 LLM API 时，最容易犯的错误是把模型理解成：

prompt → answer

实际上，应用层真正发送的通常是一组结构化消息。

例如：

{
  "messages": [
    {
      "role": "system",
      "content": "你是一名客服分类助手。"
    },
    {
      "role": "user",
      "content": "我的快递三天没有更新了。"
    }
  ]
}

这里至少存在两个概念：

  • role
  • content

你暂时可以把它理解成：

模型不是只看到“一个字符串”，而是在特定上下文中看到一组有角色的消息。

角色信息为什么重要？

假设你这样写：

请判断下面内容属于哪类问题：
用户说：“物流三天没更新。”

和：

system:
你负责客服分类。

user:
物流三天没更新。

从人的角度看，它们都在表达同一件事。

但对于模型系统来说，消息结构本身就是输入的一部分。

这也是为什么后面我们会不断回到一个词：

Context。

现在你不需要马上掌握 Context Engineering。

你只需要记住：

模型最终做什么，取决于你给它什么输入，而这个输入远不只是用户最后打出的那句话。

1.4 Token：为什么一句话不是“一句话”？

如果你以前没有接触过 LLM，第一次看到 token 时，可能会觉得：

“为什么模型不用字符数或者字数计算？”

因为模型实际处理的，并不是我们平常理解的“单词”或者“汉字”。

模型会把输入文本转换成某种 token 序列。

因此：

文本长度

和：

Token 数量

并不是简单的一一对应关系。

这件事情为什么重要？

因为你以后会发现三个非常现实的问题。

第一，模型通常存在上下文容量限制。

第二，模型调用成本往往和输入、输出 token 有直接关系。

第三，输入越长，不一定越好。

例如：

输入 500 tokens

和：

输入 50,000 tokens

当然可能表达更多信息。

但第二种方式也意味着：

  • 更高成本
  • 更高延迟
  • 更复杂上下文
  • 更大的信息污染风险

所以以后看到：

“把所有历史记录全塞进去。”

不要觉得这是最稳妥的方案。

很多时候，恰恰相反。

1.5 一个你很快会遇到的问题

假设你的客服 Agent 需要分析一个工单。

用户可能提交：

“车昨天开始充电特别慢，我已经换过两个充电桩，还是一样，而且之前从来没有出现过这种情况。”

然后系统还需要补充：

车辆型号
电池状态
最近故障记录
最近维修记录
充电记录

于是你的输入慢慢变成：

Instructions
+
User Message
+
Vehicle Information
+
Battery Information
+
Historical Records
+
Business Rules

这时候你就会发现：

模型收到的东西，正在越来越多。

这就是为什么以后我们会专门学习：

Context Engineering。

Part 1 只需要建立一个意识：

LLM 的输入是有预算的。

不要把 Context 当成免费的。

1.6 输出也不是“随便返回一个字符串”

再来看一个非常典型的后端需求。

我们希望模型把客服工单分类成：

物流
商品
退款
其他

同时提取：

order_id
customer_name
priority

初学者很容易做成：

result = model.generate(prompt)

然后直接：

save_to_database(result)

问题是：

result 究竟是什么？

它可能返回：

物流

订单号：10001
客户：张三
优先级：高

也可能返回：

{
  "category": "物流",
  "order_id": 10001,
  "customer_name": "张三",
  "priority": "high"
}

甚至：

好的，这个问题应该属于物流类。
订单号看起来是 10001，优先级比较高。

如果你的数据库期待：

TicketClassification(
    category="物流",
    order_id=10001,
    customer_name="张三",
    priority="high",
)

那么显然：

自然语言输出并不适合作为业务系统的稳定接口。

于是我们需要一个新的概念：

Structured Output

1.7 从自然语言进入结构化世界

想象一下：

你让一个同事帮你处理一批工单。

如果你只是告诉他：

“帮我看看这些工单。”

每个人可能都会给出不同格式的结果。

但如果你明确规定：

category: 物流 / 商品 / 退款 / 其他
order_id: integer | null
customer_name: string | null
priority: low / medium / high

事情就完全不同了。

这就是 Schema。

在程序世界里，我们可以进一步使用：

from pydantic import BaseModel
from typing import Literal


class TicketClassification(BaseModel):
    category: Literal["物流", "商品", "退款", "其他"]
    order_id: int | None
    customer_name: str | None
    priority: Literal["low", "medium", "high"]

现在我们的系统可以变成：

User Text
   ↓
LLM
   ↓
Structured Output
   ↓
Pydantic Validation
   ↓
Business Object
   ↓
Backend Logic

这一步特别重要。

因为它第一次建立了：

AI 世界和传统软件世界之间的接口。

LLM 负责：

从自然语言中提取和判断。

Pydantic / Schema 负责：

把结果约束成程序能够可靠处理的结构。

业务系统负责：

决定下一步怎么执行。

三者职责开始分离。

1.8 为什么 Schema 是 AI Engineering 的重要工具？

想象一个没有 Schema 的 AI 系统。

LLM
 ↓
自然语言
 ↓
业务代码自己猜怎么解析

这会非常脆弱。

再看：

LLM
 ↓
Schema
 ↓
Validation
 ↓
Business Object

此时系统多了一道边界。

例如模型返回：

{
  "category": "logistics",
  "order_id": "10001",
  "priority": "urgent"
}

Schema 校验可能马上发现：

priority 不在允许范围

于是系统可以：

  • 拒绝
  • 重试
  • 修复
  • 降级
  • 请求人工处理

而不是：

把一个奇怪的数据直接写入生产数据库。

这其实和传统后端的很多思想非常相似。

你以前会校验：

amount > 0

现在只是多了一个新的边界：

AI Output Validation。

1.9 这时候你应该想到 Retry 了

现在假设模型偶尔返回一个无法解析的结果。

作为后端工程师，你通常不会说：

“服务器有时候报错很正常。”

你会考虑：

  • Retry
  • Timeout
  • Backoff
  • Fallback

LLM 也一样。

例如：

Request
   ↓
Model
   ↓
Malformed Output
   ↓
Validation Failed
   ↓
Retry / Repair

但是这里有一个很重要的问题：

什么时候重试是合理的？

假设模型输出格式错误。

可以考虑重试。

如果是网络超时。

也可以重试。

如果服务端暂时繁忙。

可能也可以重试。

但如果模型连续三次都无法完成这个任务：

Attempt 1 → wrong
Attempt 2 → wrong
Attempt 3 → wrong

继续无脑重试可能只是：

增加成本，而不是增加正确率。

所以 AI 系统里的 Retry 也不能照搬传统数据库 API 的思路。

以后你会发现：

Retry 本身也应该被 Evaluation。

1.10 Timeout：最容易被忽略的生产问题

本地 Demo 最容易给工程师制造一种错觉：

“调用模型，好像也就几秒。”

但一旦上线，模型调用就可能出现：

100 ms
800 ms
2 s
5 s
10 s
...

甚至失败。

假设你的接口：

POST /ticket

同步调用 LLM。

如果：

Frontend Timeout = 10s
Backend Timeout = 30s
LLM Timeout = 60s

那么你的系统设计其实已经存在明显的问题。

用户已经放弃等待了。

后端还在等模型。

所以：

LLM 的延迟必须被当成系统设计的一部分，而不是调用细节。

这会进一步影响：

  • API timeout
  • async task
  • queue
  • streaming
  • background worker
  • fallback

这些概念会在后面逐渐展开。

现在你只需要形成一个感觉：

LLM 是一个慢而且可能失败的远程依赖。

1.11 Streaming：为什么有时候用户感觉“更快了”？

假设模型最终会生成：

“根据订单状态和物流信息……”

如果你等到全部生成完再返回：

Request
       ↓
[ 等待 5 秒 ]
       ↓
Complete Response

用户会感觉：

“这个系统好慢。”

如果模型支持逐步发送输出，那么用户可能看到：

Request
 ↓
“根据订单状态……”
 ↓
“根据订单状态和物流信息……”
 ↓
“目前订单已经发出……”

即使完整响应总耗时没有变化，用户也会觉得：

“系统开始工作了。”

因此，Streaming 不只是一个 UI 技巧。

它其实涉及：

系统响应模型。

你需要开始区分：

Time to First Token

和：

Time to Complete Response

这两个指标以后都会影响 AI Application 的设计。

1.12 模型不是一种商品，而是一组能力

到现在为止，我们还可以假设：

“模型就是模型。”

但真正开始做工程以后，你很快会发现：

不同模型可能在不同任务上表现不同。

例如一个模型：

  • 长文本很好
  • 工具调用不错
  • 成本比较高

另一个模型：

  • 分类已经足够准确
  • 成本更低
  • 延迟更低

第三个模型：

  • 复杂推理更强
  • 但普通提取任务完全没必要使用

所以一个成熟的 AI Application 不应该在业务代码里到处写：

call_specific_model_xxx(...)

否则以后业务逻辑会被模型供应商和模型名称绑死。

1.13 给模型加一层抽象

你可能已经在后端系统里见过类似设计。

例如：

PaymentService

下面可以有：

AlipayAdapter
WechatPayAdapter
StripeAdapter

上层业务只关心：

payment_service.pay(...)

而不是：

stripe_create_payment(...)

LLM 也可以采用类似思想：

Application
     ↓
Model Interface
     ↓
Provider Adapter
 ┌─────┼─────┐
 ↓     ↓     ↓
Model A Model B Model C

例如定义一个最小接口：

class ModelClient:
    def generate(...):
        ...

上层业务不关心具体是哪一家 Provider。

这里不是要求你现在就建立一个巨大抽象层。

恰恰相反：

抽象的目标不是为了“看起来架构高级”，而是为了保护业务系统。

如果你只有一个模型、一个项目、一个调用点，那么简单封装就足够。

如果未来有：

  • 多 Provider
  • 多模型
  • Fallback
  • Routing
  • Cost Optimization

那么抽象层的价值会越来越明显。

1.14 成本：为什么“效果更好”不是唯一目标？

假设有两个模型。

Model A
准确率：90%
成本：1

Model B
准确率：92%
成本：10

你会选哪个？

很多人第一反应是：

Model B。

因为 92% 更高。

但是如果一个业务每天调用 100 万次：

A：
1 × 1,000,000

B：
10 × 1,000,000

成本差距就非常明显。

更重要的是：

如果 Model A 已经满足业务目标，

那么为了多获得几个百分点的准确率支付十倍成本，

可能根本不是一个好的工程选择。

所以 AI Application Engineering 开始出现新的优化目标：

Quality
+
Cost
+
Latency
+
Reliability

而不是只有：

Quality

1.15 一个很有意思的工程问题

假设一个 Agent 会连续调用三次模型：

Model Call 1
      ↓
Model Call 2
      ↓
Model Call 3

那么单次调用成本不是总成本。

粗略地说：

Total Cost
≈
Σ Model Cost
+
Tool Cost
+
Retrieval Cost
+
Infrastructure Cost

同样：

Total Latency

也可能来自：

Model
+
Network
+
Tool
+
Database
+
Retrieval
+
Serialization

这就是为什么：

后面学习 Agent 时，我们绝不能只盯着模型 Prompt。

Agent 是一个系统。

1.16 实验：把一个后端 API 变成 AI Application

现在我们终于开始动手。

假设你已有一个：

POST /ticket

请求：

{
  "text": "我的订单已经三天没有物流更新了"
}

你需要增加一个 AI 能力：

classify_ticket

让系统返回：

{
  "category": "物流",
  "priority": "high",
  "summary": "订单物流三天没有更新"
}

第一步：最小版本

先只做：

API
 ↓
LLM
 ↓
Text Output

不要急着优化。

先让它跑起来。

第二步：Structured Output

增加：

JSON Schema
 ↓
Pydantic
 ↓
Validation

第三步：Timeout

给模型调用增加：

Request Timeout

第四步：Retry

仅对明确可恢复的错误进行有限重试。

第五步：Logging

记录：

request_id
model
latency
input_tokens
output_tokens
status
error

第六步：Cost Tracking

根据调用结果记录：

input tokens
output tokens
estimated cost

不需要一开始就做复杂计费系统。

我们首先要培养的是：

可观测意识。

在把系统故意弄坏之前，先为这个最小版本建立一个可重复的基线。配套仓库中的对应实验是 labs/lab01_llm_api/。先阅读其中的 TASK.md，确认要实现的接口契约，再阅读 README.md 了解真实运行边界。主线不要求 API Key：

python -m labs.lab01_llm_api.src.run --mode fake
python -m pytest labs/lab01_llm_api/tests

第一条命令让你观察确定性工程路径是否按契约输出；第二条命令检查格式错误、超时、重试等边界。之后再执行本节的 Failure Lab，把超时或无效输出变成可以复现的输入。

可选真实模型实验：观察当前 Provider 行为

这条轨道不是主线的前置条件。只有在已经配置并获准使用 Provider、确认输入不包含未授权的敏感业务数据、了解调用费用与数据处理条件后，才执行。它用于观察当前模型在指定配置下的实际表现，不替代离线契约测试，也不能单独证明生产质量。

python -m labs.lab01_llm_api.src.run --mode real

运行前先按本书的公共实验手册配置 AI_BASE_URL、AI_API_KEY 与 AI_MODEL。保留实际报告和失败案例，不要把 Fake 返回值当成模型质量结果，也不要将缺失的 usage/cost 填成零。推荐交付 part01-report.md：记录输入条件、接口契约、失败样例、重试行为、指标已知性，以及这次实验能够支持和不能支持的结论。

1.19 一个非常重要的转变

到这里，你已经可以回头重新看待：

response = model.generate(...)

这行代码。

以前你可能把它理解成：

“调用 AI。”

现在应该把它理解成：

“调用一个可能慢、可能失败、有成本、输出存在不确定性的远程计算服务。”

这两个理解看起来差别不大。

实际上，它们决定了完全不同的代码质量。

1.20 练习：自己设计一个 AI Backend Endpoint

现在选择一个你比较熟悉的后端功能。

1.22 现在重新回答一个问题

AI Application Engineer 和普通后端工程师有什么区别？

1.23 为什么我们现在还不能直接做 Agent？

你可能已经发现，我们目前已经拥有：

LLM
Structured Output
Timeout
Retry
Logging
Cost Tracking

那么：

Agent 还差什么？

答案其实很有意思。

差的不是“更大的 Prompt”。

也不是“更高级的模型”。

而是：

模型开始参与决定下一步应该做什么。

比如：

用户：
帮我看看订单 10001 为什么还没发货。

系统可能先调用：

query_order()

然后发现：

订单已经出库。

于是模型决定：

那我下一步需要查询物流。

再调用：

query_logistics()

然后根据物流结果继续判断。

现在系统开始出现：

Decision
 ↓
Action
 ↓
Observation
 ↓
Decision
 ↓
Action

这才是真正走向 Agent 的地方。

本 Part 小结

如果你认真完成了这一部分，你应该已经建立了几个非常重要的工程习惯。

第一：

LLM 是软件系统中的一个组件，不是整个系统。

第二：

LLM 调用应该像远程依赖一样被管理。

第三：

自然语言输出不能直接等价于业务对象。

第四：

Structured Output + Validation 是连接 AI 与传统软件的重要边界。

第五：

Latency、Cost、Failure 都是 AI Application 的一部分。

第六：

模型应该被抽象为一种可替换的计算能力，而不是写死在业务代码里的供应商 API。

第七：

一个 AI Demo 能运行，不等于它已经是一个工程系统。

而你现在已经站在 Agent 的门口了。
