Part 2｜Context Engineering：决定模型到底能看到什么

一个模型“知道什么”，和它“这一次到底看到了什么”，是两件完全不同的事情。

Part 1 解决了调用边界：请求能够发出去，返回值也经过结构校验。但接口正常不代表模型在每次决策时都获得了真正需要的信息。

现在假设服务本身没有报错，用户却仍然遇到一个问题。

用户说：“我前面已经告诉你了，我的车是 2024 款双电机版本，为什么你又问我车型？”

你查看日志。

发现用户明明说过。

模型也明明收到了对话历史。

甚至那句话就在上下文里。

可是模型还是没有使用。

于是你开始修改 Prompt：“请注意，一定要记住用户已经提供的信息。”

还是不稳定。

你继续修改：“不要重复询问用户已经提供的信息。”

似乎好了一点。

但过了一段时间，对话变长以后，问题又出现了。

这时候，你开始怀疑：“是不是模型的记忆能力不行？”

但很多时候，真正的问题并不是“模型不会记”。

而是：

你给模型的 Context 本身就没有被设计好。

这就是这一 Part 要解决的问题。

2.1 模型到底看到了什么？

这是整个 Part 2 最值得你反复思考的问题。

当用户说：“帮我看看订单为什么还没发货。”

你可能认为模型看到的只是：

帮我看看订单为什么还没发货。

但实际上，一个真实的 AI Application 在调用模型时，可能已经构造了这样的输入：

System Instructions

+
User Message

+
Conversation History

+
Current User Profile

+
Relevant Business Data

+
Retrieved Documents

+
Previous Tool Results

+
Current Task State

也就是说：

模型的输入不是“用户说的话”，而是整个 Context。

你可以把它理解成：

Context
├── Instructions
├── User Input
├── History
├── Retrieved Knowledge
├── Tool Results
├── State
└── Memory

最后这些信息一起进入模型。

因此，如果模型做错了，你真正应该问的问题不是：“模型为什么不知道？”

而是：

“在它做出这个决定的那一刻，它到底看到了什么？”

这个问题一旦建立起来，很多看起来神秘的 Agent 问题都会开始变得非常普通。

2.2 “知道”与“看到”是两回事

这是理解 Context 最重要的一步。

假设模型本身具有丰富的通用知识。

这并不意味着：

它知道你公司的内部规则。

例如，你问：“按照我们公司的报销制度，这种费用能不能报？”

如果公司的报销制度从来没有进入 Context，那么模型即使再强，也不能凭空知道你们公司的内部规定。

因此：

Model Knowledge

和：

Contextual Information

必须分开。

可以简单理解成：

Model
= 它原本具备的能力

Context
= 你这一次告诉它的东西

而一次具体任务的结果，通常取决于两者共同作用：

Model Capability
        +
Task Context
        ↓
Current Behavior

所以很多时候，一个 Agent 表现不好，并不意味着：“换一个更强的模型。”

可能只意味着：

你没有给当前任务构造出合适的 Context。

2.3 为什么把信息全部塞进去也不是好办法？

这是很多初学者非常自然的想法：“既然模型可能缺信息，那我就把所有东西全部给它。”

于是一个用户的问题进入系统以后，Context 变成：

用户基本信息
+
全部历史对话
+
全部订单
+
全部维修记录
+
全部客服记录
+
全部政策
+
全部产品资料
+
所有 Tool 描述
+
所有之前的 Tool Result

从直觉上看，这似乎非常稳妥。

因为：“反正信息都在里面。”

但很快你会发现，这种做法存在至少三个问题。

第一，成本越来越高

Context 变长以后，输入 token 增加。

输入 token 增加以后：

输入 token 增加以后调用成本可能增加。

第二，延迟越来越高

更长的输入意味着更多数据需要经过模型处理。

对于一个实时交互系统来说：更大的 Context 往往意味着更大的响应压力。

第三，信息可能开始互相干扰

这是最容易被忽略的问题。

假设用户当前的问题是：“为什么我的车今天无法充电？”

你真正需要的可能只是：

当前车辆型号
当前故障码
最近充电记录
最近一次维修记录
相关维修手册

但是你把过去三个月所有聊天记录都塞进去了。

其中有大量：

  • 无关闲聊
  • 旧车辆信息
  • 已经解决的问题
  • 过期维修记录
  • 很久以前的用户偏好

这些信息虽然“正确”，但并不一定：

与当前任务相关。

于是 Context 出现了一个非常重要的问题：

相关信息不足和无关信息过多，都可能导致错误

这就是 Context Engineering 与简单“堆 Prompt”之间的区别。

2.4 Context Engineering 到底在工程上做什么？

如果把 Context 理解成：

模型这次做决策时可以看到的信息集合。

那么 Context Engineering 做的事情其实很像数据库查询优化。

你不是把数据库里的所有表都返回给前端。

你会：

  • 查询
  • 过滤
  • 排序
  • 聚合
  • 投影
  • 分页

Context 也一样。

可以建立一个非常实用的流程：

Raw Data
   ↓
Select
   ↓
Filter
   ↓
Transform
   ↓
Prioritize
   ↓
Compress
   ↓
Inject
   ↓
Model

因此：

Context Engineering 的核心，不是“往 Prompt 里加什么”，而是“在当前任务里，应该让模型看到什么”。

2.5 一个后端工程师非常熟悉的类比

想象你有一张订单表：

orders

有一千万行数据。

现在用户查询：“帮我查订单 10001。”

你显然不会这样做：

SELECT *
FROM orders;

然后把一千万条订单全部返回。

你会：

SELECT ...
FROM orders
WHERE order_id = 10001;

因为你知道：

信息越多，不代表查询结果越好。

Context 其实也存在类似的问题。

错误的方法：

所有对话
+
所有知识
+
所有 Tool
+
所有数据

更合理的方法：

当前任务
   ↓
确定需要什么
   ↓
只取相关信息

这就是一个非常好的工程类比：

Context Engineering，本质上是在做“面向模型的查询优化”。

当然，Context 比数据库查询更复杂，因为“什么信息相关”本身可能就需要模型参与判断。

但这个类比足够帮助你建立第一层直觉。

2.6 Conversation History：是不是把所有聊天记录都保存下来就行？

现在来看最常见的一类 Context：

Conversation History。

假设用户和 Agent 的对话：

用户：我的车充电很慢。
助手：请提供车型。
用户：2024 款双电机。
助手：最近有没有更换充电桩？
用户：换过两个，都一样。
助手：有没有故障码？
用户：有，P0XXX。

如果对话只有六轮，那么：

如果对话只有六轮，那么，全部保存下来很容易。

于是：

History
   ↓
Append Current Message
   ↓
Send to Model

似乎就解决了。

但假设对话变成了：

10 turns
50 turns
100 turns
500 turns

你会马上遇到问题。

2.7 最简单的方法：Full History

策略非常直接：

每次请求
=
全部历史消息
+
当前消息

例如：

Turn 1
Turn 2
Turn 3
...
Turn 100

全部发送。

这个方法有一个非常大的优点：

简单。

对于短对话，往往也是最容易实现的起点。

但是随着对话变长，它会变得越来越昂贵。

更关键的是：

有些历史信息实际上已经失去价值。

例如用户在第 3 轮说：“我现在在公司楼下。”

到第 80 轮讨论电池故障的时候，这句话大概率已经不重要了。

而用户在第 7 轮说：“车型是 2024 款双电机。”

这可能几十轮以后仍然非常重要。

所以：

历史消息的重要性不是均匀的。

2.8 Sliding Window：只保留最近几轮

最简单的优化就是：

只保留最近 N 轮

例如：

最近 10 turns

那么：

Turn 1 ~ 90
     ↓
丢弃

Turn 91 ~ 100
     ↓
保留

这样做的优点非常明显：

  • Context 可控
  • Token 可控
  • 实现简单

但是马上会出现一个问题：

但是马上会出现一个问题：如果第 10 轮有一条非常重要的信息，而现在已经到了第 100 轮怎么办？

例如：

第 7 轮：

车型：2024 款双电机

100 轮以后，被窗口策略丢掉了。

于是模型又开始问：“请提供车型。”

用户非常生气：“我不是早告诉你了吗？”

这时候你会发现：

“最近的信息”不等于“最重要的信息”。

2.9 Summary：把旧历史压缩成摘要

那么我们可以换一种思路。

不要保存所有历史原文。

而是把旧历史总结成：

用户：
2024 款双电动车主

当前问题：
充电速度明显下降

已尝试：
更换两个充电桩

已发现：
存在 P0XXX 故障码

当前状态：
等待电池诊断结果

这样原来 80 轮的信息，就变成了一小段结构化状态。

这就是 Summary。

它解决了：

如何减少 Context 大小。

但 Summary 也带来一个风险：

但 Summary 也带来一个风险摘要本身可能丢失信息。

比如原对话里有：“第一次故障发生在 10 月 3 日晚 9 点 15 分。”

摘要可能写成：“近期发生故障。”

如果这个时间后来非常重要，就会丢失。

因此：

压缩并不等于简单地总结得越短越好。

真正的问题是：

哪些信息必须保留？

2.10 Structured State：比摘要更进一步

在很多复杂 Agent 中，你其实不一定需要把所有历史信息变成自然语言摘要。

可以把重要状态直接结构化。

例如：

class VehicleTaskState(BaseModel):
    vehicle_id: str
    model: str | None
    fault_codes: list[str]
    charging_issue: str | None
    attempted_actions: list[str]
    pending_actions: list[str]
    diagnosis_status: str

这样系统运行以后：

Conversation
        ↓
Extract Important Facts
        ↓
Structured State

以后模型需要 Context 的时候：

Structured State
        ↓
Context Builder
        ↓
Model

这时你已经开始做一件非常重要的事情：

把“聊天记录”与“任务状态”分开。

2.11 History 和 State 不是一回事

这个区别值得单独记住。

假设用户说：“我昨天已经重启过设备了，还是不行。”

这是：

Conversation History。

但是系统真正关心的可能是：

restart_attempted = true

这就是：

这就是：Task State。

两者可以同时存在。

Conversation History
=
发生过什么

State
=
当前系统认为什么是重要事实

更进一步：

History
=
原始事件

State
=
当前任务的结构化表示

如果你做过分布式系统或者状态机，这个概念应该很熟悉。

你不会让所有历史日志直接承担“当前状态”的职责。

同样：

你也不应该让聊天记录承担所有 Agent State 的职责。

2.12 一个很关键的设计原则

可以把 Context 看成一个“视图”。

数据库里的原始数据可能很多。

但：

当前请求需要的，只是其中一部分。

所以：

Source of Truth
      ↓
Application State
      ↓
Context Builder
      ↓
Model Context

这意味着：

Context 不应该天然等于数据库，不应该天然等于完整历史，也不应该天然等于 Memory。

Context 是：

为了当前决策而构造出来的输入视图。

这是整个 Part 2 最核心的概念之一。

2.13 Memory 又是什么？

现在问题进一步复杂了。

假设一个用户连续使用你的 Agent 一个月。

第一天他说：“以后回复我时尽量简洁一点。”

第七天他说：“我是做电池测试的工程师。”

第二十天他说：“我通常需要先看诊断数据，再看维修建议。”

这些信息如果每次都从头开始重新解释，非常低效。

于是我们可能希望系统“记住”。

这就是 Memory。

但 Memory 不应该简单理解成：“把全部历史对话永久保存下来。”

因为那样得到的只是一个越来越大的聊天记录。

真正的 Memory 需要回答：

什么值得长期保存？

例如：

User Preference
    → concise responses

User Profile
    → battery test engineer

Long-term Task Preference
    → diagnostics before repair recommendation

这些东西可能比某一天的闲聊更值得保留。

所以：

Memory 是经过筛选、整理和长期管理的信息，而不是简单的 History。

2.14 Memory、History、State、RAG：把它们的关系区分开

这几个词经常被混在一起，但它们并不处于同一个概念层级。

History

已经发生过的对话或事件记录。

例如：

用户昨天报告过同一个故障。

State

应用维护的权威当前任务或业务状态。

例如：

repair_status = "waiting_for_battery_data"

Memory

经过筛选和治理、可能在后续任务中复用的信息。

例如：

用户偏好先看原始诊断数据。

Knowledge Retrieval（RAG）

RAG 不是一份与 History 或 State 同类的信息。它是一条从外部知识源检索候选证据、再把相关证据提供给当前任务的处理路径。

例如，检索操作手册后得到“维修手册第 43 页”的相关段落。文档是知识来源；检索与排序是 RAG 路径；返回的段落才可能进入当前 Context。

一次模型调用的 Context，可能由以下材料组装而成：

Current User Input
+ Relevant History
+ Authoritative State Snapshot
+ Eligible Memory
+ Retrieved Evidence (via RAG)
+ Tool Results
+ Instructions

这些材料并不一定全部出现，也不应该不加筛选地全部塞入模型。应用需要为当前任务选择合适的信息、验证来源，并在必要时保留出处。

因此请记住：Context 描述当前决策给模型看的输入视图；State 是权威当前状态；Memory 是经治理的信息；RAG 是获取外部证据的路径。它们有关联，但并非同一维度的“信息来源”。

2.15 Context Construction：真正开始工程化

现在我们可以正式把 Context 构建过程工程化。

假设用户问：“这个故障为什么还没解决？”

Context Builder 可以做：

第一步：当前问题

保留：

这个故障为什么还没解决？

第二步：Task State

加入：

fault_code = P0XXX
diagnosis_status = waiting
vehicle_model = 2024_dual_motor

第三步：Memory

加入：

user_role = battery_test_engineer

第四步：Relevant History

只保留：

最近与当前故障相关的几轮

第五步：RAG

检索：

P0XXX 对应维修手册

第六步：Tool Results

加入最新诊断结果。

最后构造成：

System Instructions
       +
Current User Input
       +
Task State
       +
Relevant History
       +
Memory
       +
Retrieved Knowledge
       +
Tool Results
       ↓
      LLM

这就开始真正像一个：

Context Pipeline。

2.16 不要把 Context Builder 写成一个巨型字符串

最初你可能会这样写：

prompt = f"""
你是一个售后助手。

用户信息：
{user_info}

历史：
{history}

维修记录：
{repair_records}

知识库：
{documents}

当前问题：
{user_question}
"""

短期看没有问题。

但系统一复杂，这个函数会迅速变成一个灾难。

因为你根本不知道：

  • 哪些数据是必须的？
  • 哪些数据是可选的？
  • 为什么放进去？
  • 哪些数据已经过期？
  • 哪些数据和当前任务无关？

所以更成熟的思路是拆开：

context = ContextBuilder(
    instructions=...,
    state=...,
    history=...,
    memory=...,
    retrieval=...,
    tool_results=...,
).build()

然后每一个来源都有自己的策略。

2.17 一个非常重要的问题：相关性

假设你的系统拥有 10000 条历史维修记录。

用户当前只问：“P0XXX 这个故障码通常意味着什么？”

你显然不应该把 10000 条全部塞进去。

需要先做：

Query
 ↓
Retrieve Candidate Records
 ↓
Rank
 ↓
Select Relevant Records
 ↓
Context

这其实已经非常接近数据库查询和搜索系统的思想。

所以后面你会发现：

RAG 并不是一个孤立的“向量数据库技术”。

它实际上是：

Context Construction 的一个重要组成部分。

2.18 Context Budget：每一块 Context 都应该有预算

假设模型允许非常大的上下文。

我们仍然不应该认为：“那就全部放进去。”

可以给不同来源设置预算。

例如只是示意：

Instructions      10%
Current Task       10%
State              10%
History            20%
Retrieval          30%
Tool Results       20%

这不是固定标准。

真正的含义是：

Context 是有限资源。

每一类信息都应该争取：“我为什么值得占用上下文空间？”

这和后端中的：

  • CPU budget
  • Memory budget
  • DB connection pool
  • Request budget

非常类似。

2.19 信息应该如何被压缩？

假设你已经发现 Context 太长。

第一种思路：

第一种思路直接截掉后面的内容。

第二种：

第二种：删除最早的内容。

第三种：

第三种：全部总结成一段话。

都不一定好。

更好的问题是：

这个任务真正需要哪些信息？

于是压缩可以分成几种思路：

不要的信息
    ↓
删除

重复的信息
    ↓
合并

详细但非关键的信息
    ↓
摘要

关键事实
    ↓
结构化保存

当前不知道但可能需要的信息
    ↓
需要时重新检索

注意：

Compaction 的目标不是让 Context 尽可能短。

而是：

在有限空间里保留对当前任务最有价值的信息。

2.20 一个 100 轮对话实验

现在设计一个实验。

创建一个非常简单的 Agent。

让它完成一个长期任务，比如：“帮助用户分析一台存在间歇性故障的设备。”

Strategy B：Sliding Window

Strategy C：Summary

旧历史压缩成摘要。

Strategy D：Structured State

  "first_occurrence": "...",

2.22 故障实验：让 Context 自己出问题

加入大量与当前任务无关的历史记录。

2.23 从失败中你会发现一个非常重要的事实

Context 本身已经开始像一种工程系统。

它有：

  • 数据来源
  • 生命周期
  • 一致性
  • 优先级
  • 容量限制
  • 更新策略
  • 失效策略

于是：

Context Engineering 并不是 Prompt Engineering 的高级版本。

它更接近：

围绕模型输入构建的一整套数据与状态工程。

这也是为什么后面的 Agent 系统越来越像一个真正的后端系统。

2.24 Context 和 Prompt：不要再混为一谈

很多文章会把：

很多文章会把 Prompt

和：

和：Context

混在一起说。

在实际工程中，可以做一个简单区分。

Prompt 更强调：

你希望模型遵循什么指令。

Context 更强调：

模型在当前任务中拥有的全部输入信息。

例如：

Instruction:
你是售后诊断助手。

Context:
车型 = 2024 双电机
故障码 = P0XXX
历史维修 = ...
手册内容 = ...
最新诊断结果 = ...

于是：

Instruction
+
Context

共同构成一次模型调用的重要输入。

这个区分很重要，因为后面当 Agent 出问题时：“改 Prompt”只是解决问题的一种可能。

有时候真正应该修改的是：

  • Retrieval
  • State
  • Memory
  • History
  • Tool Result
  • Context Builder

2.25 Context Engineering 的一个核心原则

到这里，可以得到一条非常重要的工程原则：

不要问“我还能给模型更多什么信息”，而要问“模型为了完成当前任务，真正需要什么信息”。

两种思路看起来只差几个字。

但它们对应两种完全不同的系统设计方法。

第一种：

Need more information
      ↓
Add Context

第二种：

Understand Task
      ↓
Identify Necessary Information
      ↓
Construct Context

第二种才是我们需要培养的工程能力。

2.26 一个更进一步的问题：谁来决定 Context？

现在问题开始变得有意思了。

如果每一次 Context 都需要应用程序严格手工决定：

这个时候查订单
这个时候查历史
这个时候查手册
这个时候查维修记录

那么系统依然可能是一个固定 Workflow。

如果系统可以根据当前任务动态决定：

  • 我现在缺什么信息？
  • 我应该查哪个知识源？
  • 我是否需要重新检索？

那么 Agent 就开始出现了。

所以你会发现：

Context Engineering 是 Agent Engineering 的前置基础。

Agent 并不是凭空出现。

它首先必须知道：

它首先必须知道自己现在拥有什么信息。

以及：

以及：自己还缺什么信息。

然后才可能决定：

下一步应该做什么。

2.27 Context → Tool → Agent

可以把这三者的关系理解成：

Context
  ↓
告诉 Agent：
“我现在知道什么”

Tool
  ↓
允许 Agent：
“去获取什么 / 做什么”

Agent
  ↓
决定：
“下一步应该获取什么 / 做什么”

因此：

Context 不是 Agent 的附属品。

恰恰相反：

Agent 的每一次决策，都建立在当前 Context 之上。

这也是为什么我们先学 Context，再进入 Tool 和 Agent Harness。

2.28 一个工程师应该形成的新直觉

以后如果你发现 Agent 出现：“明明查过了，却又查一次。”

2.31 一个小结论：Context 是动态的

这是另一个特别重要的认识。

Context 不是数据库中的永久对象。

Context 更像是：

一次决策时动态生成的视图。

同一个用户：

早上 9 点

和：

下午 3 点

面对两个不同任务，

Context 完全可能不同。

甚至同一个任务，在不同执行阶段：

Task Start

和：

Task After Tool Call

Context 也可能完全不同。

因此：

Context
=
f(
    task,
    user,
    state,
    history,
    memory,
    retrieval,
    tools
)

你可以把它简单理解成：

Context 是一个函数的结果。

这个理解会非常有用。

2.32 Part 2 最重要的几个认识

现在回头看整个 Part 2。

我们实际上没有学多少“花哨技术”。

我们只是不断回答几个问题。

第一

模型到底看到了什么？

答案：

答案：Context。

第二

Context 从哪里来？

答案：

Instructions、User Input、History、State、Memory、Retrieval、Tool Results 等。

第三

为什么不能把所有信息全部塞进去？

因为：

  • 成本
  • 延迟
  • 容量
  • 噪声
  • 信息相关性

都会成为问题。

第四

History、State、Memory、RAG 是不是一回事？

不是。

History
= 过去发生过什么

State
= 当前任务是什么状态

Memory
= 哪些长期信息值得保留

RAG
= 当前需要时，从外部知识中找什么

第五

Context Engineering 到底是什么？

可以把它概括成一句话：

为了让模型在当前任务中做出更好的决策，有意识地选择、组织、压缩和注入它应该看到的信息。

本 Part → Part 3：从决定“看什么”到决定“做什么”

Context 决定模型在当前决策中可用的信息，但它本身并不授予模型执行权限。即使模型正确识别出下一步应当查询订单或创建工单，系统仍需要验证工具、参数、权限和停止条件。

下一部分把这个边界落到可运行的 Agent Loop 与 Harness：模型提出行动，运行时检查并执行，工具返回观察，再由系统决定是否继续。
