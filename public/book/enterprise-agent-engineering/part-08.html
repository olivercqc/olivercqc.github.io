Part 8｜Advanced Agent Patterns：当简单 Agent 已经不够用了

当一个 Agent 做得越来越复杂时，第一反应不应该是“再加一个 Agent”。
真正应该问的是：当前的任务复杂性，到底来自哪里？

Part 7 为基本 Agent 建立了超时、重试、预算、授权和可观察性等运行底线。高级模式并不是在这套系统上无条件叠加更多组件，而是应对任务中新出现的复杂性：是否需要先规划、主动寻找更多证据、验证中间结果，或跨进程恢复长任务？

有些任务需要先规划。

有些任务需要不断搜索。

有些任务需要操作浏览器。

有些任务需要运行几十分钟甚至几个小时。

还有一些任务，在执行过程中会不断产生新的信息，导致原来的计划失效。

这时候，一个最基本的：

Think
 ↓
Tool
 ↓
Observe
 ↓
Think

可能开始显得不够。

于是，业界逐渐出现了很多不同的 Agent Pattern：

  • Planning
  • Reflection
  • Research Agent
  • Browser Agent
  • Computer-use Agent
  • Long-running Agent
  • Stateful Agent

这些名字很容易让人产生一种错觉：“这些都是更高级的 Agent。”

其实不是。

它们更像是：

面对不同问题时，对基本 Agent Loop 做出的不同结构化扩展。

这一 Part 不希望你背下来一堆 Pattern。

这一 Part 希望你真正理解一件事情：

一个 Agent 为什么需要这些结构？

8.3 为什么不能直接让 Agent 边做边想？

可以。

而且很多任务完全应该这么做。

例如：“订单 10001 为什么还没发货？”

因此：

Planning 主要解决的是任务组织问题。

而不是：“让模型看起来更聪明。”

8.10 什么时候 Reflection 真正有价值？

不是所有结果都值得二次检查。

例如：“今天日期是多少？”

没必要。

而对于：“生成一份涉及多个资料来源的分析报告。”

额外检查可能非常有价值。

可以把 Reflection 的价值粗略理解为：

Task Risk
×
Error Cost
×
Detectability

如果任务：

  • 错误成本高
  • 错误容易被检查出来
  • 二次验证成本低

那么 Reflection 比较值得。

8.11 不要只让模型“再想一遍”

这是很多简单实现的问题。

例如：

“请再检查一下你的答案。”

然后又让同一个模型生成一次。

这种方法有时有效。

但工程上更值得思考的问题是：

“第二次检查，到底依据什么判断？”

例如可以检查：

是否满足 Schema？
是否引用真实资料？
是否违反业务规则？
是否遗漏关键字段？
是否调用了不允许的 Tool？

这时候，Reflection 开始从：“让模型重新思考。”

升级成：

“让系统增加一个明确的验证阶段。”

后者更加工程化。

State 当前任务执行到了哪里。

例如：

8.32 Pattern Selection：真正需要的是选择能力

可以建立一个非常实用的映射。

问题特征 可能需要的 Pattern
多步骤且有明确结构 Planning

8.36 Pattern Explosion

这是高级 Agent 项目特别容易出现的现象。

再：

再：

最后：

┌────────────────────────┐
│        Agent           │
├────────────────────────┤

结果没有人说得清：

每一层到底解决了什么问题。

这就是：

8.37 如何避免 Pattern Explosion？

每增加一个 Pattern，都强制问三个问题。

问题一

它解决了什么具体失败？

问题二

没有它，系统会发生什么？

问题三

增加它以后，新增了什么成本和风险？

如果回答不清楚：

如果回答不清楚，不加。

这可以成为整门课程的一条统一原则。

8.39 最终实验：Pattern Shootout

现在可以把前面讨论过的模式放在同一组案例里比较。但请先从最小模式开始，而不是一次性打开所有能力。配套实验位于 labs/lab08_advanced/：

先看 simple 的输出与轨迹，再对照运行已经实现的其他模式：

python -m labs.lab08_advanced.src.run --mode fake --pattern evidence_validation
python -m labs.lab08_advanced.src.run --mode fake --pattern reflection
python -m labs.lab08_advanced.src.run --mode fake --pattern browser

当前可运行的模式和它们帮助你观察的问题如下：

仓库模式 主要观察问题 学习边界
simple 最小 Agent 基线是否足以完成任务？ 基线，不代表最优架构
planning 显式计划是否减少遗漏，代价是什么？ 计划质量要看具体案例
evidence_validation 外部证据检查能否阻止无依据结论？ 检查通过不等于完整语义证明
reflection 再检查一次是否改善结果，还是只增加调用？ 需要对照成本与失败案例
browser 模型能否对受控文档语料执行搜索与打开？ 只操作仓库内的受控语料，不访问公共互联网
long_running 中断后能否从 checkpoint 恢复？ 需要显式持久化授权；不等于加密存储

不要用一张表预先写好谁得了五星。运行后记录任务得分、成功/失败样本、模型与工具调用、延迟、成本状态和恢复语义，再判断复杂模式有没有带来足够收益。Fake 路径用于比较固定条件下的工程接线与轨迹；它不是实际模型自主规划或真实 Browser Agent 能力的证据。

长任务实验会读写 checkpoint，因此默认受保护、拒绝持久化。只有在受控本地实验中显式启用后，才能执行：

python -m labs.lab08_advanced.src.run --mode fake --pattern long_running --checkpoint-path artifacts/lab08-checkpoint.json
python -m labs.lab08_advanced.src.run --mode fake --pattern long_running --checkpoint-path artifacts/lab08-checkpoint.json --resume

启用前只在当前实验终端临时设置 AI_ALLOW_CHECKPOINT_PERSISTENCE=true，不要通过改写仓库默认值绕过保护。Windows PowerShell 使用：

$env:AI_ALLOW_CHECKPOINT_PERSISTENCE = "true"

Bash / Zsh 使用：

export AI_ALLOW_CHECKPOINT_PERSISTENCE=true

第一次命令模拟中断并保存进度，第二次恢复同一文件继续运行。记录恢复前后的状态和写入次数，不要把“有文件”当作恢复成功。实验结束后关闭本终端中的开关：PowerShell 使用 Remove-Item Env:AI_ALLOW_CHECKPOINT_PERSISTENCE；Bash / Zsh 使用 unset AI_ALLOW_CHECKPOINT_PERSISTENCE。这只是当前 shell 的临时设置，不要将它写入 .env 或项目默认配置。

可选真实模型实验：单独观察最小模式

以下命令只运行 simple 模式，不触发长任务 checkpoint。它会调用当前 Provider，可能产生费用，并只用于观察该配置在这组受控任务中的回答与工具使用；不代表其他高级模式已经通过验证。只有在 Fake 主线通过、已批准使用 Provider、确认价格与数据处理/留存安排且输入不含未经批准的敏感资料时才运行。不要为这项只读观察开启 checkpoint 持久化或真实写操作。

python -m labs.lab08_advanced.src.run --mode real --pattern simple --output artifacts/lab08-simple-real

Computer-use / GUI 自动化在本章用于解释环境状态、观察与执行风险；当前 Lab 并没有控制宿主机桌面或公共互联网的真实 Computer-use 实现。若需要此能力，应另行设计受控环境、授权和审计，而不是把概念示例写成现成的可运行实验。

8.41 Part 8 的几个核心结论

Planning

解决任务组织问题。

Replanning

解决环境变化问题。

Reflection

解决结果验证问题。

Research Agent

解决信息探索与证据综合问题。

Browser / Computer-use

解决缺少结构化 API、需要与动态环境交互的问题。

Long-running Agent

解决执行时间长、任务无法绑定单次 Request 的问题。

Checkpoint / State

解决跨时间持续执行与恢复问题。

Artifact

解决中间成果太大、不能全部塞入 Context 的问题。
