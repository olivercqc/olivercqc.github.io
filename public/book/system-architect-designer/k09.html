第 1 节 SOA 的概念与价值

本节要解决的问题：SOA 与"分层架构"的根本区别是什么？服务为什么必须是"粗粒度、松耦合"？

一、从"分层"到"服务"

分层架构按技术职责切（表现、业务、数据），SOA 按业务能力切（下单、支付、库存）。

这个转变带来三个后果：

  • 边界与业务对齐：一个服务对应一项完整业务能力，而不是一段技术逻辑；
  • 可复用：同一能力可被多个系统调用；
  • 独立演进：服务的内部实现可以替换，只要接口不变。

二、服务的特征

特征 含义
粗粒度 一次服务调用完成一件业务事，而不是一个数据库操作
松耦合 服务之间只依赖接口契约，不依赖实现
可复用 服务被设计为可被多处使用
标准化接口 用标准协议与数据格式描述与调用
自治 服务能独立部署、独立运行

"粗粒度"最容易被误解：把每个数据库操作都包成一个服务，是最典型的反模式——调用次数爆炸、性能极差。

三、SOA 的价值

  • 复用：避免重复建设（K8 的"共享能力"）；
  • 集成：异构系统通过标准接口互通；
  • 敏捷：业务变化时只改相关服务；
  • 可组合：把服务编排成新的业务流程。

想一想 ①：SOA 与面向对象有什么区别？两者都讲"封装"，为什么还要服务化？

四、SOA 的微服务化发展

SOA 早期依赖集中式 ESB（重总线、重治理），实践中暴露出两个问题：总线成为瓶颈与单点、服务粒度偏大难以独立交付。

微服务是 SOA 的轻量化演进：去中心化治理、按业务域细粒度拆分、每个服务独立部署与数据存储。

一句话：微服务不是否定 SOA，而是把"重总线"换成"轻契约 + 自动化"。

五、例题精解

例（工程项目：服务粒度判断） 某团队把"订单"拆成 12 个服务：创建订单、校验库存、扣减库存、生成流水、发通知、写日志……每个对应一次数据库操作。请评价这次拆分。

解答：
- 粒度错误：按数据库操作拆分，导致一次下单要走 8—10 次远程调用，延迟与失败率飙升；
- 正确的做法：按业务能力拆——「订单服务」负责订单生命周期，「库存服务」负责库存，「通知服务」只管通知；单次下单由订单服务编排 2—3 次调用；
- 日志、流水这类技术性动作不应成为独立服务，可用切面或消息异步处理。

点评：判断粒度的标准是"一次调用是否完成一件业务事"，而不是"是否对应一张表"。

第 2 节 SOA 参考架构与协议规范

本节要解决的问题：UDDI、WSDL、SOAP、REST 各自解决什么问题？它们在一个调用链里怎么配合？

一、一次服务调用的完整链条

服务提供者 --发布--> 服务注册中心（UDDI）
服务消费者 --查找--> 服务注册中心
服务消费者 --绑定/调用--> 服务提供者（用 SOAP/REST，按 WSDL 描述）

四个规范刚好对应四件事：

规范 解决什么 一句话
UDDI 服务注册与发现 "服务目录"
WSDL 服务描述 "服务说明书"
SOAP 消息协议 "信封式传输"
REST 资源风格 "用 HTTP 动词操作资源"

二、逐个看

UDDI（Universal Description, Discovery and Integration）：统一描述、发现与集成。提供服务注册表，供提供者发布、消费者查找。是 SOA 的"黄页"。

WSDL（Web Services Description Language）：用 XML 描述服务的接口、操作、消息格式与访问地址，让调用方知道"怎么调"。

SOAP（Simple Object Access Protocol）：基于 XML 的消息协议，有严格的信封（Envelope）、头（Header）与体（Body）结构，可承载在 HTTP 之上。特点是规范严谨、可扩展，但消息冗长、解析开销大。

REST（Representational State Transfer）：一种架构风格而非协议，用 URI 标识资源、用 HTTP 方法（GET/POST/PUT/DELETE）表达操作，通常用 JSON。特点是轻量、易用、可缓存，但缺少 SOAP 那样的强类型契约与安全扩展。

三、ESB 在参考架构中的位置

服务提供者与消费者之间常有一个 ESB（企业服务总线）：负责路由、协议转换、数据映射、安全与监控。

优点是接入标准化、治理集中；缺点是可能成为单点与瓶颈，且配置复杂——这正是微服务"去中心化"要解决的问题。

四、例题精解

例（工程判断：协议选型） 某银行要对接一个历史遗留的第三方系统，对方只提供 WSDL，要求强类型、事务与安全扩展；同时要给移动端提供查询接口。请分别选型。

解答：
- 对遗留第三方：用 SOAP + WSDL，因为对方契约已定、需要强类型与 WS-Security 等扩展；
- 对移动端：用 REST/JSON，轻量、易缓存、对带宽友好；
- 服务注册可用 UDDI/注册中心，内部再通过 ESB 或 API 网关做协议转换。

点评：协议选型看三点——对方契约、性能与带宽约束、安全扩展需求。

五、常见误区

误区一：认为 REST 是协议。
它是一套架构风格与约束。

误区二：认为 SOAP 已淘汰。
在金融、电信等强契约场景仍广泛使用。

误区三：把 UDDI 当成"服务实现"。
它只是注册与发现机制。

下一节讲 SOA 设计标准。

第 3 节 SOA 设计标准与作用

本节要解决的问题：什么样的服务算"设计合格"？SOA 给组织带来的作用是什么？

一、四条设计标准

标准 要求
文档标准化 服务接口、数据格式、调用说明有统一文档规范
通信协议标准 统一使用标准协议（SOAP/REST/消息），避免私有协议
应用程序统一登记与集成 服务统一注册、可被发现、可被编排
服务质量（QoS） 明确可用性、性能、安全等级并度量

QoS 最容易被忽略：没有服务等级约定的"服务"只是接口，不是资产。QoS 通常包括响应时间、可用性、限流阈值、鉴权方式与 SLA。

二、SOA 的作用

  • 提升复用：能力沉淀为服务，多处调用；
  • 降低集成成本：标准接口替代点对点；
  • 提高敏捷性：业务流程可编排，变化响应更快；
  • 支撑外包与多团队协作：契约清晰，边界明确。

三、SOA 落地的三个前提

  1. 服务目录与治理：没有注册与治理，服务会变成新的"接口烟囱"；
  2. 数据一致性策略：跨服务事务必须提前设计（补偿、Saga、最终一致）；
  3. 组织配套：服务归属、版本管理、SLA 责任要落到团队。

想一想 ①：为什么"服务治理"比"服务拆分"更难？如果只拆不管，会发生什么？

四、例题精解

例（工程项目：服务治理缺失的后果） 某公司两年内建了 300 个服务，如今没人说得清哪个服务在用、哪个版本是生产版本，重复服务大量存在。请给出治理方案。

解答：
- 服务目录：统一注册，登记服务名、负责人、版本、依赖、SLA；
- 生命周期管理：上线、变更、下线全流程受控，下线前做调用方确认；
- 重复识别：按业务能力归并重复服务，建立"能力地图"；
- QoS 与度量：为每个服务定义 SLA 并监控；
- 组织：明确服务 owner，纳入考核。

点评：这是"只拆不管"的典型后果，答题骨架是"目录—生命周期—归并—度量—组织"。

五、常见误区

误区一：认为服务拆分完成就实现了 SOA。
没有治理与 QoS，服务化只会增加复杂度。

误区二：忽视 QoS。
没有等级约定的服务无法被依赖。

误区三：认为文档标准化只是"写文档"。
它要求接口契约可被机器解析与校验（如 OpenAPI、WSDL）。

下三节讲云原生。

第 4 节 云原生的定义与原则

本节要解决的问题：把系统搬到云上就是云原生吗？云原生有哪七条原则？

一、云原生不是"上云"

上云只是把虚拟机搬到云上，架构不变；云原生是一套架构原则与设计模式的集合，目标是充分利用云的弹性、自动化与分布式能力。

一句话区别：上云是搬家，云原生是按云的方式重新设计。

二、云原生架构的定义

从技术角度，云原生架构是基于云原生技术的一组架构原则和设计模式的集合，旨在把应用的开发、部署、运维全过程都建立在云的能力之上。

三、七条原则（必背）

原则 含义
服务化 按业务能力拆成服务，接口标准化
弹性 按负载自动伸缩，容量与业务解耦
可观测 日志、指标、链路追踪三件套
韧性 故障可隔离、可降级、可自愈
所有过程自动化 CI/CD、基础设施即代码
零信任 不默认内网可信，处处认证授权
架构持续演进 架构随业务与技术持续调整

记忆线索：拆开（服务化）→ 能伸（弹性）→ 看得见（可观测）→ 打不垮（韧性）→ 自动化 → 不轻信（零信任）→ 一直在变（演进）。

想一想 ①：为什么"零信任"会成为云原生原则？传统"内网可信"的假设在云上为什么失效？

四、例题精解

例（工程项目：云原生改造目标） 某系统已迁到云上虚拟机，但仍需手工部署、高峰期靠人扩容、故障靠人肉排查。请对照七条原则指出差距。

解答：
- 服务化：单体未拆，无法局部扩容（差距）；
- 弹性：人工扩容，未实现按负载自动伸缩（差距）；
- 可观测：靠人肉排查，缺指标与链路追踪（差距）；
- 韧性：无降级与自愈机制（差距）；
- 自动化：手工部署，缺 CI/CD 与基础设施即代码（差距）；
- 零信任：内网直连数据库，缺服务间认证（差距）；
- 持续演进：无架构演进机制。

点评：七条原则正好可以当"云原生成熟度检查单"用——逐条对照打分，比笼统说"要云原生"有效。

五、常见误区

误区一：认为上云就等于云原生。
架构不变，弹性与自动化都不会自动出现。

误区二：认为弹性就是"能加机器"。
真正的弹性是自动、按需、可回收。

误区三：把可观测等同于"打日志"。
还需要指标与分布式链路追踪。

下一节讲模式与反模式。

第 5 节 云原生架构模式与反模式

本节要解决的问题：哪些架构模式是云原生的标准动作？哪些做法看似云原生、实则反模式？

一、主要架构模式

模式 做法 解决的问题
服务化架构 按业务域拆服务，接口标准化 独立交付与弹性伸缩
Mesh 化架构 把通信、安全、可观测下沉到服务网格 业务代码与治理解耦
Serverless 无需管理服务器，按调用计费 极致弹性与运维简化
存储计算分离 计算无状态、状态外置到存储 计算可弹性伸缩
分布式事务模式 Saga、TCC、消息最终一致 跨服务数据一致性
可观测架构 日志、指标、追踪统一采集 故障定位与容量分析
事件驱动架构 通过事件解耦生产者与消费者 削峰、异步、扩展

其中存储计算分离是弹性伸缩的前提：如果计算节点上有本地状态，就无法随意扩缩容。

二、三个典型反模式

反模式 症状
庞大的单体应用 一个应用包揽全部功能，无法局部扩容与独立交付
单体"硬拆"为微服务 只按代码结构切分，未按业务域，导致跨服务调用爆炸、事务混乱
缺乏自动化能力的微服务 服务拆了，但部署、测试、监控全靠手工，复杂度徒增

第三个尤其常见：微服务的收益来自自动化，没有自动化的微服务是负债。

想一想 ①：为什么"硬拆"比"不拆"更糟？举一个具体后果。

三、模式选择的判据

  • 业务复杂度高、团队多 → 服务化 + 事件驱动；
  • 流量波峰波谷明显 → 弹性 + Serverless；
  • 有状态计算多 → 先做存储计算分离；
  • 遗留系统多 → Mesh 化（把治理下沉，少改业务代码）。

四、例题精解

例（工程项目：识别反模式） 某团队把单体按"controller / service / dao"三个包拆成三个微服务，共用同一个数据库，部署靠手工脚本，监控只看到机器 CPU。请指出问题。

解答：
- 硬拆：按技术分层而非业务域拆分，一个业务请求要跨三个服务，调用链与事务复杂度飙升；
- 共享数据库：破坏服务自治，等于"分布式单体"；
- 缺自动化：手工部署无法支撑多服务发布，违背"所有过程自动化"原则；
- 可观测不足：只看机器指标，看不到服务与链路。
- 改进：按业务域重划边界、每服务独立数据、建 CI/CD、上指标与链路追踪。

点评：这题四个问题正好对应三条反模式 + 一条原则，可作为反模式的识别模板。

误区一：认为微服务就是云原生。
没有弹性、自动化、可观测，只是"分布式单体"。

误区二：认为共享数据库"省事"。
它让服务无法独立演进，是最常见的隐性反模式。

误区三：认为 Serverless 适用于所有场景。
冷启动、执行时长、状态管理都有约束。

第 6 节 云原生关键技术

本节要解决的问题：容器、微服务、Serverless、服务网格分别解决什么问题？它们如何组合？

一、四类技术各管一段

技术 解决什么 关键点
容器 一致的运行环境与打包 镜像、隔离、轻量；K8s 负责编排
微服务 业务拆分与独立交付 服务注册发现、配置、熔断限流
Serverless 极致弹性与免运维 事件触发、按量计费、冷启动
服务网格 通信治理下沉 数据平面（Sidecar）+ 控制平面

二、容器与编排

容器把应用与依赖打包成镜像，保证"开发环境能跑、生产也能跑"。相比虚拟机，容器更轻、启动更快、密度更高。

Kubernetes（K8s） 是容器编排的事实标准，核心能力：调度、自愈（重启/替换）、滚动更新、服务发现、配置与密钥管理、水平扩缩容。

一句话：容器解决"怎么打包"，K8s 解决"怎么调度与自愈"。

三、微服务与治理

微服务的关键不在"拆"，而在治理：

  • 服务注册与发现：实例变化时调用方自动感知；
  • 配置中心：配置与代码分离、可动态刷新；
  • 熔断与限流：防止故障扩散（雪崩）；
  • 网关：统一入口、鉴权、路由。

四、Serverless

Serverless（无服务器） 让开发者不感知服务器：代码以函数为单位部署，事件触发执行，按调用次数与时长计费。

优点：极致弹性、零运维、成本按需。
约束：冷启动延迟、执行时长上限、状态需外置、调试与可观测较难。

Serverless 的组成

Serverless 不是"没有服务器"，而是把服务器运维从开发者视野里移走。它由两块拼成：

组成 含义 典型形态
BaaS（后端即服务） 把存储、数据库、消息、鉴权、AI 等后端能力做成全托管的云服务 API，直接调用 对象存储、托管数据库、消息队列、身份服务
FaaS（函数即服务） 把应用逻辑拆成函数，由事件触发执行，平台负责伸缩与计费 上传文件触发转码、定时任务、API 后端

FaaS 是 Serverless 中最具代表性的形态：函数不常驻、按事件唤起、执行完即释放，因此计费按"调用次数 + 执行时长"。

四个特征：

  1. 全托管：只写代码，不碰服务器、网络、高可用；
  2. 通用性：结合 BaaS 的 API 能力，能支撑云上大多数应用类型；
  3. 自动弹性：无需提前做容量规划，按请求量自动扩缩；
  4. 按量计费：不为闲置资源付费。

这四个特征正好对应"降本增效、弹性伸缩"——BaaS 提供能力、FaaS 提供算力、事件把两者串起来。

五、服务网格

服务网格（Service Mesh） 把服务间通信的流量管理、安全、可观测能力从业务代码中抽出来，交给 Sidecar 代理。

结构：

  • 数据平面：一组 Sidecar 代理，拦截服务间流量；
  • 控制平面：下发路由、策略、证书。

价值：业务代码不感知治理逻辑，多语言统一治理；代价：多一跳网络、运维复杂度上升。

想一想 ①：已经用了微服务框架（如 Spring Cloud），还需要服务网格吗？判断依据是什么？

六、例题精解

例（工程项目：技术选型组合） 某系统要做云原生改造，要求：多语言服务共存、需要灰度与熔断、部分任务型接口流量稀疏、要能自动扩缩容。请给出技术组合。

- 服务网格统一处理多语言服务的灰度、熔断、mTLS，避免每种语言各写一套治理；

第 7 节 分布式事务

本节要解决的问题：服务各自持有私有数据源后，"一笔业务跨多个服务"怎么保证要么全成、要么全败？

一、为什么突然需要分布式事务

单体架构里，一次业务写多张表，靠本地事务就解决了。微服务提倡每个服务使用私有数据源，于是一个大颗粒度业务要访问多个服务——跨库写入无法用本地事务保证，数据就可能不一致。

这就是分布式事务要解决的问题。注意它不是"技术炫技"，而是拆服务带来的必然代价。

二、五种主流模式

五种主流模式，各自的取舍很明确：

模式 做法 优点 代价
XA（两阶段提交） 协调者先问所有参与者"能否提交"，再统一提交 一致性很强、标准成熟 性能差，协调者阻塞、锁持有时间长
消息最终一致（BASE） 本地事务 + 消息，下游异步消费 性能很高、解耦 通用性有限，只适合可异步的场景
TCC（Try-Confirm-Cancel） 业务层实现三阶段：预留、确认、取消 隔离性可控、较高效 对业务侵入性非常强，开发维护成本高
SAGA 每个正向事务配一个补偿事务，失败则逆序补偿 无 Try 阶段，长事务友好 与 TCC 类似，开发维护成本高，无隔离性
SEATA AT 框架自动记录数据快照，失败时自动回滚 高性能、几乎无代码改造 有使用场景限制（依赖 SQL 解析与全局锁）

三、怎么选

场景 建议
强一致、低频、可接受延迟（转账、账务） XA 或 TCC
可异步、允许秒级延迟（发券、积分、通知） 消息最终一致
长事务、跨多个服务、步骤可补偿（订单履约） SAGA
已有大量存量 SQL、想少改代码 SEATA AT
强一致且高并发 重新设计边界，尽量避免跨服务事务

最后一行才是真正的架构答案：最好的分布式事务，是不产生分布式事务——通过业务边界划分把强一致需求收进同一个服务。

四、三个必须配套的机制

无论选哪种模式，都要配套：

  1. 幂等：补偿、重试、消息重复投递都会导致重复执行；
  2. 空回滚与悬挂：TCC 的 Cancel 可能先于 Try 到达（空回滚），也可能 Try 在 Cancel 之后才到（悬挂），需要事务状态表控制；
  3. 对账与告警：最终一致必须有兜底核对，否则不一致会长期沉默。

想一想 ①：为什么 TCC 的 Cancel 必须"幂等且能空回滚"？如果做不到，会出现什么故障？

五、例题精解

解答：
- ① 用 TCC 或 SAGA：库存要预留（Try 冻结库存），失败要释放；若业务简单可用"本地消息表 + 库存服务内扣减"；
- ② 用消息最终一致：积分与通知可异步，失败重试 + 对账；
- ③ 用 XA 或 TCC：金融转账要求强一致，且通常频率可控、可接受延迟。

点评：选型三步——先看一致性要求，再看能否异步，最后看业务改造成本。

六、常见误区

第 8 节 可观测性

本节要解决的问题：日志、链路、指标各自回答什么问题？为什么三样缺一不可？

一、可观测不是"多打日志"

一个常见误解：日志打得越多越"可观测"。实际上可观测要回答的是具体问题：

  • 这个接口为什么慢了？（链路）
  • 错误率什么时候开始上升、影响多少用户？（指标）
  • 这次请求到底走到哪一步失败的？（日志 + 链路）

三类工具缺一不可，因为它们回答的问题不同。

二、三件套

组件 提供什么 由谁产生 典型用途
Logging（日志） 多个级别的详细信息跟踪：verbose / debug / warning / error / fatal 应用开发者主动提供 定位具体错误、审计
Tracing（链路追踪） 一个请求从前端到后端的完整调用链路 框架/SDK 自动埋点 分布式场景定位慢点
Metrics（指标） 可聚合的数值时间序列 采集器/暴露端点 容量、告警、趋势

三者的定位很清楚：Logging 由开发者主动提供，Tracing 对分布式场景尤其有用，Metrics 提供可聚合的量化视图。

三、为什么分布式场景离不开 Tracing

单体时代，一次请求的调用栈就在一个进程里，日志里有 traceId 就能串起来。

微服务下，一次请求会穿过网关、多个服务、数据库、消息队列。没有链路追踪，你只知道"慢"，不知道慢在哪一跳。

链路追踪的关键是统一的 traceId 贯穿全链路，以及 span 记录每一跳的开始时间、耗时与状态。

四、指标要选对

指标的价值在于可聚合、可告警。常见四类：

  • 计数（Counter）：请求数、错误数；
  • 计量（Gauge）：在线连接数、队列深度；
  • 分布（Histogram/Summary）：响应时间分位数（P50/P95/P99）；
  • 速率：QPS。

分位数比平均值有用：平均 100ms 可能掩盖了 1% 用户 5 秒的体验。

想一想 ①：如果只能保留一个指标来判断"服务是否健康"，你选平均响应时间还是 P99？为什么？

五、例题精解

例（工程项目：定位慢请求） 某系统高峰期出现"偶尔下单很慢"，平均响应正常，用户投诉集中在少数人。请说明如何用可观测三件套定位。

*解答**：
- 指标：看下单接口的 P99/P999 而非平均值，确认长尾存在；按时间与实例维度下钻，判断是全局还是个别实例；
- 链路：抽取 P99 的慢请求 traceId，看 span 耗时分布，定位是数据库、下游服务还是消息队列；
- 日志：用 traceId 拉取该请求全链路日志，查看是否有重试、超时、GC 或慢 SQL；
- 闭环：定位后加对应指标与告警，形成"发现—定位—验证"的常态能力。

点评：这题的层次感在于"指标发现异常 → 链路定位位置 → 日志确认原因"，三步顺序不能乱。

六、常见误区

误区一：只做 Metrics 不做 Tracing。
知道"慢"但不知道"慢在哪"，排查成本极高。

误区二：日志级别全开、不设采样。
成本爆炸且淹没关键信息，生产应分级 + 采样。

误区三：只看平均值。
长尾问题会被平均值掩盖。

第 9 节 云原生数据库

本节要解决的问题：传统数据库上云与"云原生数据库"差在哪？它的四大优势具体指什么？

一、传统数据库上云的困境

把 Oracle 从自建机房搬到云上虚拟机，问题并没有解决：

  • 存储与计算耦合：扩容只能整体升配，不能只扩存储或只扩计算；
  • 扩展能力受限：单机上限决定业务上限；
  • 运维成本高：备份、升级、故障切换依赖人工；
  • 故障恢复慢：主备切换往往需要分钟级。

这些痛点的根源是架构按"单机"设计，上云只是换了物理位置。

二、云原生数据库的四个特征

特征 含义
存储计算分离 计算节点无状态、存储独立扩展，可按需分别伸缩
弹性伸缩 秒级/分钟级增减计算节点，按负载自动调整
故障自愈 节点故障自动摘除与重建，数据由存储层保证持久
全链路可观测 内置监控、慢查询、链路与容量分析

存储计算分离是其余三点的基础：计算节点无状态，才能随时增删；存储独立，才能保证数据不随计算节点丢失。

三、OLTP 与 OLAP 拆分

一个关键做法：把在线交易与离线分析拆到两类数据库。

  • OLTP 型：服务在线交易，强调低延迟、高并发、强一致；
  • OLAP 型：服务报表与分析，强调大扫描、列式存储、聚合性能。

传统做法用一套 Oracle 同时承担两类负载，结果互相拖累——这正是"混合负载"的典型问题。

四、选型与落地难点

难点 应对
兼容性（SQL 方言、存储过程） 提前做兼容性评估，优先改造强依赖特性
迁移风险 双写/双跑、数据校验、灰度切流
事务与一致性 明确拆分边界，减少跨库事务（见第 7 节）
成本 按实际负载评估，避免为峰值长期付费

想一想 ①：为什么"存储计算分离"能让弹性伸缩变得可行？如果计算节点带本地状态，扩容会有什么问题？

实施效果怎么衡量

云原生数据库改造完，效果要能用数字说话，通常从四个维度对比改造前后：

维度 指标
性能 交易 P95 延迟、报表查询耗时、峰值 TPS
可用性 故障切换时间、年度不可用时长、数据零丢失达成情况
成本 单笔交易数据库成本、存储与计算资源利用率、闲置资源占比
运维效率 扩容耗时（天→分钟）、备份恢复时长、人工干预次数

最容易被忽略的是"扩容耗时"：传统数据库扩容要采购、停机、迁移，常以周计；云原生数据库可到分钟级——这个前后对比最能体现架构价值。

五、例题精解

例（工程项目：迁移方案） 某企业核心系统跑在 Oracle 上，报表查询经常影响交易性能。请给出基于云原生数据库的改造方案。

*解答**：
- 拆分负载：交易库迁到 OLTP 型云原生数据库（存算分离、弹性伸缩）；报表迁到 OLAP 型（列式、大扫描优化）；
- 数据同步：通过 CDC/日志订阅把交易数据同步到分析库，避免直接查生产库；
- 弹性：交易库按大促负载预扩 + 自动伸缩，分析库按批处理时段扩缩；
- 高可用：依赖存储层多副本与自动故障转移，替代人工主备切换；
- 迁移路径：先迁报表（风险低、见效快），再迁交易（灰度切流 + 双跑校验）。

点评：这类题的得分点在"先拆负载、再谈迁移"，以及"先易后难的迁移顺序"。

六、常见误区

误区一：认为数据库上了云就是云原生数据库。
关键看是否存算分离、能否弹性与自愈。

误区二：认为存算分离一定更快。
它牺牲了一部分本地 IO 优势，换的是弹性与运维简化。

第 10 节 以服务为中心的企业集成

本节要解决的问题：企业数据"分布 + 异构"造成访问障碍，标准化的集成服务怎么解决？

一、障碍在哪

企业数据的分布性（数据散在多个系统）与异构性（格式、模型、DBMS 不同），是"方便访问企业数据"的主要障碍。

数据集成与聚合技术因此诞生，目标是：对分布式数据与异构数据提供透明访问。

二、三种标准集成服务

以服务为中心的企业集成，通过信息服务提供集成数据的能力，主要包括：

服务 作用 关键点
联邦服务（Federation） 把各种类型的数据聚合起来统一访问 支持关系型与非关系型（XML、文本、内容）；各数据仍按自身方式管理
复制服务（Replication） 提供远程数据的本地访问 通过实时复制与数据转换，在本地维护副本；本地与源可技术独立
转换服务（Transformation） 格式转换 源格式 → 目标格式，可批量也可实时

三者的分工可以这样记：联邦是"看得见"（不搬数据）、复制是"搬过来"（本地副本）、转换是"换格式"（模型映射）。

异构的五个体现

"异构"不是一个笼统的词，落到工程上至少有五个方面：

体现 说明 集成时的对策
数据格式 XML、JSON、CSV、EDI、二进制 转换服务做格式映射
数据模型 关系表、文档、图、键值 统一模型层或联邦查询
传输协议 HTTP、MQ、文件、专有协议、RosettaNet/AS1/AS2 协议适配与网关
编码与语义 字段编码规则不同、同名不同义、单位不一致 主数据与字典映射
DBMS 与访问方式 不同厂商、不同 SQL 方言、不同驱动 通用接口（ODBC/JDBC）或数据服务

教材在讲伙伴集成时点得很准："因为业务伙伴系统的异构性，伙伴服务需要支持多种传输协议和数据格式"——协议与格式是异构最外显的两层，模型与语义是更深的两层。

三、与 ESB 的关系

  • ESB 解决"消息怎么路由、协议怎么转换"；
  • 三种集成服务解决"数据怎么被统一访问、复制与转换"。

二者常配合：ESB 负责传输与路由，集成服务负责语义与格式。SOA 的设计标准里也包含"应用程序统一登记与集成"。

四、例题精解

例（工程项目：多源异构数据集成） 某集团要整合 ERP、CRM 与自建系统：ERP 数据不能动（只读）、CRM 要提供实时查询、自建系统的编码规则与集团标准不一致。请分别选用哪种集成服务。

*解答**：
- ERP（只读、不能动） → 联邦服务：不搬数据，只做聚合访问；
- CRM（需本地实时查询、降低对源系统压力） → 复制服务：实时复制到本地，查询走副本；
- 自建系统（编码/格式不一致） → 转换服务：做模型映射与格式转换后接入。

点评：判断依据是"能否搬数据、是否要低延迟、是否只是格式差异"。

五、常见误区

误区一：认为集成就是"抽数到数据仓库"。
联邦服务不搬数据，是"虚拟集成"。

误区二：认为复制服务只做备份。
它的目的是本地访问性能与解耦，不只是容灾。

一、这一章的主线

这一章回答的是"把系统拆成服务、让服务跑在云上"。十节分两条线：前四节讲 SOA——服务特征、参考架构与四类协议、设计标准与治理、云原生七原则；后六节讲落地——架构模式与反模式、容器/微服务/Serverless/网格、分布式事务、可观测性、云原生数据库、企业集成三服务。

二、必须能说出的判断

  • 服务的粒度标准是"一次调用完成一件业务事"，不是"一张表一个服务"；
  • UDDI 管发现、WSDL 管描述、SOAP/REST 管调用，四者位置不能混；
  • 云原生七原则可当成熟度检查单：服务化、弹性、可观测、韧性、自动化、零信任、持续演进；
  • 分布式事务五模式各有取舍，最好的方案常常是"通过划分边界避免分布式事务"；
  • 可观测三件套分工明确：日志回答"发生了什么"，链路回答"慢在哪一跳"，指标回答"多严重"。
