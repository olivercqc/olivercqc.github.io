第 1 节 计算机系统是什么

本节要解决的问题：一台计算机由哪些部分构成，硬件与软件的边界到底在哪里？

一、从一个"装系统"的老问题说起

同一台笔记本，出厂预装 Windows，你格掉换成 Linux，跑同一段代码，速度可能差一截；再换一块更好的显卡，某些程序又会快很多。

如果计算机只是"一堆硬件的组合"，那么换不换操作系统不该影响速度；如果只是"一堆软件"，那么换显卡也不该有用。

事实是两者都影响。这说明：计算机不是硬件的集合，也不只是软件的集合，而是一个软硬协同的系统。

计算机系统的定义很克制：

计算机系统是指用于数据管理的计算机硬件、软件及网络组成的系统。它按人的要求接收和存储信息，自动进行数据处理和计算，并输出结果信息。

这句话有三个关键词，值得拆开看：硬件、软件、网络。注意第三个——很多人会下意识把"网络"排除在"一台计算机"之外，但我们把它算进系统组成，因为现代计算机的能力边界早已不是机箱内部。

想一想 ①：一台没联网的电脑和一台联网的电脑，硬件相同，它们算不算"同一个计算机系统"？为什么把网络列入系统组成？

二、硬件：五个部件，三种现实形态

从这里开始冯·诺依曼结构，这是现代计算机的起点。

冯·诺依曼结构把硬件划分为 5 部分：运算器、控制器、存储器、输入设备、输出设备。

但你真的拆开机箱，看到的并不是五块东西。现实中的工程集成做了两次合并：

  • 运算器 + 控制器 → 处理器。今天没有独立的"运算器芯片"，它们被集成封装成 CPU。要注意：处理器并不只有这两部分，它还集成了多级缓存、多种通信总线和接口。
  • 输入 + 输出 → 按传输过程重新划分。键盘、显示器这些设备不是直接接到 CPU 上的，中间要经过总线、接口、外部设备这条链路。所以讲完处理器和存储器之后，讲的是总线、接口、外设，而不是"输入设备、输出设备"。

这就是"5 个部件"和"现实 4 类硬件"的对应关系。考试里两种问法都出现过：问"冯·诺依曼结构包含哪五部分"答五部分，问"计算机硬件由哪些部分组成"答处理器、存储器、总线、接口、外部设备。

硬件本身是什么？这里的定义是：由机械、电子元器件、磁介质和光介质等物理实体构成。这句话的用处在于——判断某个东西是不是硬件，看它是不是物理实体。

三、软件：系统软件与应用软件

软件的定义比"程序"宽：

软件是一系列按特定顺序组织的数据和指令，并控制硬件完成指定的功能。

软件划了两层：

系统软件——为整个系统配置、不依赖特定应用领域的通用软件，负责控制和管理硬件与软件资源，并为上层提供运行环境。这里列出四类：

  1. 操作系统
  2. 程序设计语言翻译系统（编译器、解释器）
  3. 数据库管理系统
  4. 网络软件

应用软件——为某类应用需要或解决某个特定问题而设计，如图形图像处理、财务软件、游戏。再分为专用（为一个单位定制）和通用（面向大众，如 Office）两类。

判断一个软件属于哪类，标准不是"我用不用它"，而是它是否为特定的应用目的而存在。数据库管理系统属于系统软件，但基于它开发的"学生成绩管理系统"是应用软件——这两者经常被混淆。

想一想 ②：微信是系统软件还是应用软件？微信内置的"小程序运行环境"呢？

四、一条越来越模糊的边界

有个很好的例子软硬件的界限：

可编程逻辑，它在设计阶段可作为软件对待，但运行中则以逻辑门的物理形态存在。

换句话说，同一件东西，在设计时是"配置/代码"，在运行时是"电路"。FPGA 就是这样：你写一段硬件描述语言，烧进去之后它真的变成了电路，不再是"执行指令的软件"。

这个现象带出一个重要结论：软硬件是功能实现方式的两种选择，而非两类东西。同一功能可以用软件实现（灵活、慢、便宜），也可以用硬件实现（快、贵、难改）。嵌入式领域里这个权衡尤其常见——要不要给视频解码加一个专用硬件模块？

五、计算机怎么分类

分类维度很多，可以从硬件（结构、性能、规模）、软件（构成、特征）、整体用途与服务对象三个角度分。

但要注意的是：分类没有严格界限。电话手表、能通信的平板、带路由功能的电视盒，同一设备可以归入多个父类。所以考试里如果问分类，通常考的是"按什么维度分"，而不是让你给某台设备贴唯一标签。

常见的一张大类：个人计算机（台式、平板）、通用计算机（服务器、超级计算机）、嵌入式计算机（医疗、交通、金融、国防设备）、家用电子设备、电信设备、云计算/云存储。

六、例题精解

例 1（工程项目） 某银行要把 200 个网点的 VTM（远程视频柜员机）统一改造。设备需支持身份证读卡、人脸识别、视频通话、凭条打印，要求 7×24 运行、故障可远程诊断、单台硬件成本不高于 8000 元。

请回答：① 它属于哪一类计算机；② 按软考口径的硬件分类列出其组成；③ 人脸识别应放在本地还是云端，为什么。

思路：先定位类别，再按"处理器—存储器—总线/接口—外部设备"四类拆，最后把软硬件划分当成一次取舍来做。

解答：
- 分类：嵌入式计算机（专用性强、嵌入具体设备、资源受限）。
- 硬件：
- 处理器：低功耗 SoC（CPU + 轻量 NPU，用于本地活体检测）；
- 存储器：Flash 存系统镜像与本地模型、RAM 作为运行区、外存可选 SSD 缓存录像；
- 总线与接口：内部总线连接读卡器与摄像头；网口/4G 模块用于远程通信；USB/串口连接打印机；
- 外部设备：摄像头与补光灯、身份证读卡器、触摸屏、凭条打印机、密码键盘。
- 人脸识别放哪：本地做活体检测与特征提取，云端做比对检索。理由：本地保证断网可用（7×24 场景）与低延迟，且原始人脸不出网点，符合个人信息合规；云端承担大库检索与模型迭代，避免每台设备都堆算力，从而压住 8000 元成本。

点评：这类题的失分点有两个——拆硬件时漏掉"接口"这一层（我们把总线、接口、外设分开算），以及把"软硬件划分"当成纯技术问题，忘了它同时受成本、可用性、合规三重约束。

工程启示：选型从来不是"选最强的"，而是"在成本、可用性、合规、可维护性之间找平衡点"——这正是第 8 章质量属性与架构评估要展开的东西。

七、常见误区

误区一：把"处理器"等同于"CPU 的运算部分"。
处理器除了运算和控制，还集成了缓存、总线接口、MMU 等。问"处理器由哪些部分组成"时，只答运算器和控制器会漏分。

误区二：把数据库管理系统当成应用软件。
它管理的是数据资源、为上层应用提供平台，属于系统软件；基于它做的业务系统才是应用软件。

误区三：认为硬件与软件的界限是固定的。
可编程逻辑、固件、微码都在边界上。判断标准是"运行时的存在形态"，不是"开发时用什么写"。

误区四：把网络排除在计算机系统之外。
这里的定义明确包含网络。答题时如果问"计算机系统组成"，只答硬件和软件两分法，可能不完整。

九、小结与衔接

留下一个问题：这五个部件里，哪个最快、哪个最慢？为什么"最快的那个"反而决定了整个系统的设计？

下一节先看最快的那个——处理器。

第 2 节 处理器：为什么手机和电脑的芯片不能互换

本节要解决的问题：处理器凭什么成为"运算与控制的核心"？CISC 与 RISC 的差别到底是什么，为什么最后 RISC 成了主流？

一、一个换不了芯片的现实

你手机里是 ARM 芯片，电脑里是 x86 芯片。把电脑的 CPU 拆下来焊到手机上，手机不会变快，只会不亮。

这不是性能问题，而是指令集不兼容——手机 App 是为 ARM 指令集编译的，x86 根本看不懂那些机器码。

所以，处理器的"身份"不是主频、不是核心数，而是它认识哪一套指令。这一点是理解 CISC 与 RISC 之争的钥匙。

想一想 ①：如果指令集只是"软件和硬件的约定"，那为什么不让所有处理器都支持所有指令集，省掉兼容问题？

二、处理器里到底有什么

的典型处理器结构包含六个部分：

部件 职责
指令部件 取指令、译码、控制
运算部件 整型、浮点、向量运算
寄存器组 暂存操作数与结果（最快的一层存储）
存取部件 从存储设备取数据
Cache 部件 缓存热点数据（第 3 节详讲）
MMU 部件 地址转换（虚拟地址 → 物理地址）

一条指令在里面的流转过程是：指令部件经 MMU-Cache 取到指令并译码 → 控制存取部件取数据 → 控制寄存器组为运算器准备操作数 → 运算部件计算 → 完成部件排队并向指令部件反馈 → 决定下一条指令的顺序或跳转。

这段流程听起来抽象，但它解释了一个常见现象：为什么主频提升带来的性能提升越来越小。因为主频只加快"运算"这一步，而取指、取数、访存这些环节的延迟并没有同比下降——第 3 节会看到，主存延迟是几百个周期，光靠主频根本补不回来。

三、指令集的两条路：CISC 与 RISC

CISC（复杂指令集）：指令多、长度可变、寻址方式复杂，一条指令可以完成较复杂的操作（比如"从内存取数、加、写回"一步到位）。代表是 Intel、AMD 的 x86。

RISC（精简指令集）：指令少、长度固定、寻址方式简单、寄存器多，一条指令只做一件简单的事，复杂操作由多条指令组合完成。代表是 ARM 和 Power。

一句判断很关键：

除了由于历史原因而仍然存在的 CISC 结构外，RISC 已经成为计算机指令集发展的趋势，几乎所有后期出现的指令集均为 RISC 架构。

为什么？三个原因：

  1. 流水线友好。指令定长、格式统一，CPU 可以像流水线一样每个周期发射一条，不必等"这条指令到底多长"。
  2. 功耗与面积。CISC 的复杂译码电路耗电、占面积；移动设备对功耗极敏感，这也是 ARM 统治手机的根本原因。
  3. 编译器分担复杂度。把"复杂操作"交给编译器拆成多条简单指令，硬件就能保持简单——复杂度从硬件转移到了软件。

想一想 ②：既然 RISC 更好，为什么 x86 至今还在？提示：想想你电脑上那些二十年前的老软件。

四、专用处理器：不追求通用，只追求极致

除了 CPU，这里还列出三类专用处理器，它们的取舍逻辑完全不同：

GPU（图形处理器）：数百到数千个内核，为并行计算优化。单个核心弱、但数量极多，适合"同一操作作用于海量数据"的场景——这正是深度学习的计算特征，所以 GPU 成了 AI 训练的标配。

DSP（数字信号处理器）：专用于实时数字信号处理。点出了三个技术特征：用饱和算法处理溢出（溢出时钳位到最大/最小值，而不是回绕）、用乘累加运算提高矩阵运算效率、为傅里叶变换设计专用指令。它出现在高速信号采集设备里（雷达、通信基带、音频处理）。

FPGA（现场可编程逻辑门阵列）：硬件可编程。它的价值不在"快"，而在"可以变成任何电路"——小批量、需要快速迭代、或需要极低延迟的场景（如高频交易、协议加速）会选它。

三者的对比可以这样记：GPU 是"很多个简单工人"，DSP 是"一个熟练的专职工匠"，FPGA 是"可以自己捏形状的工具"。

另外，国产处理器已有较完整的布局：龙芯、飞腾、申威、兆芯、国微、国芯、华睿、翔腾微、景嘉微。其中多数走 RISC 路线（龙芯为 LoongArch、飞腾为 ARM 架构、申威为 Alpha 衍生），这条信息在做"自主可控"类案例题时会用到。

五、例题精解

例 1（工程选型） 某安防公司要做一个"边缘智能分析盒"：接入 8 路 4K 摄像头，实时做人形与车辆检测；单盒硬件成本不超过 3000 元；算法每季度迭代一次；部署在客户机房，无人值守。

请给出处理器方案并说明理由，同时说明为什么排除另外两种选择。

思路：先把约束翻译成技术要求——多路视频解码（并发）、推理算力（固定成本下的性能）、季度迭代（可更新性）、无人值守（功耗与稳定性）。

解答：
- 方案：主控选 ARM 多核 SoC（跑 Linux、负责解码与业务逻辑），推理交给集成 NPU 或板载 GPU 加速器。
- 理由：ARM 功耗低、单价低，能在 3000 元成本内做到 8 路解码；NPU/GPU 提供并行算力，满足实时推理；算法以模型文件下发，季度迭代只需更新软件，不必换硬件。
- 排除项：
- 纯 x86 方案：算力够但功耗与整机成本偏高，且多路解码需要额外加速卡，超预算；
- 定制 ASIC：流片成本高、周期长，算法每季度变一次，硬件跟不上，且 8 路规模撑不起流片量。

点评：工程选型的标准写法是"约束 → 技术要求 → 方案 → 排除理由"，缺最后一步最容易被扣分，因为阅卷人看不出你是权衡过还是碰巧选对。

例 2（工程权衡） 某物流公司的 5 万台手持终端（PDA）项目：要求单次充电续航 12 小时，支持扫码、热敏打印、4G 回传，采购单价控制在 2500 元以内，且要能批量供货。

请问：处理器架构应选 x86 还是 ARM？如果改用 x86，会付出什么代价？

解答：
- 选 ARM（RISC）。理由：定长指令、译码电路简单，同等算力下功耗与芯片面积更小，直接决定续航与整机成本；ARM 生态在移动/手持终端成熟，供货稳定。
- 改 x86 的代价：功耗高 → 电池容量需加大 → 重量与成本上升；散热设计复杂 → 结构件成本增加；单颗芯片价格更高 → 5000 台量级的采购预算撑不住；此外待机功耗大，12 小时续航难以达标。

点评：这道题的关键不是"ARM 比 x86 好"，而是把架构特性和约束（功耗、成本、续航、批量供货）一一对应。工程语境下，没有绝对优劣，只有是否匹配约束。

工程启示：处理器选型是架构决策的缩影——先定约束，再谈技术。这条思路在 K5（架构风格选型）、K9（云原生技术选型）里会反复出现。

六、常见误区

误区一：RISC 指令少 = 功能弱 = 性能低。
恰恰相反，定长指令利于流水线，现代 RISC 在通用性能上已不输 CISC。指令少不等于能力弱，复杂操作由编译器拆解。

误区二：主频高 = 性能强。
主频只反映时钟频率，实际性能还取决于 IPC（每周期指令数）、缓存命中、访存延迟。第 3 节会量化这个差距。

误区三：GPU 主频低，所以不如 CPU。
GPU 核心多、单核弱，胜在并行吞吐。判断依据是"任务是否可并行"，而不是单看频率。

误区四：把"处理器"和"CPU"当同义词，忽略专用处理器。
GPU、DSP、FPGA 与 CPU 同属处理器，只是定位不同。

第 3 节 存储器：为什么 8GB 的电脑能跑 12GB 的程序

本节要解决的问题：处理器很快、存储器很慢，计算机靠什么把这个速度差"藏"起来，又怎么把这个"快"算出来？

一、两个说不通的现象

打开任务管理器，你可能见过这样的画面：物理内存 8GB，但正在运行的程序加起来占了 12GB，系统既没崩，也没报错。

再看另一个：CPU 主频 3.5GHz，意味着每秒 35 亿个时钟周期，理论上跑一个百万次的循环只要几毫秒，可你实际等它跑完，喝了半杯水。

这两件事看着无关，其实是同一个原因：计算机的各个部件，速度差了整整几个数量级。

数据在哪 大致延迟 打个比方（从书桌到仓库）
寄存器 不到 1 纳秒 手里拿着的笔
L1 Cache 约 1 纳秒 桌面上摊开的书
L2/L3 Cache 4～20 纳秒 身后的书架
主存 约 100 纳秒 隔壁房间的书柜
SSD 数十微秒 楼下快递柜
机械硬盘 数毫秒 城郊的仓库

看最后一行：访问一次硬盘，够 CPU 空转上百万个周期。如果只有这四五层里最慢的那几层，CPU 绝大部分时间都在等数据，主频再高也没用。

那为什么不干脆全用最快的存储器？

因为物理与成本不允许。片上缓存用 SRAM（六个晶体管存一位），快、不用刷新，但面积大、贵、费电；主存用 DRAM（一个电容加一个晶体管存一位），便宜、密度高，但要不断充电刷新，慢一个数量级。容量每翻一级，单位成本降一个数量级，速度也降一个数量级。

于是只能做一件朴素的事：用很小的快速存储，去缓存那些"正在被反复使用"的数据。而"反复使用"不是猜测，是程序本身的性质。

想一想 ①：如果程序是随机地在整个内存里取数，缓存还有用吗？为什么？

二、局部性原理：程序其实很"懒"

时间局部性：刚用过的数据，很可能马上还要用。

for (int i = 0; i < n; i++)
    sum += a[i];      // i 和 sum 每一轮都被访问——时间局部性

空间局部性：用了一个地址，很可能接着用相邻地址。a[i]、a[i+1] 在内存里连着，CPU 取 a[i] 时顺手把后面几十字节一起搬进缓存，后续访问就都命中了。

这里有一条很实用的推论：同样遍历一万个元素，数组比链表快得多。不是复杂度不同（都是 O(n)），而是数组能吃到空间局部性，链表节点散落各处，每跳一次都可能是一次缓存缺失。高性能代码里，"数据结构的内存布局"往往比"算法"更影响实际速度。

理解了这一点，存储层次才有了存在的基础：快的那几层，缓存的正是这种"最近用过、位置相邻"的数据。

想一想 ②：遍历一个 std::list<int> 和一个 int[10000]，时间复杂度相同，但运行时间可能差 5～10 倍。请用本节概念解释这个差距。

三、四层结构：一条从快到慢、从小到大、从贵到便宜的阶梯

第一层：片上缓存。做在处理器核心里，SRAM，16KB～512KB，通常分 L1（指令/数据），有的再分 L2。零距离——不经总线，一个时钟周期上下就能取到。

第二层：片外缓存。在核心之外，需经交换互联开关访问，仍是 SRAM，256KB～4MB，一般称 L2/L3 Cache 或平台缓存（Platform Cache），承接片上装不下的热点数据。

第三层：主存（内存）。DRAM，独立芯片，经总线与处理器相连，数百 MB 到数十 GB。靠电容存电荷，电荷会漏，必须周期刷新；掉电即失。

第四层：外存。磁带、磁盘、光盘、各类 Flash。最慢、最大，而且掉电保持数据。这里有个容易忽略的细节：不同介质的保持年限不同——Flash 约 10 年，光盘数年至数十年，磁盘 10 年以上，磁带 30 年以上。问"哪种介质保存最久"，答案是磁带而不是硬盘。

四层连起来看：越靠近 CPU，越贵越快越小；越远离 CPU，越便宜越慢越大。所有性能优化，本质都是"让更多访问落在靠近 CPU 的那几层"。

想一想 ③：为什么"片外缓存"容量只有几 MB，却比几百 GB 的硬盘更重要？

四、命中率：把"快慢混用"变成一个数

引入命中率 h：要的数据正好在缓存里的比例；1-h 是缺失率。

命中耗时 Tc，不命中则去主存取，耗时 Tm。平均访问时间：

EAT = h × Tc + (1-h) × Tm

直觉是：95% 的访问只花 2 纳秒，5% 花 100 纳秒，平均被拉到 6.9 纳秒——比每次都访问主存快一个数量级。这就是缓存的全部意义。

这里给出的是概念描述，公式需要自己补全。而考试真正考的不是背公式，是单位是否统一、什么情况下公式会变形。

五、例题精解

例 1（工程项目：缓存收益的两条路） 某证券行情系统的报价服务，热点合约数据放在进程内缓存：命中率 92%，缓存访问 3μs，未命中时回源数据库 8ms。当前平均响应时间是多少？如果把命中率提到 96%，或者把数据库优化到 4ms，哪个更划算？

思路：先把指标统一成 μs，再套 EAT；然后分别算两条优化路径的收益，用数字比。

解答：
- 现状：EAT = 0.92 × 3 + 0.08 × 8000 = 2.76 + 640 = 642.8μs（约 0.64ms）
- 路径 A（命中率 96%）：0.96 × 3 + 0.04 × 8000 = 2.88 + 320 = 322.9μs
- 路径 B（数据库 8ms→4ms）：0.92 × 3 + 0.08 × 4000 = 2.76 + 320 = 322.8μs
- 若命中率能到 99%：0.99 × 3 + 0.01 × 8000 = 2.97 + 80 = 82.97μs

点评：A 与 B 的结果几乎一样（322.9 对 322.8），说明两条路的收益等价，该选成本低的那条——这就是工程决策。而命中率一旦推到 99%，收益又跳了一个台阶（83μs），说明命中率在高位区间的边际收益更大。这三个数字摆在一起，"该往哪儿投人力"就不再是拍脑袋。

例 2（工程选型：监控存储的分层设计） 某视频监控平台要求：4K 录像每天写入 20TB，最近 7 天可秒级回放，30 天内可查，保留期内不可丢失。请设计存储层次，并说明为什么不能全用 SSD。

解答：
- 热层（最近 7 天）：NVMe SSD 或高性能分布式存储，保证秒级回放；容量按 7×20TB=140TB 估算；
- 温层（8～30 天）：大容量 HDD 或对象存储，顺序写、批量读，容量约 460TB；
- 归档层：磁带库或冷存储，用于合规长留。
- 为什么不能全 SSD：600TB 全 SSD 的成本是 HDD 的数倍到十倍，而 8～30 天的访问频率极低；按"单位容量成本 × 访问频率"排布，才是最优解——这正是存储层次思想在系统级的翻版。

点评：CPU 里的四层缓存与这里的"热-温-冷"三层，本质是同一个模型：用小的快存储兜住高频访问，用大的慢存储承接低频数据。把这个概念迁移到架构设计上，就是 K3 要讲的"多级缓存架构"。

六、常见误区

误区一：把平均访问时间算成 h × Tm + (1-h) × Tc。 命中和缺失记反了。自检办法：代入 h=1，结果必须等于 Tc。

误区二：单位不统一。 题干可能混用 ns 与 μs，不换算差 1000 倍。例 1 里我把 8ms 换成 8000μs，就是为了避免这个坑。

误区三：多级缓存直接套单级公式。 会漏掉中间那层的贡献，正确做法是分层叠加。

还有一个容易被忽略的细节：严格来说未命中要先查缓存失败、再访问主存，耗时是 Tc + Tm，对应 EAT = hTc + (1-h)(Tc+Tm)。多数考题采用简化模型（只算 Tm），以题干给定模型为准；题干明确"缺失时先查缓存再访问主存"才用严格式。知道差别、按题选式，本身就是得分点。

第 4 节 总线与接口：部件之间怎么连

本节要解决的问题：处理器、内存、外设之间靠什么传递数据？为什么现代总线都从"并行"转向了"串行"？

一、一块采集卡插错槽引发的故障

某工控项目在机箱里加了一块高速采集卡，插上后系统起不来，换到另一个插槽就正常了。查手册发现：两个插槽外观一样，但一个是 PCIe x16 直连 CPU，另一个是 PCIe x4 经芯片组转发，带宽与供电都不同。

这类问题在工程里很常见，它背后是一个容易被忽略的事实：计算机不是一个整体，而是由若干速度、协议各不相同的部件通过"总线 + 接口"拼起来的。插槽不同，本质是挂在了不同的总线上。

二、三类总线与一个"翻译官"

总线按所处位置分三类：

类型 位置 典型作用
内总线（片上总线） 芯片内部 核与核、核与 Cache 的互连
系统总线 CPU、主存、I/O 接口之间 承载处理器与内存的数据流
外部总线（通信总线） 机箱与外设、系统与系统之间 USB、以太网、CAN、RS-485 等

计算机发展为多总线结构后，系统总线的含义有所变化：狭义上专指 CPU 与主存、通信桥连接的总线；广义上还包含由系统总线再次级联的局部总线。

三类总线之间协议不同，需要一个"翻译官"——桥（Bridge）。它是特殊的外设，负责总线协议之间的转换。上一节说"片外缓存需经交换互联开关访问"，那个开关就是桥的一种形态。

想一想 ①：如果所有部件都挂在同一根总线上，会有什么问题？为什么现代计算机要设计成多总线、多层级结构？

三、并行与串行：一条被反转的技术路线

早期的总线多是并行的：PCI、ATA(IDE) 一次传多位。但今天的高速总线几乎都改成了串行：PCIe、USB、SATA、RapidIO。

原因不是串行更快，而是并行到了高频就撑不住：

  • 并行总线要求多条线同时到达，频率越高，线间时序偏差（skew）越难对齐；
  • 线间串扰、反射问题随频率急剧恶化；
  • 布线密度上不去，走线长度被严格限制。

串行总线放弃"一次传多位"，改用差分信号 + 高速串行 + 多通道并行（如 PCIe x16 就是 16 条串行通道）。把"宽度"换成"速度"，再用多条通道换回宽度——这是过去二十年总线演进的主线。

想一想 ②：既然并行难做高频，为什么内存条（DDR）至今还是并行结构？

四、接口：同一根总线的多种"插座"

接口是同一计算机不同功能层之间的通信规则。这里列出一串常见接口，其实可以按用途归成四组：

用途 典型接口
显示 HDMI、DVI、DP
音频 TRS（耳机）、RCA、XLR
网络 RJ45、FC（光纤通道）
通用/存储/串口 USB、SATA、PS/2、LPT（打印）、RS-232

要注意接口与总线不是一一对应：一种总线可以有多种接口形态。以太网总线既能用 RJ45，也能用同轴电缆；PCIe 总线则有 x1/x4/x8/x16 多种物理形态。这也是第一节说的"一块采集卡插错槽"的根源——同样叫 PCIe，通道数和挂载位置不同，带宽差几倍。

五、外部设备：被重新划分的"输入输出"

硬件的划分是"处理器、存储器、总线、接口、外部设备"，而不是"输入设备、输出设备"。原因是：现代外设早已不是"只进或只出"——触屏既是输入也是输出，网卡既能收也能发。

外设的范围包括所有输入输出设备以及部分存储设备（即外存）。常见的有键盘、鼠标、显示器、扫描仪、摄像头、打印机、光驱、网卡、各类存储卡；移动与穿戴设备上还有加速计、GPS、陀螺仪、指纹识别；工业与航空航天领域更多：测温仪、轨迹球、红外/NFC 感应、功率驱动装置、机械臂等。

不管形态多杂，它们都通过接口与计算机主体连接，靠指令与数据实现功能。

六、例题精解

例 1（工程项目：采集卡插槽不匹配） 前述工控项目中，采集卡要求稳定 6GB/s 带宽。机箱有两个 PCIe 插槽：A 为 PCIe 3.0 x16 直连 CPU，B 为 PCIe 3.0 x4 经芯片组。请判断应该插哪个，并说明理由。

解答：
- PCIe 3.0 单通道约 1GB/s（8GT/s 编码后有效带宽约 0.985GB/s），x4 约 3.9GB/s，达不到 6GB/s；x16 约 15.8GB/s，满足要求。
- 应插 A。除了带宽，直连 CPU 还避免了与芯片组上其他设备争抢带宽、降低时延。
- 这也解释了"插 B 起不来"：部分采集卡在链路训练阶段会因带宽不足或供电不足直接初始化失败。

点评：考试里常考"某设备应接在哪种总线/接口"，答题关键不是背接口名字，而是先算带宽需求，再对通道数。

例 2（工程选型：现场总线之争） 某工厂要在车间部署 200 个传感器节点，传输距离 500 米，电磁干扰强，要求支持多主通信与优先级仲裁。候选方案是 RS-485 与 CAN，选哪个？

解答：
- 选 CAN。RS-485 只是电气层标准，能差分传输、抗干扰、支持多点，但没有协议层，多主仲裁、错误检测、优先级都要自己实现。
- CAN 在差分物理层之上定义了完整的帧格式、非破坏性位仲裁、CRC 校验与错误帧，天然支持多主与优先级——正好匹配"200 节点 + 仲裁需求"。
- 若只是点对点或单主轮询、成本极紧，RS-485 更简单便宜。

点评：这题的区分点是"电气标准 vs 完整协议"。工程上很多选型错误，都是把"能连上"当成了"能协同"。

七、常见误区

误区一：认为 PCIe 是并行总线。
PCIe 的每个通道（lane）是串行差分链路，x16 是 16 条独立串行通道并行工作，不是传统意义的多位并行总线。

误区二：把接口当成总线。
接口是"插座与规则"，总线是"传输通道"。同一总线可对应多种接口形态。

误区三：认为 USB 只能接"外设"。
USB 也承载存储（U 盘、移动硬盘）、网络（USB 网卡）、显示（DisplayLink），它已是通用外部总线。

误区四：以为外设就是输入输出设备。
软考口径里，外设还包括部分外存（存储卡、光驱、移动硬盘）。

第 5 节 操作系统：谁在分配资源

本节要解决的问题：多个程序同时要 CPU、要内存、要磁盘时，按什么规则分配？为什么"CPU 占用率 100%"有时反而是好事？

一、一台"很忙但没干活"的服务器

某业务服务器监控告警：CPU 使用率连续几天 100%，运维准备扩容。但查下去发现，系统每秒只处理几十个请求——CPU 忙，是在空转等 IO。

同一台机器，换个角度看：磁盘队列排了几十个请求，内存里有一半是缓存。也就是说，三个部件都很"忙"，但真正干活的没几个。

这就是操作系统要解决的核心问题：资源是有限的，请求是并发到来的，必须有规则去分配和调度。我们把操作系统定义为"计算机系统的资源管理者"，一句话点到了本质——它管的不是程序，是资源。

二、操作系统管什么、为什么需要它

我们把内核的职责归纳为四块：进程（任务）管理、存储管理、文件管理、设备管理。所有上层软件——编译器、数据库、浏览器——都建立在这四块能力之上。

操作系统有三个作用：

  1. 管理运行的程序、分配软硬件资源。避免冲突，保证程序有序运行。
  2. 提供友善的人机界面。图形界面、命令行，本质都是"让人不用直接操作硬件"。
  3. 为应用程序提供高效平台。个很准确的说法：装了操作系统后，呈现在应用面前的是"一台虚拟计算机"——它屏蔽了物理设备细节，用系统调用和库函数提供统一接口。

四个特征（考试常考）：

  • 并发性：宏观上多个程序同时推进，微观上单核一次只执行一个。
  • 共享性：资源可被多个并发进程共同使用，分同时共享与互斥共享。
  • 虚拟性：把物理上的一个实体变成逻辑上的多个（如虚拟内存），或反过来。
  • 不确定性：进程何时执行、何时暂停、何时完成不可预知，因此程序执行结果可能不唯一。

想一想 ①：为什么"不确定性"被列为操作系统的特征，而不是缺点？如果系统完全没有不确定性，会付出什么代价？

三、七类操作系统：按"调度目标"分，而不是按功能分

这里列出七类：批处理、分时、实时、网络、分布式、微机、嵌入式。死记容易乱，抓住每类的调度目标就清楚了：

类型 目标 典型做法 代价
批处理（单道/多道） 吞吐量 作业排队，IO 时切换给下一个作业 响应慢，用户无交互
分时 响应时间 时间片轮转（如 20 个终端 × 50ms 一片） 上下文切换开销
实时 确定性/截止时间 优先级抢占，最坏情况可预测 平均性能不高
网络 资源共享 通信协议 + 目录服务 依赖网络
分布式 透明性 统一视图、任务划分 复杂度高

一个具体例子：20 个终端的分时系统，每个用户分配 50ms 时间片，每隔 1 秒就能为所有用户服务一遍。这就是"用响应时间换吞吐"的量化表达。

实时系统再分两类：实时控制系统（数据采集、武器控制、飞机自动驾驶）和实时信息处理系统（订票、情报检索）。前者要求硬实时，后者多为软实时。

想一想 ②：为什么实时系统"对交互能力要求不高，但要求可靠性有保障"？如果给实时系统加一个漂亮的图形界面，会带来什么风险？

四、考纲要求、但容易一带而过的三块（补充）

本章只讲操作系统的概念、作用、特征与分类，不展开进程调度、分页存储、死锁。但这三块是上午题的常客，所以下面单独补上，做题时诊断标签会标 B。

(1) 进程与线程。 进程 = 程序 + 数据 + PCB，是资源分配的基本单位；线程是调度的基本单位，共享进程的地址空间，切换开销小。进程有三态：就绪、运行、阻塞，合法转换是"就绪↔运行、运行→阻塞、阻塞→就绪"，不允许"阻塞→运行"。

(2) 调度算法与周转时间。 常见四种：先来先服务（FCFS）、短作业优先（SJF）、优先级、时间片轮转。

周转时间 = 完成时间 − 到达时间；带权周转时间 = 周转时间 / 运行时间。

(3) 分页与页面置换。 页式存储把地址空间等长切分，逻辑地址 = 页号 + 页内偏移；页内偏移位数 = log₂(页面大小)。置换算法有 OPT（最优但不可实现）、FIFO（会出现 Belady 异常：页框增多反而缺页更多）、LRU、Clock。

五、例题精解

例 1（工程项目：批处理平台的调度选择） 某数据平台每晚跑批，5 个作业的到达时间都是 0，运行时间分别为 12、6、4、3、1 分钟。分别用 FCFS（按给定顺序）与 SJF 计算平均周转时间，并说明为什么生产上不一定选 SJF。

解答：
- FCFS：完成时间 12、18、22、25、26 → 平均 (12+18+22+25+26)/5 = 20.6 分钟
- SJF：按 1、3、4、6、12 执行 → 完成时间 1、4、8、14、26 → 平均 (1+4+8+14+26)/5 = 10.6 分钟

SJF 把平均周转时间几乎砍半，但它有两个工程问题：必须预知运行时间（实际只能用历史均值估算），以及长作业可能饿死（不断有短作业插队）。生产上通常用"优先级 + 老化"或"时间片 + 分级队列"折中。

点评：这道题的考点不是算对 10.6，而是最后那句"为什么生产上不一定选最优解"——这正是论文里写"做了权衡"的素材。

例 2（工程计算：页式地址变换） 某系统页面大小 4KB，逻辑地址 32 位。求页内偏移位数、页号位数，以及单个进程最大页表项数。

解答：
- 4KB = 2¹² → 页内偏移 12 位
- 页号 = 32 − 12 = 20 位
- 页表最多 2²⁰ ≈ 104 万个表项。这也是为什么大地址空间必须用多级页表——单级页表本身就占 4MB。

六、常见误区

误区一：并发等于并行。
单核也能并发（时间片轮转），并行必须多核同时执行。判断标准是"物理上是否同时"。

误区二：CPU 使用率高 = 系统忙 = 该扩容。
本例的 100% 很可能是在等 IO 自旋。要看的是有效吞吐与IO 等待占比，不是 CPU 数字本身。

误区三：把进程当成"运行中的程序"。
进程还包含 PCB 与资源上下文；同一程序跑两份就是两个进程。

误区四：FIFO 置换算法"公平所以不会差"。
FIFO 存在 Belady 异常，页框增加缺页率反而上升，这是它被 LRU 取代的原因。

一、一个"三套数据"的老问题

某零售企业的订单数据，交易系统用关系库，报表系统另存一份到数据仓库，审计部门还要导出 Excel 归档。结果是：三套数据口径不一致，对账要三天。

这不是工具问题，而是数据组织方式没设计好。我们把数据库定义为"长期存储在计算机内、有组织、统一管理的相关数据的集合"——注意三个关键词：有组织、统一管理、可共享。这三点恰好是"三套数据"的反面。

二、数据库的类型谱系

的分类很实用，按存储体系分：

类型 特点 典型场景
关系型 数据组织成二维表，用关系运算操作 交易、账务
键值（KV） 简单键值对，键唯一标识 会话、缓存

三、关系模型与数据库设计六阶段

关系可以理解为二维表。选课的例子给出：

学生（学号，姓名，年龄，系别）
课程（课程号，课程名，学分）
选课（学号，课程号，分数）

其中带下划线的是主码——主码能唯一确定某个实体（学号能唯一确定一个学生）。

数据库设计分六个阶段：需求分析 → 概念结构设计（E-R 模型）→ 逻辑结构设计 → 物理结构设计 → 应用程序设计 → 运行维护。概念设计最常用的方法是 E-R 方法，分三步：设计局部 E-R 模型 → 设计全局 E-R 模型 → 全局模型优化。

这套流程在下午案例题里经常考"补全 E-R 图""判定范式"。更细的范式与 SQL 会在 K4（第 6 章）展开，本节只需记住阶段顺序与"概念设计产出 E-R 图"。

四、分布式数据库：四层模式

这里给出我国《分布式数据库系统标准》中的四层结构：

全局外层（全局视图）
   ↕ 映射
全局概念层（全局概念模式 → 分片模式 → 分配模式）
   ↕ 映射
局部概念层（局部概念模式）
   ↕
局部内层（局部内模式）→ 局部数据库

关键在中间那层：分片模式决定"数据怎么切"，分配模式决定"切片放哪"。这四层对同构、异构分布式库都适用。

判断一个分布式数据库是否"完全分布"，看四点：分布性、逻辑相关性、场地透明性、场地自治性。

五、文件系统：数据库之下的一层

不是所有数据都值得进数据库。日志、图片、备份这类，直接放文件系统更划算。文件系统要解决三件事：

1. 文件的物理结构。 三种选择：

  • 连续分配：读写最快，但文件增长困难、有外碎片；
  • 链接分配：易扩展，但随机访问差（要顺着链走）；
  • 索引分配：用索引结点（inode）记录块号，随机访问好，代价是索引本身占空间。

2. 空闲空间管理。 这里列出三种：空闲区表、位示图、空闲块链。位示图用一位表示一个块是否被占，大小由物理块总数决定——这是考试的计算点。

3. 链接方式。 硬链接是"两个目录项指向同一个索引结点"，删掉一个另一个还在；符号链接存的是路径，源文件删了就失效。

六、例题精解

例 1（工程计算：位示图容量） 某视频平台用位示图管理 2TB 的存储池，块大小 4KB。求位示图需要多少字节；若每 32 位为一个字，需要多少字？

解答：
- 块数 = 2TB / 4KB = 2×2⁴⁰ / 2¹² = 2²⁸ ≈ 2.68 亿块
- 位示图位数 = 块数 = 2²⁸ bits → 字节数 = 2²⁸ / 8 = 2²⁵ = 33,554,432 字节 ≈ 32MB
- 每字 32 位 → 字数 = 2²⁸ / 32 = 2²³ = 8,388,608 字

点评：32MB 看起来很占内存，但相比 2TB 的容量只占十万分之一——这正是位示图被广泛使用的原因：用极小的元数据换极快的空闲块定位。

例 2（工程权衡：订单数据该放哪） 某电商的"订单评论"需要支持：按订单查、按商品查最近 100 条、全文搜索关键词。请给出存储方案并说明理由。

解答：
- 主体存关系库（订单-评论关联、强一致、事务）；
- 按商品查最近 N 条建宽表或列存储（按商品 ID 分区，只读少数字段）；
- 全文检索交给搜索引擎（倒排索引）；
- 三者通过消息队列异步同步，接受秒级延迟，用最终一致换查询性能。

点评：这是"一种数据、多种查法"的典型解——不要试图让一个存储满足所有访问模式，而要按访问模式拆存储、用同步机制保持一致。这个思路在 K4 与 K3（多级缓存）里会反复出现。

七、常见误区

误区一：把"文档数据库"当成"文件系统"。
文档库有索引、可查询、支持事务语义（部分产品）；文件系统只提供字节流的存取。

误区二：认为分布式数据库的"分片"就是"分表"。
分片是逻辑层概念（全局概念层），落地到物理才涉及具体存储；分表更多是应用层的实现手段。

误区三：认为硬链接可以跨文件系统。
硬链接共享同一 inode，inode 号只在单个文件系统内唯一，所以不能跨；符号链接存路径，可以跨。

误区四：把 E-R 设计放到逻辑设计阶段。
E-R 建模属于概念结构设计，逻辑设计是把 E-R 图转换成具体数据模型（关系/层次/网状）。

第 7 节 中间件与软件构件：异构系统怎么连

本节要解决的问题：20 个来自不同厂商、跑在不同平台上的系统，如何互不干扰地协作？

一、银行里的 20 个系统

某银行的账户、支付、信贷、风控、报表分别由不同厂商建设，运行在 AIX、Linux、Windows 上，用 Oracle、DB2、SQL Server。若让每个系统两两对接，需要 20×19/2 = 190 条接口。

中间件要做的，就是把这些"两两对接"变成"统一接入"——用一层标准化的服务，把异构性挡在外面。

这里的定义很直接：中间件处在操作系统、网络和数据库之上，应用软件的下层；它让应用能在不同平台上运行、实现相同的功能。

二、中间件的八类职责

按在分布式系统中承担的职责，分为八类，这是本节的核心考点：

类型 解决什么 代表产品
通信处理（消息）中间件 可靠、高效、实时的跨平台数据传输 IBM MQSeries、BEA eLink、TongLINK
事务处理（交易）中间件 大量 OLTP 事务的并发、负载均衡、故障切换 BEA Tuxedo
数据存取管理中间件 异构数据源的虚拟缓冲、格式转换、解压 —
Web 服务器中间件 扩展 HTTP 的会话与写入能力 SilverStream
安全中间件 国产化的加密、认证、防火墙等安全能力 —
跨平台和架构中间件 集成不同平台/版本的构件 CORBA、COM+、JavaBeans
专用平台中间件 特定领域（电商、网站）的参考架构与构件库 —
网络中间件 网管、接入、测试、虚拟社区等 —

有一点要特别记住：消息中间件是市面上销售额最大的中间件产品。

想一想 ①：消息中间件和事务中间件都能"连接系统"，它们的根本区别是什么？提示：一个关心"送到没送到"，一个关心"一起成功或一起失败"。

三、两件"代表作"的差别

MQSeries（消息中间件）：核心是消息 + 队列。关键能力是可靠传输——即使网络不可靠或对端应用"忙"甚至故障，消息也不丢、不阻塞。它实现的是异步解耦：发送方发完就走，接收方什么时候处理都行。

Tuxedo（交易中间件）：核心是事务协调。OLTP 场景下一笔业务要跨多台服务器按顺序完成，中间任何一步故障，不仅要恢复，还要自动切换保证不停机。它实现的是同步的一致性保障。

这个区别决定了选型：跨系统通知、削峰、最终一致选消息；强一致、短事务、高并发 OLTP 选交易中间件。

四、软件构件：复用的一层封装

我们把"软件构件"单列一节，落脚点是复用。构件的核心思想是：把可复用的功能封装成有明确接口、可独立部署的单元。

与之相关的工程方法是 CBSE（基于构件的软件工程）：构件模型（定义构件长什么样）→ CBSE 过程（怎么开发与组装）→ 构件组装（怎么拼起来）。这部分在 K7（第 5 章 5.6）会展开，本节只需记住：构件 = 接口 + 实现 + 可独立部署。

五、应用软件：专用与通用的分界

我们把应用软件分两类：

  • 专用：为一个单位、一类业务定制（如某银行的信贷系统）；
  • 通用：面向大众市场（如 Office、财务软件包）。

判断标准不是"复杂程度"，而是服务对象的范围。这也解释了一个常见困惑：为什么同样叫"管理系统"，有的是产品（通用），有的是项目（专用）——前者卖 license，后者卖实施。

六、例题精解

例 1（工程项目：中间件选型） 某银行要打通"柜面系统"与"核心账务系统"：一笔转账需在两边同时记账，任一步失败必须整体回滚，峰值 3000 TPS。另有一个"客户画像"系统，需要把交易流水异步推送给风控，允许分钟级延迟。请分别选择中间件类型。

解答：
- 转账：选事务处理（交易）中间件（如 Tuxedo 类）。理由是要求跨系统强一致、失败整体回滚、高并发短事务；消息中间件只能保证"至少一次送达"，不保证两边同时成功。
- 画像推送：选消息中间件（如 MQSeries/Kafka 类）。理由是允许异步与延迟，需要削峰与解耦，发送方不应被下游阻塞。

点评：同一家企业、同一批系统，两套中间件并存是常态。选型的分水岭是"一致性要求"，不是"技术新旧"。

例 2（工程权衡：190 条接口怎么收） 前述 20 个系统两两对接，改造方案有三种：① 全部点对点；② 引入 ESB 统一接入；③ 建统一 API 网关 + 消息总线。请比较优劣。

解答：
- ① 点对点：改动小、上线快，但接口数随系统数平方增长，运维不可控；
- ② ESB：协议转换、路由、监控集中，但 ESB 本身可能成为单点与瓶颈，团队需专门维护；
- ③ 网关 + 消息总线：HTTP 同步走网关、异步走消息，职责清晰、易水平扩展，但需要治理（限流、鉴权、版本管理）。

工程上常见的是 ③，把 ESB 的"重"拆成"网关 + 总线"两件"轻"的东西——这正是 K9（云原生/SOA）里"服务网格"与"API 网关"分工的雏形。

第 8 节 嵌入式系统：资源受限时怎么取舍

本节要解决的问题：只有几 MB 内存、要靠电池跑十年、还要在 10 毫秒内响应——这样的系统怎么设计？

一、一个刹车信号的时限

汽车 ECU 收到刹车踏板信号后，必须在 10 毫秒内点亮刹车灯并通知 ABS。晚 100 毫秒，后果不是"卡顿"，是事故。

这就是嵌入式与通用计算机的根本差别：它不是让你用得更爽，而是必须在确定的时间内完成确定的事。嵌入式软件的描述紧扣这一点——专用、实时、可靠。

二、组成与特点

嵌入式系统由硬件（处理器、存储器、I/O）+ 软件（OS、中间件、应用）组成，特点可以概括为四条：

  • 专用性强：为一个具体设备服务，功能固定；
  • 资源受限：内存小、字长短、算力有限、供电受限；
  • 实时性：必须在截止时间内响应；
  • 可靠性：常年在无人值守环境下运行。

嵌入式操作系统的五点要求，几乎就是为上述约束量身定做的：

要求 为什么
微型化 内存少、字长短、能耗低
可定制 同一 OS 要适配不同 MCU 与硬件配置
实时性 过程控制、数据采集必须及时响应
可靠性 关键要害领域要容错、防故障
易移植性 靠 HAL（硬件抽象层）+ BSP（板级支撑包） 实现

HAL 与 BSP 是这一节唯一需要"理解而不是背"的概念：HAL 把"硬件相关"的代码隔离成一层接口，BSP 提供"这块板子"的具体实现。换一块板子，只改 BSP，上层不动。

想一想 ①：既然嵌入式要"微型化"，为什么不干脆写裸机程序、不要操作系统？

三、实时不是"快"，是"可预测"

这是最容易被误解的一点：实时 ≠ 高性能。实时追求的是最坏情况可预测——每次执行都能在截止时间前完成，而不是平均很快。

两类实时调度算法常考：

  • RMS（速率单调调度）：静态优先级，周期越短优先级越高，适合固定周期任务；
  • EDF（最早截止优先）：动态优先级，截止时间越近越先执行，利用率更高但实现更复杂。

判断 RMS 是否可调度有个经典判据（Liu & Layland 界）：

∑CiTi ≤ n(21/n-1)

当 n=3 时，界约为 0.78；利用率低于这个值一定可调度，高于它不一定不可调度（只是判据失效，需精确分析）。

四、安全攸关软件：DO-178

当嵌入式软件出问题会危及人身安全时，就进入"安全攸关"范畴。这里给出的标准是 DO-178B/C，它把软件生命周期分为三个过程：

  1. 软件计划过程：策划与协调全部生命周期活动，产出各类计划与标准；
  2. 软件开发过程：含需求、设计、编码、集成四个子过程；
  3. 软件综合过程：含验证、配置管理、质量保证、审定联络四个子过程。

专门比较了 DO-178 与 CMMI 的三点差异：

  • 视角不同：DO-178 从适航审定出发，关注"软件质量对安全性的影响"；CMMI 从过程改进出发，关注"组织整体能力提升"；
  • 组成不同：DO-178 由目标、活动、数据组成，要求具体；CMMI 由实践组成，是各行业最佳实践的抽象；
  • 范围不同：DO-178 聚焦软件，表述清晰；CMMI 集成系统/软件/硬件，易产生歧义。

一句话记：DO-178 管"这款软件能不能上飞机"，CMMI 管"这家公司会不会做软件"。

五、例题精解

例 1（工程判断：要不要上 RTOS） 某智能门锁项目：需要按键响应、蓝牙通信、指纹识别、低功耗待机。团队争论"用裸机轮询还是上 RTOS"。请给出判断依据。

解答：
- 若功能之间没有硬实时约束、逻辑简单，裸机轮询（前后台结构）功耗更低、启动更快、代码量小，是合理选择；
- 一旦出现"指纹识别耗时长，但按键必须立即响应"这类并发 + 时限需求，轮询会阻塞响应，就应上 RTOS，用任务优先级保证关键路径；
- 折中方案：主循环 + 中断处理关键事件（中断服务程序极短），也能满足多数家电级需求。

点评：这题的答案是"看约束"，而不是"RTOS 更专业"。嵌入式领域最常见的过度设计，就是给一个只需轮询的设备上 RTOS，白白增加内存占用与启动时间。

例 2（工程计算：RMS 可调度性） 三个周期任务：T1（C=1ms, T=4ms）、T2（C=2ms, T=8ms）、T3（C=3ms, T=16ms）。用 Liu & Layland 判据判断是否可调度。

解答：
- 利用率 U = 1/4 + 2/8 + 3/16 = 0.25 + 0.25 + 0.1875 = 0.6875
- n=3 时判据界 = 3×(2^(1/3)−1) ≈ 3×0.2599 ≈ 0.7798
- 0.6875 < 0.7798 → 满足充分条件，一定可调度

点评：注意这只是充分条件。U 超过界不代表不可调度，需要用响应时间分析（RTA）做精确判断——考试若问"是否一定可调度"，答案取决于是否满足充分条件。

六、常见误区

误区一：实时系统 = 高性能系统。
实时追求可预测的最坏情况，很多实时系统的平均性能并不高，甚至刻意降低主频以保证时序确定。

误区二：认为 HAL 和 BSP 是一回事。
HAL 是抽象接口层（与具体芯片无关），BSP 是针对某块板子的实现（含驱动、启动代码）。

误区三：把 DO-178 当成"开发方法"。
它是审定标准，规定"要达到什么目标、产出什么数据"，不规定具体开发流程。

本节要解决的问题：一次 HTTPS 请求从客户端到服务器，要经过哪些层、哪些设备、哪些协议？

一、一次请求的旅程

你在浏览器输入网址、回车，几百毫秒后页面出现。这期间发生了：DNS 解析域名 → 建立 TCP 连接 → TLS 握手 → 发 HTTP 请求 → 经过交换机、路由器逐跳转发 → 服务端处理 → 原路返回。

每一跳都在做一件事：把数据交给"下一层"或"下一跳"。分层的意义，就是让每一层只关心自己的事。

二、两个模型：OSI 七层与 TCP/IP 四层

OSI 七层 TCP/IP 四层 关键协议
应用层 / 表示层 / 会话层 应用层 HTTP、FTP、SMTP、DNS、SNMP、Telnet、NFS
传输层 传输层 TCP、UDP
网络层 网际层 IP、ICMP、ARP、RARP
数据链路层 / 物理层 网络接口层 以太网、PPP、FDDI

记忆抓手：TCP/IP 把 OSI 的"高三层"合成了应用层，"低两层"合成了网络接口层。网际层的四个协议（IP、ICMP、ARP、RARP）是高频考点：IP 负责寻址路由，ICMP 负责差错报告（ping 用的就是它），ARP 把 IP 解析成 MAC，RARP 反过来。

三、设备与层级的对应

这是考试里最容易拿分也最容易错的一类题，记住这张对应表即可：

设备 工作层次 判断依据
中继器、集线器 物理层 只放大/转发电信号，不识别帧
网桥、交换机 数据链路层 按 MAC 地址转发，隔离冲突域
路由器 网络层 按 IP 与路由表转发，隔离广播域
防火墙 门户过滤 按规则检查进出流量

交换机的工作机制值得多说一句：学习（记源 MAC 与端口）→ 转发（查目的 MAC）→ 泛洪（查不到就向除源端口外所有端口发）→ 老化（约 300 秒更新一次）。为避免环路，用 STP 生成树协议；为提升带宽与可靠性，用链路聚合（802.3ad）。

四、路由：两种算法的取舍

路由协议分两类：

  • 内部网关协议（IGP）：自治系统内部。又分距离矢量（只知邻居，易环路，适合小网）与链路状态（掌握全网拓扑，收敛快，OSPF/IS-IS 属于此类）；
  • 外部网关协议（EGP）：自治系统之间，主要是 BGP。

一个实用的判断很实用：小网用距离矢量易配置；大网必须链路状态，否则环路与带宽消耗都撑不住。

六、例题精解

例 1（工程计算：子网划分） 某公司分到 192.168.10.0/24，需要划分为 6 个子网，每个子网至少 25 台主机。请给出子网掩码与可用地址数。

解答：
- 需要 6 个子网 → 至少借 3 位（2³=8 ≥ 6），掩码从 /24 变 /27（255.255.255.224）；
- 每个子网主机位 = 32−27 = 5 位 → 2⁵ = 32 个地址，扣除网络号与广播地址，可用 30 台（≥25 满足）；
- 8 个子网、每个 30 台，正好覆盖需求，且留有 2 个子网余量。

点评：这类题的标准流程是"先算子网数 → 再算主机数 → 取能同时满足的最小借位数"。借位过多会浪费地址，过少则不满足主机数。

例 2（工程排障：为什么交换机不能隔离广播） 某办公网 200 台机器接在同一台三层交换机上，广播风暴导致全网变慢。请分析原因与解决办法。

解答：
- 交换机工作在数据链路层，隔离的是冲突域，不隔离广播域——所有端口同属一个广播域，广播帧会被泛洪到所有端口；
- 解决办法是划分 VLAN：在交换机上把端口划入不同 VLAN，每个 VLAN 是一个独立广播域；跨 VLAN 通信必须经过三层（路由或三层交换）；
- 若还需控制广播规模，可进一步用路由器或三层交换机做子网划分。

点评：这题的考点是"冲突域与广播域的区别"，也是"交换机 vs 路由器"最常见的考法。

七、常见误区

误区一：认为交换机可以隔离广播域。
交换机隔离冲突域；隔离广播域要靠 VLAN 或路由器。

误区二：把 OSI 七层与 TCP/IP 四层一一对应。
TCP/IP 的四层是合并后的结果，应用层对应 OSI 的高三层，不存在"四层对应七层"的一一映射。

误区三：香农公式直接代 dB 值。
dB 是信噪比的对数表示，必须先换算成比值再代入。

误区四：认为 STP 是用来"加速"的。
STP 是为了消除环路（阻塞冗余链路），代价是牺牲部分带宽；链路聚合才是提升带宽的手段。

留一个问题：网络解决了"机器之间怎么通信"，可机器只认识 0 和 1。人写的代码，是怎么变成机器能执行的指令的？

下一节讲计算机语言。

第 10 节 计算机语言：人怎么指挥机器

本节要解决的问题：人写的代码经过哪些步骤变成机器指令？为什么"同一份代码换个平台就要重编译"？

一、从一行代码到一条指令

你写下 a = b + c，机器最终执行的是类似 ADD R1, R2, R3 的一条指令。中间发生了什么？

我们把计算机语言定义为"人与计算机之间传递信息的媒介"，主要由指令组成，指令包含三部分：表达式（变量、常量、字面量、运算符）、流程控制（分支、循环、函数、异常）、集合（字符串、数组、散列表）。

这三分法看似简单，其实涵盖了所有编程语言的骨架——把任何一门语言拆开，都能归到这三类。

二、语言的五代：从 0/1 到形式化

按发展历程分为五类：

层次 语言 特点
第一代 机器语言 指令系统本身，是计算机的"本地语"；执行快、占内存少，但不可读、不可移植
第二代 汇编语言 用助记符替代二进制串（ADD、MOV）；仍是面向机器的语言，需汇编程序翻译
第三代 高级语言 面向问题、可移植，需编译或解释
建模语言 UML 等 描述结构与行为，不直接执行
形式化语言 数学化描述 用于规约与验证

机器语言的指令格式是考点：一条指令由操作码与地址码组成。按地址域的数量分为三地址、二地址、单地址、零地址（堆栈机）、可变地址数。操作码长度取决于指令条数（如 256 条指令需 8 位操作码）。

想一想 ①：为什么"零地址指令"能在堆栈型计算机上工作？它的操作数从哪来？

三、编译与解释：两种"翻译"策略

  • 编译：先把整个源程序翻译成目标代码，再执行。优点是执行快、可优化；缺点是不跨平台（换个 CPU 架构要重新编译）。
  • 解释：逐句翻译并立即执行。优点是跨平台、调试方便；缺点是执行慢。

Java 的折中值得单独提一句：先编译成字节码（跨平台的中间表示），再由 JVM 解释/即时编译执行——这解释了"一次编写，到处运行"的由来，也解释了为什么 JVM 本身要针对不同平台各写一套。

四、例题精解

例 1（工程计算：指令编码） 某嵌入式处理器有 60 条指令，采用定长指令格式，指令字长 16 位。若采用单地址格式，地址字段最多能表示多少个存储单元？

解答：
- 60 条指令需 6 位操作码（2⁵=32 < 60 ≤ 2⁶=64）；
- 剩余地址位 = 16 − 6 = 10 位；
- 地址字段可表示 2¹⁰ = 1024 个存储单元。

点评：这类题的关键是"操作码位数由指令条数决定，剩余全给地址"。若题目改成"二地址"，则每个地址字段分 5 位（1024→32），要看清地址字段是共享还是各占一半。

例 2（工程选型：为什么选解释型） 某低代码平台要在浏览器里运行用户拖拽生成的逻辑，需要热更新、可随时回滚。选编译型还是解释型方案？

解答：
- 选解释/字节码执行方案。理由：用户逻辑在运行时才能确定，无法提前整体编译；解释执行支持热更新与快速回滚；配合沙箱可限制资源与权限。
- 代价是执行效率低于 AOT 编译，因此常用"热点代码即时编译（JIT）"折中。

点评：语言与执行方式的选择，本质是"确定性 vs 灵活性"的权衡，与第 6 节"一种数据多种查法"是同一类思路。

五、常见误区

误区一：认为汇编语言不是"面向机器"的语言。
它只是机器语言的符号化，仍依赖具体指令系统，可移植性差。

误区二：把"编译型语言"与"静态类型语言"混为一谈。
前者说的是翻译时机，后者说的是类型检查时机，两回事。

误区三：认为解释执行一定比编译执行慢很多。
有 JIT 后差距大幅缩小，热点代码甚至可接近编译型性能。

留一个问题：文本、图像、音频、视频这些非结构化数据，计算机怎么处理？

下一节讲多媒体。

第 11 节 多媒体：非结构化数据怎么处理

本节要解决的问题：一段 4K 视频每秒产生上 GB 数据，怎么在有限带宽与存储下传输与呈现？

一、一个算不平的账

4K 视频按原始像素算：3840×2160×3 字节×30 帧/秒 ≈ 746 MB/s。一部两小时的电影就是 5 TB 以上——无论带宽还是硬盘都撑不住。

所以多媒体技术的核心命题只有一个：压缩与实时。压缩解决"存不下、传不动"，实时解决"播放时不能卡"。

二、媒体的五类划分

我们把媒体分为：感觉媒体（人直接感知的，如声音、图像）、表示媒体（编码形式，如 JPEG、MP3）、表现媒体（输入输出设备，如摄像头、显示器）、存储媒体（如光盘、硬盘）、传输媒体（如光纤、电缆）。

考试常考"某个东西属于哪类"：编码格式属于表示媒体，摄像头属于表现媒体——这两个最容易混。

三、关键技术：压缩是主线

多媒体系统的关键技术，重点是数据压缩：

  • 无损压缩：Huffman 编码、算术编码、LZW。解压后与原始数据完全一致，适合文本、医疗影像、程序。
  • 有损压缩：JPEG（图像）、MPEG（视频）、MP3（音频）。丢弃人眼/人耳不敏感的信息，压缩比可达几十倍。

为什么能有损：因为人的感知有阈值——人眼对亮度敏感、对色度迟钝（JPEG 就利用这点做色度下采样）；人耳有掩蔽效应（MP3 就丢掉被强音掩盖的弱音）。

想一想 ①：为什么手术影像必须用无损压缩，而流媒体视频可以用有损？判断标准是什么？

四、VR/AR 的四种形态

我们把 VR/AR 技术分为四类，考点在"特点匹配"：

类型 特点 适用
桌面式 VR 易实现、应用广泛、成本较低，但受环境干扰、缺体验感 教学演示
分布式 VR 多用户共享同一虚拟环境，共享度高但研发成本极高 专业训练
沉浸式 VR 完全沉浸、全身参与，实时交互好，但硬件与混合技术要求高 高端体验
增强式 AR 虚拟与现实叠加，体验更完美，但混合技术要求最高、起步晚 工业维修、导航

关键技术包括：数据采集与优化传输（全向相机、高速摄像机、激光设备）、交互与情形实时再现（力觉/触觉反馈、跟踪定位、渲染、显示）。

五、例题精解

例 1（工程权衡：直播方案设计） 某在线教育平台要做 1 万人在线的直播课，要求延迟低于 3 秒、国内多地域可看、成本可控。请给出技术方案并说明取舍。

解答：
- 编码：H.264/H.265 有损压缩，按带宽自适应多码率（540p/720p/1080p）；
- 传输：RTMP 推流 → 转码集群 → CDN 分发（边缘节点就近服务），而非源站直出；
- 取舍：低延迟与成本天然冲突——用 CDN 换延迟与并发，用有损压缩换带宽；若要求"抖动能忍、延迟不能忍"，可换 WebRTC，代价是并发成本更高。

点评：多媒体方案的评价维度永远是三个：画质、延迟、成本，三者不可同时最优，必须按业务定优先级。

例 2（工程判断：存储与压缩的选择） 某医院 PACS 系统存 CT 影像，要求诊断级精度、可回溯 15 年。是否可用 JPEG 有损压缩？

解答：
- 不可。诊断级影像要求像素级保真，有损压缩可能抹掉早期病灶的细微差别；医疗影像通常要求无损或近无损压缩（如 JPEG-LS、JPEG2000 无损模式）。
- 存储上采用分层：近线用高速存储、归档用磁带库（保持年限最长），配合压缩与去重。

点评：这题与第 3 节"监控存储分层"是同一套思路：按数据价值与访问频率分层，而不是一刀切。

六、常见误区

误区一：把编码格式当成存储媒体。
JPEG/MP3 是表示媒体（编码形式），光盘、硬盘才是存储媒体。

误区二：认为有损压缩"质量差"。
在感知阈值内的有损压缩，人眼几乎无法分辨，压缩比却可达数十倍，这是流媒体的基础。

误区三：认为 VR 一定比 AR 高级。
二者解决不同问题：VR 是"进入虚拟世界"，AR 是"虚拟叠加现实"。AR 对混合技术（跟踪、配准、光照一致性）要求更高。

第 12 节 系统工程：复杂系统怎么组织

本节要解决的问题：面对一个涉及多种专业、跨越数年的复杂工程，用什么框架把它拆开、排好、管住？

一、为什么需要"系统工程"

造一台交换机是工程问题；建一张覆盖全省的政务云，是系统问题——它同时涉及网络、机房、安全、数据、应用、运维、预算、合规，还有十几个部门。

系统工程的定位是"一种组织管理技术"：它不是某一门专业技术，而是把多种专业组织起来达成整体目标的方法。

二、霍尔三维结构：把复杂拆成三个维度

这是本节唯一必须记住的模型。霍尔（A.D. Hall）把系统工程活动拆成三维：

时间维（按时间顺序的 7 个阶段）：

规划 → 拟订方案 → 研制 → 生产 → 安装 → 运行 → 更新

逻辑维（每个阶段内要走的 7 个步骤）：

明确问题 → 确定目标 → 系统综合 → 系统分析 → 优化 → 决策 → 实施

知识维（需要的专业知识）：工程、医学、建筑、商业、法律、管理、社会科学、艺术等。

记忆口诀：时间维"规拟研生安运更"，逻辑维"问目综析优决实"。

它的价值在于：任何一个工程阶段，都可以用同一套逻辑步骤去推。比如"研制"阶段，也要走"明确问题→确定目标→…→实施"这七步。

想一想 ①：为什么"决策"排在"实施"之前、"优化"之后？如果把决策放到最前面，会出什么问题？

三、生命周期与 MBSE

讲了系统工程的生命周期，以及基于模型的系统工程（MBSE）。

区别一句话概括：传统系统工程靠文档传递，MBSE 靠模型传递。文档的问题是"各写各的、对不上"；模型的好处是"改一处、全局一致"，且可仿真验证。

MBSE 与第 5 节讲的 DO-178、第 8 节的嵌入式开发是同一趋势：从文档驱动转向模型驱动。

四、例题精解

例 1（工程项目：用霍尔三维拆解） 某市要建"智慧交通"项目：整合 2000 个路口信号、公交调度、停车诱导、应急指挥，工期 3 年。请用霍尔三维说明如何组织。

解答：
- 时间维：规划（顶层设计与可行性）→ 拟订方案（技术路线比选）→ 研制（平台与接口开发）→ 生产（设备批量制造）→ 安装（路口改造与联网）→ 运行（试运行与运维）→ 更新（迭代升级）；
- 逻辑维（以"规划"阶段为例）：明确问题（拥堵点在哪）→ 确定目标（通行效率提升 15%）→ 系统综合（提出多种方案）→ 系统分析（评估各方案）→ 优化 → 决策 → 实施（立项）；
- 知识维：交通工程、通信、软件、数据治理、法规（数据共享合规）、项目管理。

点评：这类题的关键不是把 7×7 全写出来，而是挑一个阶段完整走一遍逻辑维，让阅卷人看到你真的会用这个框架。

例 2（工程判断：文档驱动 vs 模型驱动） 某装备研制项目，涉及 5 家单位、12 个专业，接口频繁变更。用文档管理还是 MBSE？

解答：
- 优先 MBSE。理由：多单位多专业、接口频繁变更，文档模式下"改一处要通知所有人、且容易漏"；模型可做单一数据源，接口变更自动传导，还能做早期仿真验证；
- 代价：需要统一建模语言与工具链、团队学习成本高、初期投入大；
- 折中：先用 MBSE 管接口与关键子系统，非关键部分仍用文档，逐步迁移。

点评：这是典型的"方法选择跟着协作复杂度走"——单团队小项目用文档更轻，多单位强耦合才值得上 MBSE。

五、常见误区

误区一：把系统工程当成"项目管理"。
项目管理管进度、成本、风险；系统工程管"技术方案的分解与集成"，两者互补但不同。

误区二：认为霍尔三维是"7×7=49 个步骤依次执行"。
时间维是阶段，逻辑维是每阶段内的思维程序，二者是"每个阶段都要走一遍逻辑维"，不是串成 49 步。

误区三：以为 MBSE 就是"画 UML 图"。
MBSE 的核心是"模型作为唯一数据源、可追溯、可仿真"，画图只是表现形式。

第 13 节 系统性能：快慢怎么度量与优化

本节要解决的问题：如何用数字说明一个系统"快"，又如何判断优化该往哪里投？

一、一句"系统很慢"背后的三件事

用户说"系统很慢"，可能是：单次请求响应 3 秒（延迟高）、每秒只能处理 50 笔（吞吐低）、高峰期直接超时（稳定性差）。

这三件事的优化手段完全不同：延迟靠减少单次处理路径（缓存、索引），吞吐靠并行与解耦（集群、消息队列），稳定性靠容量规划与限流降级。

所以性能的第一步不是优化，是说清楚在说哪个指标。

二、指标：先分清三组

这里列出一大串指标，记住三组就够用：

  • 计算能力：主频、运算速度、MIPS、PDR（数据处理速率）；
  • 服务能力：吞吐率、响应时间、并发数、最大并发连接数；
  • 可靠性：RASIS——可靠性（Reliability）、可用性（Availability）、可维护性（Serviceability）、完整性、安全性；以及 MTBF（平均无故障时间）、MTTR（平均修复时间）。

可用性公式很实用：A = MTBFMTBF + MTTR。要提升可用性，要么拉长 MTBF（少出故障），要么缩短 MTTR（快恢复）——工程上后者往往更划算。

三、计算：MIPS 与 Amdahl

MIPS（每秒百万条指令）衡量处理器运算速度：MIPS = 指令数执行时间 × 106 = 主频 ÷ CPI ÷ 106。

Amdahl 定律是本节的核心，它回答"优化局部到底值不值"：

总加速比 = 1(1 - 增强比例) + 增强比例增强加速比

它的含义是：只优化一部分，整体加速有上限。如果只有 40% 的执行时间能被优化，那么即使把这一部分加速到无穷快，总加速比也不会超过 1/(1-0.4) = 1.67 倍。

想一想 ①：为什么"只优化瓶颈"是共识？用 Amdahl 定律解释，如果优化了非瓶颈部分会怎样。

四、设计与评估

性能设计：的"性能调整"分两步——准备（识别约束、指定负载、设置性能目标）与循环（收集 → 分析 → 配置 → 测试）。

性能评估：方法有基准测试、压力测试、可靠性测试。基准程序分四类，准确度递减：真实程序 > 核心程序 > 小型基准程序 > 合成基准程序。常见基准有 Dhrystone（整数）、Linpack（浮点）、Whetstone、SPEC、TPC。

想一想 ②：为什么"合成基准程序"的准确度最低，但厂商最喜欢用它宣传？

五、例题精解

例 1（工程计算：Amdahl 与优化决策） 某系统耗时分布：数据库查询 45%、业务逻辑 35%、网络传输 15%、其他 5%。团队只能做一项优化，候选是"查询加索引提速 3 倍"或"逻辑重构提速 2 倍"。选哪个？

解答：
- 加索引：增强比例 0.45，加速 3 → 总加速 = 1/(0.55 + 0.45/3) = 1/(0.55+0.15) = 1.43 倍
- 重构逻辑：增强比例 0.35，加速 2 → 总加速 = 1/(0.65 + 0.35/2) = 1/(0.65+0.175) = 1.21 倍
- 选加索引。虽然"提速倍数"看起来都不夸张，但索引作用在占比更大的部分。

点评：优化决策的公式化表达就是"增强比例 × 加速倍数"，而不是"哪个手段听起来更高级"。这条也是论文里论证"性能优化思路"的标准依据。

例 2（工程判断：基准程序的选择） 某团队要采购数据库服务器，厂商给出 SPEC 跑分与 TPC-C 跑分。业务是 OLTP 交易系统，应该看哪个？

解答：
- 看 TPC-C。它是专门针对 OLTP 的基准（模拟订单录入、支付等事务），与业务形态匹配；
- SPEC 系列更偏通用计算/Web 服务，不能代表交易型负载；
- 更稳妥的做法是用自己的真实业务负载做压测（的"真实程序"准确度最高），厂商跑分只作参考。

点评：基准测试的坑在于"跑分场景与业务场景不匹配"。选基准的原则是"越接近真实负载越可信"。

六、常见误区

误区一：把"响应时间"与"吞吐量"混为一谈。
二者常常互相制约：批量处理能提高吞吐但拉长单次响应；实时系统反之。

误区二：认为优化一定成正比。
Amdahl 定律说明整体加速受未优化部分限制，优化非瓶颈部分收益极低。

误区三：认为 MTBF 越大系统越可用。
可用性取决于 MTBF 与 MTTR 的比值。MTBF 很长但一次故障恢复要 10 小时，可用性依然很差。

误区四：把 SPEC 跑分直接当成业务性能。
跑分是特定场景的加权结果，业务负载不同，结论可能完全相反。
