第 1 节 信息系统架构是什么

本节要解决的问题：同一个系统为什么要有"物理结构"和"逻辑结构"两种描述？

一、两种结构

结构 描述什么 关注者
物理结构 硬件、网络、部署节点的实际组织 运维、集成
逻辑结构 功能单元、数据流、模块关系 设计者、开发者

物理结构回答"跑在哪几台机器上、怎么连"，逻辑结构回答"分成几块、怎么交互"。同一个逻辑结构可以对应多种物理部署（单体部署、集群部署、云上部署）。

二、架构风格在信息系统中的落点

K5 讲的五种风格，在信息系统里最常用的是三类：

  • 分层：表现层、业务层、数据层——几乎所有企业系统的基本骨架；
  • 客户机/服务器：资源不对等下的共享，演化出多层 C/S 与 B/S；
  • 面向服务：把能力封装成可复用服务，支撑集成与复用（K9 展开）。

三、为什么企业系统偏爱分层

三个理由：

  1. 关注点分离：界面变化不影响业务逻辑，业务变化不影响数据库；
  2. 团队分工：前端、后端、DBA 可并行工作；
  3. 可替换：换数据库、换前端框架时，只需改相邻层。

代价是调用链变长、性能损耗，且分层不当会退化成"每层只做透传"的空壳。

想一想 ①：如果一个系统的"业务层"里只有一句"调用数据层"，这说明什么？

四、例题精解

例（工程判断：逻辑与物理的区分） 某系统做了三项调整：① 把数据库从单机换成主从集群；② 把"订单"与"支付"拆成两个独立服务；③ 新增 CDN 加速静态资源。哪些属于逻辑结构变化？

解答：
- ① 物理结构变化：逻辑上仍是"数据访问"这一层，只是部署形态变了；
- ② 逻辑结构变化：模块边界改变，出现了新的服务单元与接口；
- ③ 物理结构变化：逻辑上仍是静态资源访问，只是分发方式变了。

点评：判据是"是否改变了功能单元与接口"。改部署、改容量、改分发方式，属物理结构。

五、常见误区

误区一：认为物理结构就是"部署图"。
部署图只是物理结构的一种表达，还包括网络拓扑、容量分布。

误区二：认为逻辑结构可以脱离物理约束设计。
逻辑结构最终要落到物理上，容量与延迟约束会反过来影响逻辑划分。

留一个问题：从最原始的单机程序到今天的服务化，架构模型经历了哪几步？

下一节看四种模型。

第 2 节 四种典型架构模型

本节要解决的问题：单机、C/S、SOA、企业数据交换总线，各自解决什么问题、留在什么场景？

一、模型的演进线索

四种模型的演进逻辑是"从封闭到开放、从耦合到解耦"：

单机 → 客户机/服务器（含多层）→ 面向服务 → 企业数据交换总线

二、单机应用模式

最简单：运行在一台物理机器上的独立应用，可以是多进程/多线程。

特点：

  • 部署简单、无网络开销；
  • 复杂单机系统并不少见（CAD、图像处理等），可能上百万行代码；
  • 局限：难以共享、难以扩展、难以与其他系统集成。

三、客户机/服务器模式

基于资源不对等、为实现共享而提出。

  • 两层 C/S：客户机（胖客户端）+ 数据库服务器，业务逻辑在客户端；
  • 多层 C/S（含 B/S）：增加应用服务器，形成表示层、功能层、数据层，客户端变"瘦"。

优点是共享与集中管理，缺点是客户端部署/升级成本（两层）或中间层成为瓶颈（多层）。

四、面向服务架构（SOA）模式

无论多少层 C/S，对外都只是一个整体。SOA 把能力拆成可复用的服务，服务之间通过标准接口与协议交互，从而实现跨系统集成与复用。

关键变化：接口标准化、服务可编排、松耦合。

五、企业数据交换总线

当企业内部有几十个异构系统时，点对点集成会形成"蜘蛛网"。企业数据交换总线（ESB/EAI） 提供统一的消息路由、协议转换与数据格式映射，把 n×n 的连接收敛为 n 条接入。

想一想 ①：有了 SOA 和 ESB，为什么后来还出现了微服务？提示：从"集中式总线"的角度想。

六、例题精解

例（工程选型：集成方式） 某集团有 20 个异构系统（不同厂商、不同数据库），需要打通数据。方案 A 点对点接口，方案 B 建 ESB 统一接入，方案 C 全部改造成微服务。请比较并推荐。

解答：
- A：接口数随系统数平方增长（190 条），运维不可控，适合 2—3 个系统的临时集成；
- B：统一路由与协议转换，接入成本线性（20 条），适合异构、多厂商、改造代价大的现状；缺点是总线可能成为单点与瓶颈；
- C：最彻底但代价最大，等于重建，且 20 个系统同时改造风险不可控；
- 推荐 B 起步，逐步把高频、核心能力服务化，避免一次性大改（呼应 K7 的平滑演化原则）。

点评：集成方案的选择依据是"系统数量 × 改造代价 × 一致性要求"。

留一个问题：一个组织的信息系统不止一套，从全局看该怎么分层组织？

下一节看企业信息系统总体框架。

第 3 节 企业信息系统总体框架

本节要解决的问题：企业架构为什么常被拆成业务、应用、数据、技术四个视角？

一、四个视角

视角 关注 典型产物
业务架构 业务流程、组织、能力 业务流程模型、能力地图
应用架构 有哪些应用系统、如何交互 应用蓝图、集成关系
数据架构 数据分布、主数据、数据流 数据模型、数据分布图
技术架构 基础设施、中间件、平台 技术栈、部署架构

四者的关系是：业务驱动应用，应用产生与消费数据，数据依托技术承载。

二、信息系统架构的一般原理

几条常被引用的原理：

  1. 业务与 IT 对齐：架构服务于业务目标，而不是技术偏好；
  2. 分层与解耦：通过分层隔离变化；
  3. 标准化：接口、数据、协议标准化，是集成的前提；
  4. 可演进：架构要能随业务变化调整（K7）。

三、总体框架的意义

总体框架解决"全局视角"问题：单个系统的架构再好，如果彼此重复建设、数据不通，整体仍是低效的。

它带来的三个好处：

  • 避免重复建设：识别哪些能力可以共享（用户中心、支付中心、消息中心）；
  • 识别集成点：明确系统之间的接口责任；
  • 支撑决策：投资优先级、改造顺序有据可依。

想一想 ①：为什么"数据架构"常常是企业架构中最难的一层？（提示：数据有归属、有口径、有合规）

四、例题精解

例（工程项目：从系统视角到全局视角） 某集团 12 家子公司各自建了"用户管理"系统，重复投入且用户数据不一致。请从企业架构四视角给出改进思路。

解答：
- 业务架构：梳理各公司的用户相关流程，识别共性与差异；
- 应用架构：将"用户管理"识别为共享能力，规划建设统一的用户中心，各系统改为调用；
- 数据架构：定义用户主数据标准（唯一标识、字段口径、更新责任），建立主数据管理；
- 技术架构：统一认证与授权平台（IAM），提供标准化接口。

点评：这类题的答题骨架就是"四视角逐条说明改什么"，比单说"建个中台"更有说服力。

五、常见误区

误区一：认为企业架构就是"几张全局图"。
它是一套决策体系，图只是表达。

误区二：认为技术架构最重要。
业务对齐才是目的，技术只是承载。

误区三：认为数据架构是 DBA 的事。
数据架构涉及口径、归属与治理，是跨部门决策。

下一节讲 ADM。

第 4 节 ADM 架构开发方法

本节要解决的问题：TOGAF 的 ADM 分哪几个阶段？为什么中间要有一个"需求管理"贯穿？

一、ADM 是什么

ADM（Architecture Development Method，架构开发方法） 是 TOGAF 的核心，提供了一套迭代的、分阶段的企业架构开发流程，从架构愿景一直走到变更管理。

二、八个阶段（A—H）

阶段 名称 主要工作
预备 Preliminary 确定组织、原则、工具与治理
A 架构愿景 明确范围、目标与干系人
B 业务架构 业务流程、组织与能力
C 信息系统架构 应用架构 + 数据架构
D 技术架构 平台、基础设施
E 机会与解决方案 识别可实施的项目与迁移路径
F 迁移规划 制定实施与迁移计划
G 实施治理 管控实施过程符合架构
H 架构变更管理 管理架构演进

需求管理（Requirements Management） 是贯穿 A—H 的中心环节：需求在各阶段被提出、被验证、被回溯。

三、两个关键理解

  1. 它是迭代的：B—D 之间会反复调整，架构不是一次画成；
  2. 它衔接"规划"与"实施"：E、F 把架构转成项目与计划，G、H 把实施拉回架构约束。

想一想 ①：为什么 ADM 把"机会与解决方案"单独设一个阶段，而不是直接进入迁移规划？

四、例题精解

例（工程项目：用 ADM 组织企业架构工作） 某集团要做三年信息化规划，现状是 30 个系统、数据口径不一、投资分散。请用 ADM 说明工作顺序与每阶段产出。

解答：
- 预备：成立架构组、确定架构原则与治理流程；
- A 愿景：明确三年目标（如"统一数据口径、核心能力共享"）、识别干系人；
- B 业务架构：梳理集团业务能力地图与关键流程；
- C 信息系统架构：应用蓝图（哪些系统保留/整合/新建）+ 数据架构（主数据、数据分布）；
- D 技术架构：统一平台与技术栈（云、中间件、集成平台）；
- E 机会与解决方案：把差距拆成可实施的项目（如"主数据平台建设""用户中心"）；
- F 迁移规划：排优先级与依赖，形成三年路线图；
- G/H：实施治理与变更管理。

点评：答题要点是"阶段顺序 + 每阶段一句产出"，并强调 E/F 是"架构转项目"的关键。

五、常见误区

误区一：认为 ADM 是瀑布流程。
它明确是迭代的，阶段间会回溯。

误区二：把 C 阶段只理解为"应用架构"。
C 包含应用架构与数据架构两部分。

误区三：忽视需求管理。
它是贯穿全程的中心环节，不是某个阶段的附属。

留一个问题：企业架构是全局，具体到一个系统，最常用的分层结构怎么设计？

下面两节看层次式架构的三层。

第 5 节 层次式架构：表现层

本节要解决的问题：界面代码为什么总是最先腐化？MVC、MVP 与"动态页面生成"各解决什么？

一、表现层的问题

表现层的典型病灶：

  • 页面里直接写 SQL 与业务判断；
  • 同一份校验逻辑在多个页面重复；
  • 换一次 UI 框架，业务代码跟着改。

根因是界面逻辑、业务逻辑、数据访问混在一起。表现层设计的目标就是分离这三者。

二、三种经典模式

模式 分工 适用
MVC Model 数据、View 视图、Controller 处理输入 传统 Web 与桌面应用
MVP View 与 Model 完全隔离，Presenter 协调 界面逻辑复杂、需可测试
MVVM ViewModel 暴露数据与命令，双向绑定 富客户端、前端框架

三者的共同目标：让 View 尽量"笨"，把逻辑放到可测试的地方。

三、UIP 与页面动态生成

UIP（User Interface Process） 的思想是把"界面流程"单独抽象出来：页面之间的跳转、状态保持、返回与中断，由一个流程组件统一管理，而不是散落在每个页面里。

动态生成指界面由配置/元数据驱动生成（如低代码平台、表单引擎）：用一套模型描述界面，运行时渲染。收益是变更快、一致性高，代价是灵活性受限、复杂交互难表达。

想一想 ①：如果业务要求"每个客户定制一套界面"，你会选择静态开发还是动态生成？判断依据是什么？

四、例题精解

例（工程项目：表现层重构） 某系统的 JSP 页面里既有 SQL、又有业务计算、还有页面跳转逻辑，改一次需求要动十几个页面。请给出重构方案。

解答：
- 分层剥离：SQL 移到数据访问层，业务计算移到业务层，页面只负责渲染；
- 引入 MVC：Controller 处理请求与流程，View 只做展示，Model 承载数据；
- 流程抽象：把页面跳转与状态管理抽到 UIP/流程层，避免散落；
- 校验统一：用统一校验框架，避免每个页面各写一套；
- 逐步推进：先抽数据访问，再抽业务，最后整理流程。

点评：这题的关键是"先分层再模式"——不分层直接用 MVC 只是换个名字。

五、常见误区

误区一：认为用了 MVC 框架就等于分层。
在 Controller 里写 SQL 与业务计算，等于没分层。

误区二：认为动态生成"万能"。
复杂交互与极致体验场景仍需手写。

误区三：忽视流程状态管理。
多步骤表单、跨页流程是最容易出问题的地方。

第 6 节 中间层与数据访问层

本节要解决的问题：业务逻辑层和数据访问层各自的典型设计与陷阱是什么？

一、业务逻辑层（中间层）

业务逻辑层的设计可拆成三块：

设计对象 关注
业务组件 按业务能力划分组件，组件对外只暴露接口
工作流 跨组件的流程编排：顺序、分支、并发、补偿
实体 业务对象的建模与持久化映射

业务层的设计原则：组件高内聚、流程与规则分离。把易变的规则（审批流、计费规则）从流程代码里抽出来，是提升可修改性的关键。

二、数据访问层

常见的有5 种数据访问模式，核心是"如何把 SQL 与业务代码解耦"：

模式 要点
在线访问（逐条） 直接连接数据库操作，简单但性能与耦合差
数据访问对象（DAO） 封装数据访问，隔离具体数据库
数据传输对象（DTO） 跨层/跨进程传数据，减少调用次数
对象/关系映射（ORM） 对象与表映射，自动化 CRUD
仓储（Repository） 以聚合为单位提供持久化接口，屏蔽查询细节

工厂模式常用于数据访问层：由工厂根据配置创建具体的数据访问实现，从而支持多数据库。

三、ORM 与 Hibernate

ORM 把对象模型映射到关系模型，典型价值是减少样板代码、屏蔽数据库差异。Hibernate 与 CMP（容器管理持久化）的设计思想：

  • Hibernate：以映射文件/注解描述对象与表的关系，提供会话管理与查询语言（HQL）；
  • CMP：由容器管理实体 Bean 的持久化，开发者只写字段与业务方法。

ORM 的代价：复杂查询吃力、性能调优难、容易产生 N+1 问题（K4 第 6 节）。

四、例题精解

例（工程项目：数据访问层设计） 某系统要同时支持 MySQL 与达梦，且报表模块有复杂多表关联。请设计数据访问层。

解答：
- 用 DAO/Repository + 工厂：定义数据访问接口，工厂按配置创建 MySQL/达梦实现，业务层只依赖接口；
- 简单 CRUD 用 ORM 减少样板代码；
- 复杂报表绕开 ORM 写原生 SQL，放进独立的查询组件，避免污染业务层；
- 跨层传输用 DTO，避免把实体直接暴露给前端（也防止懒加载陷阱）。

点评：四个要点——接口隔离、工厂创建、ORM 与 SQL 分工、DTO 传数据。

五、常见误区

误区一：认为 ORM 能替代一切 SQL。
复杂聚合与多表关联仍要手写。

误区二：把实体直接传给前端。
会暴露内部结构，还容易触发懒加载与序列化问题。

误区三：业务层里直接拼 SQL。
数据库一变，业务代码全改。
