第 1 节 架构是什么

本节要解决的问题：架构与"详细设计"的界限在哪？为什么同一套系统要用多个视图描述？

一、一句被说滥的话

"架构是系统的骨架"——这句话没错，但没法指导设计。更准确的说法来自 Bass、Clements 和 Kazman 的定义：

软件架构是系统的一个或多个结构，包括软件构件、构件的外部可见属性，以及它们之间的关系。

三个关键词值得拆开：

  • 构件：系统里承担计算的单元（模块、对象、服务、进程）；
  • 外部可见属性：只关心别人能看到的接口与行为，不关心内部实现——这是"架构"区别于"详细设计"的分界线；
  • 关系：构件之间怎么连（调用、消息、共享数据）。

一句话：架构关心"分几块、块之间怎么连、对方的可见接口是什么"，不关心"块内部怎么写"。

二、构件与连接件

架构描述里有两个基本角色：

角色 含义 例子
构件 计算或存储的单元 服务、模块、数据库、过滤器
连接件 构件之间的交互机制 调用、消息队列、管道、共享数据

很多风格的区别，本质上是连接件的区别：管道-过滤器的连接件是数据流管道，事件系统的连接件是事件总线，仓库风格的连接件是对中央数据的存取。

想一想 ①：如果把"函数调用"换成"消息队列"，构件本身不变，系统会变成什么风格？质量属性会怎么变？

三、为什么要多视图

一个系统不能只用一张图说清。要从不同视角观察架构，形成不同视图。

经典的 4+1 视图：

视图 关注 面向
逻辑视图 功能组织、对象与类 设计人员、用户
进程视图 并发、同步、性能 系统集成人员
开发视图（实现视图） 模块组织、编译与复用 开发人员
物理视图（配置视图） 部署到硬件节点 运维、系统工程师
场景/用例 串起四个视图的验证场景 全体

判断用哪个视图，看你关心什么质量属性：功能与可维护性看逻辑视图，性能与并发看进程视图，可移植与部署看物理视图。

四、架构为什么重要

三个层面的理由：

  1. 沟通：架构是干系人之间的共同语言，说"这是 C/S 结构"就能省掉大量解释；
  2. 决策的载体：早期决策（技术选型、分层、集成方式）代价最大、最难改；
  3. 质量的载体：性能、可用性、安全性等质量属性主要由架构决定，而非靠后期优化。

还有一句话值得记住：架构是演化的，不是一次成型的——需求与环境变化会驱动架构演化（第 8 节展开）。

五、例题精解

例（工程判断：架构决策的边界） 某团队争论三个问题：① 订单服务内部用策略模式还是状态模式；② 前端与后端通过 REST 还是消息队列通信；③ 数据库里某字段是否要加索引。哪些属于架构决策？

解答：
- ① 属于构件内部的实现细节，不是架构决策（不影响外部可见属性）；
- ② 属于连接件选择，直接决定耦合方式、可用性与一致性，是架构决策；
- ③ 属于物理设计/性能调优，尽管影响性能，通常归入详细设计与运维范畴。

点评：判据是"是否改变构件的可见边界或连接方式"。改连接件、改分层、改部署单元，都是架构决策。

六、常见误区

误区一：把架构等同于"高层设计文档"。
架构是一组结构决策，文档只是载体；没有决策的文档不叫架构。

误区二：认为架构只关心功能。
恰恰相反，架构主要承载质量属性（性能、可用、安全、可修改）。

误区三：认为视图越多越全越好。
视图是为特定关注点服务的，多余视图只增加维护成本。

第 2 节 架构风格总览

本节要解决的问题：到底什么是"架构风格"？五大类风格各自解决什么问题？

一、风格是"惯用模式"

定义是：

软件体系结构风格是描述某一特定应用领域中系统组织方式的惯用模式。

它定义一个系统家族，包含两样东西：

  • 词汇表：这类风格里有哪些构件与连接件类型；
  • 一组约束：这些构件如何组合。

举例：说"这是管道-过滤器风格"，听者立刻知道构件是过滤器、连接件是管道、数据单向流动——不需要任何细节。

二、五大类，十一种

大类 具体风格 核心特征
数据流 批处理、管道-过滤器 数据按流被逐步加工
调用/返回 主程序/子程序、面向对象、层次型、客户端/服务器 通过调用与返回传递控制
以数据为中心 仓库、黑板 有一个中央数据结构
虚拟机 解释器、规则系统 人为构造运行环境
独立构件 进程通信、事件系统 构件不直接交互

记忆方法：数据在流、控制在调、数据在中间、解释执行、各自独立。

三、怎么选风格

风格不是"越新越好"，要看质量属性：

想强化的属性 倾向的风格
可复用、可组合 管道-过滤器、分层
松耦合、可扩展 事件系统、进程通信
高并发、可伸缩 分层 + 服务化、事件驱动
可移植、可替换 分层、虚拟机（解释器）
处理非结构化问题 黑板

这句话很到位：风格的研究与实践促进设计重用，一些被验证过的方案可以可靠地用于新问题。

四、例题精解

例（工程项目：按风格归类） 判断下列系统属于哪种架构风格：① 编译器（词法→语法→语义→代码生成）；② 客服系统（坐席接起电话后触发录音、工单、质检三个模块）；③ 专家系统（规则库+推理引擎）；④ 数据仓库（多个分析工具共享一个中央数据存储）。

解答：
- ① 管道-过滤器：每个处理阶段是过滤器，数据单向流经管道；
- ② 事件系统（隐式调用）：接听事件触发多个注册的处理模块，触发方不关心谁响应；
- ③ 规则系统（虚拟机风格）：规则集 + 规则解释器 + 工作内存；
- ④ 仓库风格：中央数据结构被多个独立构件存取。

点评：归类题的抓手是"连接件是什么"——数据管道、事件、规则解释器、中央存储。

五、常见误区

误区一：认为风格之间互斥。
真实系统常是组合风格（分层 + 事件 + 管道），只要说清哪部分用哪种。

误区二：把设计模式等同于架构风格。
模式是类/对象级别的解法，风格是系统级组织方式。

误区三：认为风格只影响结构，不影响质量。
风格直接决定耦合、并发、可替换性，是质量属性的第一杠杆。

第 3 节 数据流风格

本节要解决的问题：数据一步步被加工时，用什么结构组织？批处理与管道-过滤器的关键差异是什么？

一、数据流风格的本质

数据流体系结构没有"程序计数器"——指令的可执行性由输入数据是否就绪决定，而不是由控制流决定。

这句话的含义是：系统由数据驱动，而不是由调用驱动。这一类分两种：批处理与管道-过滤器。

二、批处理

每个处理步骤是一个独立程序，前一步结束、数据完整后才开始下一步，数据以整体方式传递。

要素 内容
构件 独立的应用程序
连接件 某种媒介（如磁带、文件）
特点 顺序、整批、非交互

典型例子：传统的日终批处理（对账、结息、报表生成）。

优点：结构简单、易于并行化（不同批次可并行）、适合大数据量。
缺点：不适合交互式处理；一步失败往往要整批重来。

三、管道-过滤器

数据源源不断产生时，系统把处理分解为若干序贯步骤，每步由一个过滤器实现，步骤之间由管道传输数据流。

要素 内容
构件 过滤器（Filter）
连接件 管道（Pipe）
特点 流式、增量、可组合

优点：

  • 过滤器可独立替换与复用（只要接口约定一致）；
  • 支持并发（相邻过滤器可流水线作业）；
  • 便于添加新的处理步骤。

缺点：

  • 交互性差（不适合事件驱动的 UI）；
  • 过滤器之间需要统一的数据格式约定；
  • 某些需要全局状态的算法难以拆分。

想一想 ①：编译器为什么常用管道-过滤器？如果编译一个 10 万行的工程，中间结果要不要落盘？

四、两者的关键差异

维度 批处理 管道-过滤器
数据传递 整批、完整数据 流式、增量
时间关系 严格串行 可流水线并发
交互能力 无 弱
典型场景 日终批处理、离线计算 编译器、日志处理、ETL 流水线

五、例题精解

例（工程项目：处理链路设计） 某日志平台要处理每天 20TB 的访问日志：解析 → 过滤 → 富化（补充用户信息）→ 聚合 → 入库。要求新增字段时尽量不影响已有环节，且能横向扩展。

解答：
- 采用管道-过滤器：每个阶段是一个过滤器，阶段间通过队列/管道传递；
- 新增"补充地域信息"只需在富化后插入一个过滤器，其余不变（可复用、可组合）；
- 各过滤器可独立水平扩展（按队列积压情况扩实例）；
- 若某个阶段需要全量数据（如全局去重），则该阶段改用批处理作业，形成"流批混合"。

点评：这道题的答案里"插入一个过滤器、其余不变"正是管道-过滤器的核心价值——可组合性。

六、常见误区

误区一：认为管道-过滤器必须用消息队列实现。
管道可以是内存缓冲区、文件、套接字，形态不限。

误区二：认为批处理"过时了"。
离线计算、报表、对账仍以批处理为主，成本最低。

误区三：把数据流风格与控制流混淆。
数据流由数据就绪驱动，控制流由程序计数器驱动。

留一个问题：如果系统不是"数据流过"，而是"一个调一个"，那是什么风格？

下一节讲调用/返回。

第 4 节 调用/返回风格

本节要解决的问题：通过"调用—返回"组织系统，能演化出哪几种具体形态？分层与 C/S 的关键差别是什么？

一、分而治之的基本策略

调用/返回风格的核心思想是把大系统分解为子系统，以降低复杂度、提升可修改性。程序从起点执行构件代码，结束后把控制权返回给调用者。

这一类有四种：主程序/子程序、面向对象、层次型、客户端/服务器。

二、主程序/子程序

  • 构件：主程序与子程序（可合成为模块）；
  • 连接件：过程调用；
  • 特点：单线程控制，调用关系有层次性，子程序的正确性取决于它调用的子程序的正确性。

这是最经典的结构化程序组织方式，缺点是紧耦合、难以独立替换。

三、面向对象风格

  • 构件：对象（抽象数据类型的实例）；
  • 连接件：对象之间的消息/方法调用；
  • 特点：数据与操作封装在一起，通过接口交互，支持继承与多态。

相比主程序/子程序，它把"数据"也封装进构件，耦合更低，但对象之间的调用关系仍较紧密。

四、层次型风格

系统组织成层次结构，每层为上层提供服务、作为下层的客户；除精挑细选的输出函数外，内部层接口只对相邻层可见。

要点 说明
构件 各层（层内实现虚拟机）
连接件 层间协议
约束 只允许相邻层交互

优点：每层最多只影响两层；只要接口不变，每层可用不同方法实现——为重用提供强大支持。
缺点：分层过细会带来性能损耗（请求逐层穿越）；并非所有系统都能自然分层。

五、客户端/服务器

基于资源不对等、为实现共享而提出。

两层 C/S：数据库服务器 + 客户应用程序 + 网络。服务器负责数据管理，客户端负责与用户交互，称为"胖客户机、瘦服务器"。

三层 C/S：增加应用服务器，应用逻辑驻留在应用服务器，客户端只保留表示层，称为"瘦客户机"。三层分别是：

层 职责
表示层 用户接口（GUI）
功能层 业务处理逻辑
数据层 数据库管理系统

三层的好处是逻辑上独立：换数据库不影响界面，改界面不影响业务逻辑。

想一想 ①：为什么三层 C/S 被说成"瘦客户机"？如果把业务逻辑放回客户端会有什么问题？

六、分层与 MVC 一族

MVC 是分层思想在表现层的具体化：

模式 组成 特点
MVC Model（数据）、View（视图）、Controller（控制器） 视图与模型解耦，Controller 处理输入
MVP Model、View、Presenter View 与 Model 完全隔离，Presenter 承担交互逻辑
MVVM Model、View、ViewModel 双向绑定，ViewModel 暴露数据与命令

三者都为了把界面与业务分离，差别在"谁负责协调"：MVC 由 Controller，MVP 由 Presenter，MVVM 由数据绑定。

七、例题精解

例（工程项目：C/S 结构改造） 某单位的业务系统是两层 C/S：业务逻辑写在客户端，数据库直连。现在要支持 Web 访问、多地办公、并控制数据库账号外泄风险。请给出改造方案。

解答：
- 改造为三层 C/S（或 B/S）：把业务逻辑从客户端抽到应用服务器（功能层），客户端/浏览器只保留表示层；
- 数据层只允许应用服务器访问，客户端不再持有数据库账号（消除直连风险）；
- 应用服务器可横向扩展并做负载均衡，支持多地访问；
- 代价是增加一次网络跳转（性能略降）、需要维护应用服务器集群。

点评：这类题的答题套路是"问题现象 → 归到哪一层 → 改造后每层职责"，并补一句代价。

八、常见误区

误区一：认为分层越多越好。
层数增加会带来调用链变长、性能下降，层数应与变化边界匹配。

误区二：把两层 C/S 的"胖客户机"当成优点。
它意味着客户端承担业务逻辑，升级维护成本高。

误区三：认为 MVC 是架构风格。
MVC 更常被当作表现层的设计模式/结构模式，属于分层思想的局部应用。

误区四：混淆层次型与分层架构的"严格程度"。
层次型强调相邻层交互约束；工程上的"分层架构"常常允许跨层调用（需明确规范）。

留一个问题：如果所有构件都围着一个中央数据转，而不是互相调用，那是什么风格？

下一节讲以数据为中心。

第 5 节 以数据为中心的风格

本节要解决的问题：仓库与黑板都"有一个中央数据"，它们的区别在哪？黑板为什么适合非结构化问题？

一、两种"围着数据转"

以数据为中心的风格包括仓库与黑板，共同点是：系统中存在一个中央数据结构，多个独立构件对它进行操作。

区别在于中央数据的性质与构件的协作方式。

二、仓库风格

要素 内容
构件 中央数据结构 + 一组对中央数据进行操作的独立构件
连接件 仓库与独立构件之间的交互
特点 中央数据表示当前状态；构件之间的交互方式可能差异很大

典型例子：数据库系统（中央是数据库，应用是独立构件）、现代 IDE（中央是符号表/项目模型，插件独立处理）。

优点：数据集中、易于一致性与共享；构件可独立演进。
缺点：中央数据成为单点与瓶颈；构件之间对数据模式的依赖较强。

三、黑板风格

黑板适用于复杂的非结构化问题，能在求解过程中综合运用多种知识源。

要素 内容
构件 黑板（共享数据）、知识源（独立的知识模块）、控制模块
连接件 对黑板的直接存取与知识源间的触发
特点 解空间被组织成分级结构，每层由唯一词汇描述，代表问题的部分解

工作机制：每个知识源负责把某一层次的信息转换成同层或相邻层的信息；控制模块决定下一步由哪个知识源处理。

典型应用：语音识别、模式识别，以及松耦合代理的数据共享存取。

想一想 ①：为什么黑板要"分级结构"？如果所有知识源都直接在同一个平面上写数据，会有什么问题？

四、仓库与黑板的对比

维度 仓库 黑板
中央数据 表示当前系统状态的数据 分级的、逐步完善的问题解
谁决定下一步 外部调用者/应用逻辑 控制模块（根据黑板状态选知识源）
适用问题 数据结构清晰、共享需求强 非结构化、需要多知识源协作
典型场景 数据库、IDE、编译器的符号表 语音识别、模式识别、专家系统前端

一句话记：仓库是"共享的数据"，黑板是"逐步求解的过程"。

五、例题精解

例（工程项目：选仓库还是黑板） 某医学影像辅助诊断系统：输入影像后，需要依次经过"去噪→分割→特征提取→病灶分类→报告生成"，每个环节由不同算法团队提供，且某些环节在置信度不足时会回头要求重做前一步。应选哪种风格？

解答：
- 选黑板风格。理由：问题非结构化、需要多知识源（各算法）协作；解是逐步完善的（中间结果写在黑板上）；控制模块可根据置信度决定回溯或换算法——这正是黑板的"分级解空间 + 控制模块"。
- 若流程完全固定、无反悔，则用管道-过滤器更简单高效。

点评：判断依据是"要不要根据中间结果动态决定下一步"。要，选黑板；不要，选管道。

六、常见误区

误区一：认为仓库风格就是"用数据库"。
几乎所有系统都用数据库，但仓库风格强调的是"中央数据结构 + 独立构件围绕它协作"这一组织结构。

误区二：把黑板等同于"消息总线"。
消息总线传递的是事件，黑板存放的是共享的问题解状态。

误区三：认为以数据为中心的风格一定性能差。
中央数据可以是高性能存储，关键是并发控制与分区策略。

留一个问题：如果系统本身要"解释"用户写的规则或脚本，架构上该怎么做？

下一节讲虚拟机风格。

第 6 节 虚拟机风格

本节要解决的问题：解释器风格为什么能带来灵活性？规则系统由哪四部分组成？

一、造一个自己的运行环境

虚拟机风格的基本思想是：人为构造一个运行环境，在这个环境之上解析并运行自定义语言，从而增加架构灵活性。

代价也很明确：多一层解释，性能必然下降。

二、解释器风格

解释器通常包含四部分：

组成 作用
解释引擎 完成解释工作
存储区 存放将被解释的代码
当前状态数据结构 记录解释引擎的工作状态
执行进度结构 记录源代码被解释执行到哪

解释器的核心价值是弥合程序语义与硬件语义的差异（如 JVM 弥合 Java 字节码与各平台机器指令）。

两个要点值得记住：它通常是"软件中含有一个虚拟机，仿真硬件执行过程"；缺点是执行效率较低，典型例子是专家系统。

三、规则系统

基于规则的系统包括四部分：

组成 作用
规则集 业务规则（条件—动作）
规则解释器 执行规则的引擎
规则/数据选择器 决定当前用哪条规则
工作内存 存放事实与中间结果

工作流程是经典的"匹配—选择—执行"循环：把工作内存中的事实与规则集匹配，选出可执行规则，执行后更新工作内存，再循环。

想一想 ①：把风控规则写成代码里的 if-else，与放进规则引擎，各有什么代价？什么时候值得用规则引擎？

四、两种虚拟机的差异

维度 解释器 规则系统
被解释的对象 程序代码（脚本/字节码） 业务规则
核心组成 引擎 + 存储 + 状态 规则集 + 引擎 + 选择器 + 工作内存
灵活性来源 语言层可扩展 规则可热更新、业务人员可维护
典型场景 脚本引擎、JVM、DSL 风控、审批、促销规则

五、例题精解

例（工程项目：规则引擎的取舍） 某银行的风控规则每月调整 20 次以上，每次调整需要开发改代码、测试、发版，平均 5 天。请评估是否引入规则引擎，并说明代价。

解答：
- 值得引入：规则高频变更、且规则相对独立于主流程，规则引擎可把"改规则"从发版变成配置，缩短响应时间到小时级；
- 代价：① 引入解释执行，性能低于硬编码（需评估单笔耗时是否可接受）；② 规则表达能力受限，复杂逻辑仍需代码；③ 需要规则治理（版本、测试、回滚），否则规则本身成为风险源；
- 折中：核心交易链路保留硬编码，非核心或易变规则放引擎。

点评：虚拟机风格的价值与代价是成对的——灵活性来自"晚绑定"，代价来自"多一层解释"。

六、常见误区

误区一：认为解释器只用于编程语言。
DSL、模板引擎、公式计算都属解释器思路。

误区二：认为规则引擎能替代复杂业务逻辑。
它擅长"条件—动作"型规则，流程编排与复杂计算仍靠代码。

误区三：忽视规则引擎自身的治理成本。
规则版本、冲突检测、回归测试缺一不可。

留一个问题：如果构件之间根本不互相调用，而是"谁关心谁注册"，那是什么风格？

下一节讲独立构件。

第 7 节 独立构件风格

本节要解决的问题：构件互不直接调用，怎么协作？隐式调用带来什么好处、又埋下什么隐患？

一、松耦合的代价与收益

独立构件风格强调：每个构件相对独立，彼此不直接通信，以降低耦合、提升灵活性。包括两种：进程通信与事件系统。

二、进程通信风格

要素 内容
构件 独立的过程（一般为命名过程）
连接件 消息传递
通信方式 点到点、同步/异步、远程过程调用（RPC）

它的特点是"构件之间不共享内存，只交换消息"，天然适合分布式环境。

三、事件系统（隐式调用）

核心思想：构件不直接调用某个过程，而是触发或广播事件；其他构件把过程注册到事件上，事件发生时系统自动调用所有注册的过程。

要素 内容
构件 模块（过程或事件集合）
连接件 事件（发布/订阅）
角色 事件源、事件管理器、事件处理器

最大的特点：事件的触发者不知道哪些构件会受影响，也不假定处理顺序。

一个典型的例子：调试器在断点处停下时声明事件，编辑器自动滚动到断点、变量监视器刷新——调试器只管声明事件，不关心谁响应。

优点：
- 松耦合，新增订阅者不影响发布者；
- 可扩展性强，适合插件化、UI 联动、系统集成。

缺点：
- 无法预知处理结果与顺序，调试与测试困难；
- 事件链路过长时难以追踪；
- 可能出现事件风暴、循环触发。

想一想 ①：电商下单后要触发"扣库存、发短信、加积分、写日志"，用事件系统和用直接调用各有什么利弊？

四、例题精解

例（工程项目：订单后置动作的解耦） 下单成功后需要做四件事：扣减库存、发确认短信、累加积分、写审计日志。当前是串行直接调用，导致下单接口耗时 800ms，且任一环节失败都会影响下单。请给出改造方案。

解答：
- 采用事件系统（隐式调用）：下单成功后发布"订单已创建"事件，四个处理方各自订阅；
- 效果：下单主链路只需写库 + 发事件，耗时降到百毫秒级；短信、积分、日志失败不影响下单；
- 需配套：① 消息可靠性（持久化、重试、死信队列）；② 顺序与幂等（积分累计要幂等）；③ 可观测性（事件链路追踪），弥补"看不见谁在处理"的缺点；
- 若库存必须强一致（不能超卖），则扣库存仍应同步或采用预留机制，不能纯异步。

点评：这道题的关键是"哪些能异步、哪些必须同步"——事件驱动不是万能的，强一致环节要留在主链路。

五、常见误区

误区一：认为事件驱动天然可靠。
事件可能丢失、重复、乱序，需要持久化与幂等设计。

误区二：认为隐式调用"没有耦合"。
发布者与事件定义之间存在语义耦合（事件结构变了，订阅者都要改）。

误区三：把进程通信与事件系统混为一谈。
进程通信是"点对点消息"，事件系统是"发布/订阅广播"。

下一节讲 ABSD。

第 8 节 基于架构的软件开发（ABSD）

本节要解决的问题：ABSD 与常规开发方法有什么不同？从需求到架构、再到实现，具体分哪几步？

一、为什么需要"架构驱动"

传统方法把架构当作设计阶段的一个产物；ABSD（Architecture-Based Software Design）则把架构当作开发的核心驱动力：先定架构，再让需求、设计、实现围绕架构展开。

定义是：ABSD 是自顶向下、递归细化的方法，软件系统的体系结构通过该方法得到细化。

二、三个关键概念

1. 设计元素：最顶层把系统分解为若干概念子系统和一个概念构件，逐层细化到可实现的构件。

2. 视角与视图：从不同视角观察架构，形成不同视图（逻辑视图、进程视图、实现视图、配置视图）。选择哪些视图，取决于要关注哪些质量属性。

3. 用例与质量场景：用例用于功能需求的驱动，质量场景用于非功能需求的驱动——这是 ABSD 的一个要点：质量属性要靠场景来落地，而不是靠形容词。

想一想 ①：为什么 ABSD 强调"用质量场景驱动"？只写"系统要高性能"有什么问题？

三、ABSD 的开发模型

开发模型大致是这条链：

体系结构需求 → 体系结构设计 → 体系结构文档化 → 体系结构复审 → 体系结构实现 → 体系结构演化

阶段 主要工作
需求 从需求中提取质量目标与约束，形成质量场景；确定哪些需求"架构敏感"
设计 选择风格、划分构件、定义接口与连接件，产出架构视图
文档化 用标准化的架构描述记录（视图、接口、决策理由）
复审 组织评审，检查是否满足质量场景与约束
实现 按架构映射到构件与团队分工，逐层细化
演化 需求与环境变化时，按"0:N 更新构件相互作用"的方式演进

两个容易被忽略的点：

  • 文档化不只是画图，还要记录决策理由（为什么这样分层、为什么选这个风格）；
  • 复审要对照质量场景逐条验证，而不是只看图画得对不对。

维度 常规方法 ABSD

变更应对 改设计 架构演化（构件交互关系的更新）

五、例题精解

例（工程项目：把质量需求变成架构决策） 某系统提出三条需求：① 支持 5000 并发；② 单点故障不影响服务；③ 新增支付渠道不超过 2 人周。请把每条转成质量场景，并给出对应的架构决策。

解答：
- ① 性能场景："高峰期 5000 并发时，95% 请求响应 < 500ms" → 决策：分层 + 无状态服务 + 缓存 + 水平扩展；
- ② 可用性场景："任一节点故障时，服务在 30 秒内自动恢复，不丢请求" → 决策：集群 + 健康检查 + 故障转移 + 幂等重试；
- ③ 可修改性场景："新增支付渠道只需实现统一接口，不改核心流程" → 决策：策略模式/插件式架构，支付渠道作为可替换构件。

第 9 节 架构复用与特定领域软件架构（DSSA）

本节要解决的问题：架构怎么复用？DSSA 的"三层次、三活动"分别是什么？

一、从"复用代码"到"复用架构"

复用代码能省编码时间，但架构决定了系统的骨架——复用架构的收益远大于复用代码。

软件架构复用分两类：

  • 资产复用：复用已有的架构资产（架构、构件、文档、测试用例）；
  • 过程复用：复用开发过程与经验（如标准过程、检查单）。

二、复用的对象与形式

对象 形式
架构本身 参考架构、架构模式
构件 构件库、开源组件
领域模型 领域知识、术语体系
过程资产 过程模板、检查单、估算模型

三、DSSA：为一个领域造"标准架构"

DSSA（Domain Specific Software Architecture） 的定义：在一个特定应用领域中，为一组应用提供组织结构参考的标准软件体系结构。

两个有代表性的定义：

  • Hayes Roth：专用于一类特定任务领域、能在整个领域有效使用、为成功构造应用系统限定了标准组合结构的软件构件集合；
  • Tracz：特定问题领域中支持一组应用的领域模型、参考需求、参考体系结构组成的开发基础，目标是支持该领域中多个应用的生成。

DSSA 的必备特征：有严格定义的问题域与解决域；具有普遍性，可用于领域内特定应用的开发；是整个领域构件组织模型的恰当抽象；具备该领域固定的、典型的可重用元素。

四、DSSA 的三个层次

层次 面向 内容
领域开发环境 领域专家/架构师 领域分析、领域设计，产出参考架构与可复用构件
领域特定应用开发环境 应用开发者 基于参考架构与构件，选择、配置、生成应用
应用执行环境 最终系统 运行生成的应用

一句话记：上层造资产，中层用资产，下层跑系统。

五、DSSA 的三个基本活动

活动 产出
领域分析 领域模型（术语、共性需求、可变性）
领域设计 参考体系结构（DSSA 本身）
领域实现 可复用构件与生成器

三者是迭代的：领域分析发现共性 → 领域设计固化结构 → 领域实现产出资产 → 实践中反馈修正领域模型。

例（工程项目：领域内多系统建设） 某集团要在 12 个省份分别建设"医保结算系统"，业务规则 80% 相同、20% 因地方政策不同。当前每个省独立招标建设。请用 DSSA 思路给出改进方案。

第 10 节 事件驱动架构的工程边界

本节要解决的问题：事件驱动架构（EDA）与"事件系统风格"是同一件事吗？什么场景适合、什么场景不适合？

一、从"风格"到"架构范式"

第 7 节讲的是事件系统作为架构风格：构件不直接调用，而是触发事件、注册处理。

事件驱动架构（EDA） 是把这个思想上升为系统级的架构范式：以事件的产生、检测、消费与响应为核心组织整个分布式系统，组件之间通过异步事件通信解耦。

区别在于范围：风格描述"构件怎么交互"，范式描述"整个系统的组织方式与数据流"。

二、三类角色

角色 职责
事件生产者（Producer） 检测状态变化并发布事件
事件通道（Broker / Topic） 持久化、路由、分发事件
事件消费者（Consumer） 订阅并处理事件，可能再产生新事件

关键设计点：事件通道要能持久化，否则消费者宕机就丢事件；事件要带唯一 ID，以便幂等与去重。

三、三种常见的事件使用模式

模式 做法 适用
事件通知 事件只带"发生了什么"，消费者回查详情 解耦优先、事件很小
事件携带状态 事件里带足够数据，消费者无需回查 减少耦合调用、性能优先
事件溯源（Event Sourcing） 以事件序列作为唯一事实来源，状态由重放事件得到 需要审计、可回溯

第三种最重：它把"存状态"改成"存变更历史"，天然支持审计与回放，但查询需要物化视图，复杂度高。

四、适用边界（重要）

事件驱动不是万能的。判断很清楚：

适合：事件驱动的数据计算任务、计算时间短的请求/响应应用、没有复杂相互调用的长周期任务。

不适合：

  • 涉及频繁的外部 IO（网络、存储、服务间调用）——繁重的 IO 负担会让时延变大；
  • 复杂的相互调用链——链路一长，事件编排与排错成本急剧上升；
  • 强一致、低延迟的核心交易主链路——异步会引入最终一致与补偿。

想一想 ①：为什么"计算时间短"反而是适合 Serverless/事件驱动的条件？长任务会带来什么问题？

五、与消息队列的关系

  • 消息队列是传输设施，EDA 是架构范式；
  • 用 MQ 不等于做了 EDA：如果只是"点对点发个消息"，仍是调用式思维；
  • 真正的 EDA 要满足：事件是领域事实（已发生的事）、生产者不关心谁消费、消费者可独立增减。

命名也能帮助判断：事件名应是过去式（OrderCreated、PaymentCompleted），而不是命令式（CreateOrder）——命令式意味着生产者知道谁该做什么，那就退回了调用式。

六、例题精解

例（工程项目：是否采用 EDA） 某系统有两块：① 订单创建后要做积分、通知、风控评分；② 核心支付扣款要求强一致、延迟 <100ms。请判断哪些适合 EDA。

*解答**：
- ① 适合：积分、通知、风控评分都是"订单已创建"这一事实的下游反应，彼此独立、可异步、失败可重试；
- ② 不适合：扣款要求强一致与低延迟，应留在同步主链路（或采用 TCC 预留 + 确认）；
- 设计要点：订单服务只发 OrderCreated，不关心谁订阅；消费者各自幂等；通道持久化 + 死信队列；关键动作有对账兜底。

点评：EDA 的边界就是"反应可异步、可重复、可延迟"；主链路的强一致动作必须留在同步路径。

第 11 节 六边形架构

本节要解决的问题：怎么让核心业务逻辑完全不被数据库、框架、界面绑住？

一、分层架构的隐性问题

分层架构看起来是"上下关系"：表现层 → 业务层 → 数据层。但依赖方向是向下的——业务层要 import 数据访问代码。

结果：业务逻辑依赖了基础设施。换数据库、换框架，业务代码要跟着改；写单元测试也要连数据库。

六边形架构（Hexagonal Architecture，又称端口与适配器架构）要修正的正是这个方向。

二、核心思想：内外对称

把系统看成"内圈 + 外圈"：

圈层 内容
内圈（领域核心） 实体、领域服务、业务规则——不依赖任何技术
应用层 用例编排：调用领域对象、协调事务
端口（Port） 内圈定义的接口，声明"我需要什么能力"
适配器（Adapter） 外圈实现端口，对接数据库、消息、UI、第三方

"六边形"只是示意：有几个外部交互面就画几条边，边数没有含义。重点在端口在内、适配器在外。

三、依赖方向：全部指向内部

这是与分层架构最本质的差别：

  • 分层：业务层 → 数据层（业务依赖基础设施）；
  • 六边形：适配器 → 端口 → 领域（基础设施依赖领域，即依赖倒置）。

于是：换数据库只换一个适配器，领域代码一行不动；测试时用内存实现替代真实数据库。

四、两种端口

类型 方向 例子
驱动端口（入站） 外部驱动系统 REST 接口、消息消费者、定时任务
被驱动端口（出站） 系统驱动外部 仓储接口、消息发送、外部服务调用

入站适配器把 HTTP 请求转成用例调用；出站适配器把仓储接口实现成具体 SQL。

分析、设计、开发的三段流程

六边形不是画完就有的，它按三步落地：

阶段 做什么 产出
分析 识别用例与外部交互方（谁驱动系统、系统驱动谁），把每个交互面变成候选端口 用例清单、端口候选表
设计 在内圈建领域模型与用例，在边界定义端口接口（方法签名、数据契约）；为每个端口规划适配器 领域模型、端口契约、适配器清单
开发 内外并行：一队写领域与应用层（只依赖端口），一队写适配器；用内存实现做单元测试 可运行系统、测试替身

判断是否做对了，只看一条：断网、去掉数据库与消息中间件，领域层的单元测试还能不能全部跑通。能，说明依赖真的倒置了。

五、收益与代价

收益：

  • 领域逻辑与技术无关，可长期演进；
  • 可测试性强（适配器可替换为 Mock）；
  • 换技术栈的半径被限制在适配器层。

代价：

  • 间接层多：一个请求要经过适配器 → 端口 → 用例 → 领域，链路长；
  • 前期成本高：需要设计端口边界，小项目显得"过度设计"；
  • 团队要求：成员要理解依赖倒置，否则容易把业务写进适配器。

想一想 ①：如果团队把业务判断写在了 Controller 里，六边形架构还成立吗？

六、与分层架构、微服务的区别

对比项 分层架构 六边形架构 微服务
组织维度 上下（技术职责） 内外（依赖方向） 进程边界（业务域）
解决的问题 关注点分离 核心与基础设施解耦 独立部署与扩展
是否互斥 否 否 否

三者可以叠加：微服务内部用六边形组织，六边形内部再用分层思想划分模块。

七、例题精解

例（工程项目：改造为六边形） 某系统业务逻辑里直接写了 SQL 与 Redis 调用，换数据库要改 200 处。请给出六边形改造方案。

*解答**：
- 抽端口：把"存取订单"抽象为 OrderRepository 接口，"发送通知"抽象为 Notifier 接口，放在领域/应用层；
- 写适配器：OrderRepositoryJdbc、OrderRepositoryRedis 实现端口，SQL 与 Redis 调用全部移入；
- 依赖倒置：领域层只依赖接口，启动时注入具体适配器（DI 容器）；
- 入站适配：Controller、消息消费者作为入站适配器，只做协议转换与用例调用；
- 验证：用内存实现替换仓储，领域层可脱离数据库做单元测试。

点评：答题骨架是"先抽端口、再写适配器、最后倒置依赖"，并强调"领域层零技术依赖"这个验收标准。

八、常见误区

误区一：认为六边形就是"六层"。
边数无意义，关键在端口与适配器的内外关系。

误区二：认为用了依赖注入就是六边形。
要看领域层是否依赖了技术细节。

误区三：认为六边形等于微服务。
它是单个服务内部的组织方式，与进程边界无关。

本章总复习

一、这一章的主线

架构这一章回答的是"系统该怎么拆、拆开的部件怎么协作"。前七节建立"风格"的框架：构件与连接件、五大类十一种风格，逐一展开数据流、调用返回、以数据为中心、虚拟机、独立构件；第八节讲怎么用架构驱动开发（ABSD），第九节讲架构怎么复用（DSSA）；最后三节补三个工程视角——事件驱动架构的边界、六边形架构。

二、必须能说出的判断

  • 风格的本质是连接件：管道、事件、共享数据、解释引擎，换连接件就是换风格；
  • 分层只影响相邻层，这是它可替换性的来源，也是性能损耗的来源；
  • 事件系统的代价是"行为不确定"，所以关键链路必须留在同步路径；
  • 六边形架构的验收标准：断网、去掉数据库后，领域层单测仍能跑通；
  • 微服务不是 SOA 的对立面，而是把"重总线"换成"轻契约 + 自动化"。
